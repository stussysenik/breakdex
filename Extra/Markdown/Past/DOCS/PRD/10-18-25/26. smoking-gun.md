
⏺ FOUND THE SMOKING GUN!

  The Actual Root Cause: Race Condition in handleProgressUpdate

  Here's what happens:

  1. Line 386: coordinatePlayerInitialization sets loadingState = .loading(progress: 0.0, stage: 
  .preparingPlayback, ...)
  2. Line 390-392: The method has async suspension points (await MainActor.run {}, await 
  Task.yield())
  3. During this suspension: A stale progress update arrives from RobustVideoLoader with
  progress.value = 0.0
  4. Line 355: This calls handleProgressUpdate(progress)
  5. Line 503: handleProgressUpdate overwrites the preparingPlayback state with loadingState = 
  .loading(progress: progress.value, stage: stage, message: progress.message)
  6. Since progress.value = 0.0, this resets the progress to 0% while keeping the preparingPlayback
  stage!

  The Evidence Chain

  Line 386: preparingPlayback state set (progress: 0.0, stage: .preparingPlayback)
  Line 390: await MainActor.run {}  ← SUSPENSION POINT
  Line 391: await Task.yield()     ← SUSPENSION POINT
  Stale progress update arrives → handleProgressUpdate(0.0)
  Line 503: State overwritten → loadingState = .loading(progress: 0.0, stage: .preparingPlayback)
  Line 179: SelectClip observes "raw: 0%, calculated: 95% (preparingPlayback)"

  Why This Affects Physical Devices More

  Physical devices: Longer async suspension times → higher chance of stale progress arriving during
  suspension
  Simulator: Faster async suspension → stale progress arrives before or after state setting

  The Deterministic Fix

  The issue is that handleProgressUpdate doesn't check if the incoming progress is newer than the
  current state. It just overwrites blindly.
