## Analysis of the Core Problem: A Broken Lifecycle

The logs clearly show a pattern of creating a player for the preview screen, tearing it down, re-priming it for the trimmer, and then deallocating it entirely before the naming screen. This is where everything breaks.

1.  **The Smoking Gun (`deinit`):** The most critical log line is `ℹ️ 🎬 UNIFIED_VIDEO_PLAYER_VIEWMODEL (preview): deinit called`. This happens right after the user finishes trimming and before the naming screen appears. It tells us the `ViewModel` holding the `AVPlayer` is being completely **deallocated from memory**. The player, its configuration, and its ready-to-play state are all destroyed.

2.  **The Consequence (The Hang):** Your `NameMoveView` then tries to create a *new* video preview from scratch. It correctly uses `VideoTransformBuilder` to create a new, trimmed `AVPlayerItem`. However, the subsequent monitoring loop (`🎬 MONITOR: ⏳ Status is unknown, waiting for update...`) hangs because the `AVPlayerItem`'s status never changes from `.unknown` to `.readyToPlay`. This happens because an `AVPlayerItem` is just a data model; it only gets processed and loaded when it's associated with an active `AVPlayer` instance. Your monitoring starts before this association is fully effective, leading to an infinite wait.

3.  **The Root Cause (State Management):** The player's lifecycle is tied to individual views (`PreTrimView`, `TrimmerViewWrapper`) instead of the overall "add move" workflow managed by `AddMoveContainer`. When SwiftUI transitions between these views, the old view's state is destroyed, taking the video player down with it. The attempt to "re-prime" the player in the `TrimmerViewWrapper` is a patch on this flawed architecture, but the `deinit` proves the lifecycle is still not managed correctly.

In short, you're not passing a baton in a relay race; you're trying to build a new car at every checkpoint. 🏎️➡️🧱

## The Solution: A Unified & Persistent Video Pipeline

The solution is to establish a **single, persistent source of truth** for the video player that lives for the entire duration of the "add move" workflow. The `AVPlayer` should be created once, and its state should be modified as the user moves from previewing to trimming to naming.

Here’s how to build this robust pipeline on top of your existing code.

### 1\. Elevate the Player's Lifespan

The `UnifiedVideoPlayerViewModel` is the correct component to manage the player, but it needs to be owned by the parent `AddMoveContainer`. By initializing it there as an `@StateObject`, its lifecycle will be tied to the entire workflow, not the individual child views. It will persist across all screen transitions.

### 2\. Centralize Player Operations

Child views like `PreTrimView`, `TrimmerViewWrapper`, and `NameMoveView` should no longer manage or create player components. Instead, they will receive the *single, shared instance* of `UnifiedVideoPlayerViewModel` from the container and use its already-configured `AVPlayer`.

  * **Trimming:** Doesn't create a new player. It uses the existing one and simply tells the shared `ViewModel` the new start/end times.
  * **Naming:** Doesn't build a new player item from scratch. It receives the shared `ViewModel`, which has already been updated with a new, trimmed `AVPlayerItem` and is confirmed to be ready *before* the `NameMoveView` is even displayed.

### 3\. Refine the State Flow

The flow becomes much simpler and more reliable:

1.  **Video Selected:** `AddMoveContainer` loads the initial `AVAsset`.
2.  **Initialize Player:** It creates **one** `UnifiedVideoPlayerViewModel` instance and uses `VideoTransformBuilder` to prepare the initial `AVPlayerItem`.
3.  **Preview:** `PreTrimView` gets the shared `ViewModel` and plays the video.
4.  **Trim:** The user taps "Trim & Edit." The app transitions to `TrimmerViewWrapper`, which gets the same shared `ViewModel`. The player is paused, not destroyed.
5.  **Apply Trim:** The user finishes trimming. `AddMoveContainer` receives the new trim times. It calls a function on the shared `ViewModel` like `applyTrim(range:)`. The `ViewModel` uses `VideoTransformBuilder` to create a *new* trimmed `AVPlayerItem`, replaces the old item on its persistent `AVPlayer`, and waits for it to become ready.
6.  **Name:** Only after the new item is ready does the state transition to `.naming`. The `NameMoveView` receives the shared `ViewModel` with a perfectly prepared and ready-to-play trimmed video. **The hang is eliminated.**
