### 1\. Categorical System Analysis

Let's model the "Add Move" flow as a category where objects are states and morphisms are the functions or user actions that transition between them.

  * **Objects (States/Data Structures)**:

      * `ReadyState`: The initial state.
      * `LoadingVideoState`: Intermediate state while loading the initial asset.
      * `TrimmingState`: An object composed of `(VideoAsset, TrimmerViewModel, AddMoveUnifiedState)`. Critically, the user's trim/rotation edits exist *only* within the `TrimmerViewModel` sub-object during this phase.
      * `LoadingTrimmedAssetState`: Intermediate state while creating the trimmed preview.
      * `NamingState`: The final interactive state before saving.
      * `SavingState`: The state during the final save operation.
      * `ErrorState`/`SuccessState`: Terminal objects.

  * **Morphisms (Transitions/Functions)**:

      * `selectVideo`: `ReadyState` → `LoadingVideoState`.
      * `finishLoading`: `LoadingVideoState` → `TrimmingState`.
      * `userEdits`: `TrimmingState` → `TrimmingState` (This is a morphism on the `TrimmerViewModel` sub-object, which doesn't automatically update the parent `AddMoveUnifiedState` object).
      * **`prepareForNaming`**: `TrimmingState` → `LoadingTrimmedAssetState`. This is the morphism where the system breaks.
      * `finishAssetLoading`: `LoadingTrimmedAssetState` → `NamingState`.
      * `save`: `NamingState` → `SavingState`.

The core issue lies in the `prepareForNaming` morphism. It's an inefficient functor that fails to map all the necessary information from the source object (`TrimmingState`) to the target object (`LoadingTrimmedAssetState`). Specifically, it loses the final `(startTime, endTime, rotation)` data from the `TrimmerViewModel` sub-object.

### 2\. Chain-of-Thought Analysis & Root Cause Identification

By tracing the logs and code, we can pinpoint the exact failure chain.

1.  **Trimming Occurs**: The user interacts with the trimmer. The logs clearly show the `TrimmerViewModel` correctly processing and committing the final trim range.

      * `[TrimmerViewModel]: 🎯 Start time committed [...] committed_time="31.233333..."`
      * This confirms the `TrimmerViewModel` object holds the correct state: `startTime` is `31.233s` and `rotationQuarterTurns` is `1`.

2.  **"Continue" is Tapped**: The user initiates the `prepareForNaming` morphism by tapping "Continue".

      * `[FeatureRichTrimmer]: 👆 User Interaction: Continue button tapped`
      * This calls `FlowStateManager.proceedToNextState()` while in the `.trimming` case.

3.  **The Blind Spot (Missing Morphism)**: We examine `FlowStateManager.swift`. In the `proceedToNextState` function's `.trimming` case, the code immediately transitions to the next state (`.loadingTrimmedAsset`) and begins preparing the preview asset. **There is no step where the final trim/rotation values from `TrimmerViewModel` are copied back into the central `AddMoveUnifiedState`**.

4.  **State Preservation Fails**: Immediately after, the system calls `preserveTrimmingState()` to save data for the back button. This function reads from `AddMoveUnifiedState`, which still holds the *initial* values.

      * **Log Confirmation**: `🎬 AddMoveUnifiedState: 📊 TRIMMING STATE SNAPSHOT [...] Trim Range: 0.00s - 0.00s [...] Rotation: 0°`. This is the smoking gun. The state was preserved *before* it was updated.

5.  **Incorrect Duration Displayed**: The flow transitions to the `NamingState`. `NameMoveViewUnified` then tries to display the duration.

      * Its `calculateTrimDuration()` function reads from `unifiedState.trimStartTime` and `unifiedState.trimEndTime`, which are both `0.0`.
      * This triggers the fallback logic.
      * **Log Confirmation**: `🎬 NAME_MOVE_UNIFIED: ⚠️ No trim data available - using default duration: 3.00s`. This explains **Issue \#1**.

6.  **Save Operation Fails**: The user enters a name and taps "Save". This triggers the `save` morphism.

      * `FlowStateManager.initiateSaveOperation()` is called. It reads the trim times and rotation from `AddMoveUnifiedState`.
      * **Log Confirmation**: `🔄 FLOW_STATE: 📊 Save parameters - Name: 'okhhh', Duration: 0.00s, Rotation: 0°`. The incorrect `0.0` values are passed to the save coordinator.
      * `AddMoveSaveCoordinator` has a validation guard that fails.
      * **Log Confirmation**: `⚠️ 🎬 SAVE_COORDINATOR: Start time must be before end time 📋 Metadata: ["start_time": "0.0", "end_time": "0.0"]`. This explains **Issue \#2**.

### 3\. Categorizing the Failures

  * **Missing Morphism (State Synchronization)**: There is no function call (`morphism`) to transfer the final state from the `TrimmerViewModel` object back to the main `AddMoveUnifiedState` object before leaving the `TrimmingState`.
  * **Inefficient Functor (`prepareForNaming`)**: The process of moving from `TrimmingState` to the next state is an inefficient functor because it doesn't preserve the essential structure (the final trim/rotation data) of the source object.
  * **Isomorphism Violation (WYSIWYG Bug)**: The trimmed preview asset shown on the naming screen *is* correct because it's created directly from `TrimmerViewModel`. However, the underlying data used for saving is *not*, creating a buggy isomorphism where two things appear the same but behave differently.

-----

### 4\. Solution Hypothesis with Categorical Principles

The solution is to define and implement the missing `update_central_state: TrimmerViewModel -> AddMoveUnifiedState` morphism.

  * **Adjoint Functor Analogy**: We can think of the `TrimmerViewModel` as existing in a "detailed editing" category. The `prepareForNaming` function should act as a left adjoint functor, which has a corresponding right adjoint (`update_central_state`) that maps the information back to the "central state" category in the most natural way possible before proceeding.

  * **Commutative Diagram Verification**: The fix must ensure the following diagram commutes:

    1.  Path 1: `TrimmingState` → `userEdits` → `TrimmingState'` (with updated `TrimmerViewModel`) → `update_central_state` → `prepareForNaming` → `SavingState`.
    2.  Path 2 (The Goal): `TrimmingState'` → `save` → Correctly saved asset.
        Our fix ensures Path 1 results in the same outcome as the ideal Path 2 by synchronizing the state at the `update_central_state` step.

### 5\. Refined Implementation Plan & Code

The fix is surprisingly small but architecturally critical. We need to insert the state synchronization morphism into the `FlowStateManager`.

#### **Target File**: `FlowStateManager.swift`

#### **Target Function**: `proceedToNextState()`

#### **Targeted Code Snippet**:

Here is the refined code to be inserted into the `.trimming` case.

```swift
// 
// File: FlowStateManager.swift
// Function: proceedToNextState()
//

// ... inside the function
case .trimming:
    logger.info("🔄 FLOW_STATE: 📊 Transition: trimming → loadingTrimmedAsset")

    guard await validateTrimmingCompletion() else {
        logger.error("🔄 FLOW_STATE: ❌ Trimming validation failed")
        throw FlowStateError.trimmingIncomplete
    }

    // ============================ BEGIN SOLUTION ============================
    // This is the missing `update_central_state` morphism.
    // It synchronizes the final state from the TrimmerViewModel back to the
    // central AddMoveUnifiedState before transitioning away from trimming.
    logger.info("🔄 FLOW_STATE: 🧬 Synchronizing final trim state from TrimmerViewModel to AddMoveUnifiedState.")
    if let trimmerVM = unifiedState.trimmerViewModel as? TrimmerViewModel {
        let finalStartTime = trimmerVM.startTime.seconds
        let finalEndTime = trimmerVM.endTime.seconds
        let finalRotation = trimmerVM.rotationQuarterTurns

        // Update the central source of truth
        unifiedState.trimStartTime = finalStartTime
        unifiedState.trimEndTime = finalEndTime
        unifiedState.rotationQuarterTurns = finalRotation
        
        logger.info("🔄 FLOW_STATE: ✅ State synchronized. Start: \(finalStartTime)s, End: \(finalEndTime)s, Rotation: \(finalRotation * 90)°")
    } else {
        // This is a critical failure. If we can't get the trim data, we must stop.
        logger.error("🔄 FLOW_STATE: ❌ CRITICAL: Could not access TrimmerViewModel to synchronize state. The save operation will fail.")
        throw FlowStateError.missingViewModel("TrimmerViewModel")
    }
    // ============================= END SOLUTION =============================

    // Now, the rest of the flow can proceed with the correct data.
    let initialProgress = SimpleProgress(value: 0.0, message: "Preparing trimmed asset...")
    nextState = .loadingTrimmedAsset(progress: initialProgress)
    await performTransition(to: nextState, triggeredBy: "proceedToNextState_trimming")

    // Start asset preparation
    await prepareTrimmedAsset()

// ... rest of the function
```

### Why This Solves Both Issues

1.  **Correct Duration Display**: When `FlowStateManager` transitions to `.loadingTrimmedAsset` and then `.naming`, `AddMoveUnifiedState` now holds the correct `trimStartTime` and `trimEndTime`. `NameMoveViewUnified.calculateTrimDuration()` will read these correct values and display the proper duration, resolving **Issue \#1**.

2.  **Successful Save Operation**: When the user taps "Save" in `NameMoveViewUnified`, the `initiateSaveOperation()` in `FlowStateManager` will read the now-correct `trimStartTime`, `trimEndTime`, and `rotationQuarterTurns` from `AddMoveUnifiedState`. These valid parameters (`startTime < endTime`) will be passed to `AddMoveSaveCoordinator`, passing its validation check and allowing the video to be processed and saved correctly, resolving **Issue \#2**.

This single, targeted fix restores the integrity of your state machine and ensures the `prepareForNaming` morphism correctly preserves all necessary information, making the entire end-to-end flow robust and correct.

This specification outlines the work required to deliver a fully functional, precise, and fault-tolerant end-to-end "Add Move" flow for the BreakingFlashcards iOS application.

### \#\# Overview

This spec addresses critical bugs in the "Add Move" workflow that prevent users from successfully saving their trimmed and rotated video clips. The primary goal is to create a frictionless, WYSIWYG (What You See Is What You Get) experience where the user's exact edits in the trimming view are accurately reflected, saved, and persisted in both Core Data and the device's Photos library.

#### **User Persona: "The Athlete"**

  * **Needs**: A precise and reliable tool to quickly catalog training footage. They value mechanical precision and fault tolerance, expecting the app to work flawlessly without data loss or errors, regardless of interaction speed or video file size.
  * **Pain Points**: Frustration from incorrect data display (duration mismatch) and catastrophic failures (save errors) that break their workflow and cause them to lose their work.

#### **User Journey**

1.  **Selection**: The user selects a video from their Photos library.
2.  **Trimming**: The user precisely adjusts the start/end times and sets the rotation for the clip.
3.  **Naming**: The user sees a preview matching their exact edits (including the correct duration) and names the move.
4.  **Saving**: The user taps "Save," and the system transparently saves the asset to the "BreakDex" Photos album and creates a corresponding entry in the app's Core Data database.
5.  **Verification**: The newly created move is immediately available and viewable in the "Arsenal" section of the app.

-----

### \#\# Goals

  * **Fix Duration Display**: Ensure the duration displayed on the `NameMoveView` accurately reflects the final trim range set in the `TrimmerView`.
  * **Fix Save Functionality**: Resolve the root cause of the save error to enable successful persistence of the trimmed and rotated video asset.
  * **Ensure WYSIWYG Integrity**: Guarantee that the asset saved to Core Data and the Photos library is an exact representation of what the user sees in the final `NameMoveView` preview.
  * **Implement Fault-Tolerant Album Management**: Ensure the save logic correctly finds and uses the existing "BreakDex" album in Photos, preventing the creation of duplicate albums.

-----

### \#\# Non-Goals

  * Refactoring the UI of the `TrimmerView` or `NameMoveView`.
  * Introducing new video effects or processing capabilities beyond trimming and rotation.
  * Changing the underlying Core Data schema.
  * Modifying the existing logging infrastructure.

-----

### \#\# Acceptance Criteria (AC)

  * **AC-1: Correct Duration Display**:
      * **Given** a user has set a trim range from `X` to `Y` in the `TrimmerView`,
      * **When** they proceed to the `NameMoveView`,
      * **Then** the displayed duration must exactly equal `Y - X`, formatted correctly.
  * **AC-2: Successful Save Operation**:
      * **Given** a user has trimmed a video and entered a valid name in the `NameMoveView`,
      * **When** they tap the "Save Move" button,
      * **Then** the `flowState` transitions to `.saving` and subsequently to `.success`, without entering the `.error` state.
  * **AC-3: WYSIWYG Asset Persistence**:
      * **Given** a move has been successfully saved with a start time of `S`, end time of `E`, and rotation of `R`,
      * **When** the corresponding `Move` entity is inspected in Core Data,
      * **Then** its `trimStartTime` must equal `S`, `trimEndTime` must equal `E`, and `rotationQuarterTurns` must equal `R`.
  * **AC-4: Fault-Tolerant Album Management**:
      * **Given** the "BreakDex" album already exists in the user's Photos library,
      * **When** a new move is saved,
      * **Then** the video asset must be added to the existing album, and no new, duplicate "BreakDex" album should be created.

-----

### \#\# Key Metrics

  * **Save Success Rate**: The percentage of "Save Move" attempts that transition to the `.success` state should be \>99.9%.
  * **State Integrity**: The trim/rotation data must remain consistent across the `Trimming` → `Naming` → `Saving` state transitions, verifiable through logging.
  * **Performance**: The overhead of the state synchronization fix should not add more than 50ms to the transition time from the trimming view to the naming view.

-----

### \#\# Edge Cases & Constraints

  * **Zero-Length Trim**: The system should handle cases where `trimStartTime` and `trimEndTime` are identical, preventing the save and providing a user-friendly error. The log analysis confirms this check already exists and is the source of the current error.
  * **State Loss on App Backgrounding**: The preserved trimming state for the "Back" button should be robust enough to survive the app being sent to the background and resumed.
  * **Missing TrimmerViewModel**: If the `FlowStateManager` cannot access the `TrimmerViewModel` during the state transition, it must fail gracefully by throwing a `FlowStateError.missingViewModel` error instead of proceeding with incorrect data.
