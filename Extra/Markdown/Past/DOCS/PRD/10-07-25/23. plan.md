### Root Cause Analysis: The Resurfacing Lifecycle Bug

The latest logs provide the definitive "smoking gun." Even with the new `AddMoveStateOwner`, multiple instances of your state machine are being created.

1.  **Initial State Machine:** The app launches, and the first, correct `AddMoveStateOwner` is created with a persistent state object.

      * `🎬 MAIN_VIEW: 🎯 PERSISTENT_STATE_ID: ObjectIdentifier(0x0000000108d28000)`

2.  **The Trigger:** You select a video. The `didSelectVideo` function correctly transitions this instance's state to `.loadingVideo`.

3.  **The Bug:** This state change triggers a SwiftUI view update that incorrectly **re-creates `AddMoveStateOwner` from scratch**. The logs show this happening multiple times:

      * `🎬 PERSISTENT_STATE_OWNER: 🏗️ INITIALIZING - State owner with persistent state object`
      * This log appears again and again after the initial launch, proving the view is being re-instantiated.

4.  **The Consequence:**

      * **Successful Load on "Ghost" Instance:** The original state machine (`...d28000`) continues loading the video in the background. It successfully loads the asset and reaches 100%. The `CONSECUTIVE_LOAD` log confirms that at the moment of completion, `video_asset_available` is `true`.
      * **Empty "Live" Instance:** The UI, however, is now displaying a view hierarchy tied to a *new, empty* state machine instance.
      * **The New Error:** When the original instance finishes loading, it triggers the completion handler. This handler, however, now runs against the *new* state instance, which never loaded anything. When it checks `guard videoAsset != nil`, the check fails, and you get the `"Missing video dependencies for transition"` error.

This explains every failure you're seeing. The loading process *is* working, but it's happening on an old, orphaned state object that the UI is no longer connected to.

### The Definitive Solution

The bug is not in the files you've been editing. It's in the parent view that creates `AddMoveStateOwner` (likely your `MainView`). You must ensure this view is **created only once** and its identity is stable across UI updates.

#### 1\. Make the State Object Ownership Explicit in `MainView`

This is the most critical fix. Modify your root view (`MainView` or wherever your `TabView` lives) to create and own the `AddMoveUnifiedState` as a `@StateObject`. Then, pass this single instance down the view hierarchy.

```swift
// In your MainView.swift (or equivalent root view)

struct MainView: View {
    @State private var selectedTab: TabSelection = .add

    // 🎯 THE DEFINITIVE FIX: Create the state object here, ONCE.
    // This makes the MainView the single, authoritative owner of the state.
    @StateObject private var unifiedState: AddMoveUnifiedState

    init() {
        // Initialize the single instance of the state machine.
        let appContainer = AppContainer.shared
        _unifiedState = StateObject(wrappedValue: AddMoveUnifiedState(

    }

    var body: some View {
        TabView(selection: $selectedTab) {
            // ... your other tabs ...

            // Pass the SINGLE @StateObject instance down as an @ObservedObject.
            AddMoveStateOwner(
                selectedTab: $selectedTab,
                unifiedState: unifiedState, // Pass the instance here

                    // Handle navigation after save

                    // Handle app-wide loading overlay

    }
}
```

#### 2\. Update `AddMoveStateOwner` to Receive the State

Now, modify `AddMoveStateOwner` to no longer create its own `@StateObject`. It will receive the single, persistent instance from `MainView`.

```swift
// In: AddMoveStateOwner.swift

struct AddMoveStateOwner: View {
    @Binding var selectedTab: TabSelection

    // ✅ It now receives the state as an @ObservedObject.
    @ObservedObject var unifiedState: AddMoveUnifiedState

    private let onSaveSuccess: ((Move) -> Void)?
    private let onLoadingStateChanged: ((Bool, AddMoveUnifiedState?) -> Void)?

    private let logger = Logger(subsystem: "com.breakingflashcards", category: "AddMoveStateOwner")

    // The initializer now accepts the pre-existing state object.
    init(
        selectedTab: Binding<TabSelection>,
        unifiedState: AddMoveUnifiedState, // Receive it here
        onSaveSuccess: ((Move) -> Void)? = nil,
        onLoadingStateChanged: ((Bool, AddMoveUnifiedState?) -> Void)? = nil
    ) {
        self._selectedTab = selectedTab
        self.unifiedState = unifiedState // Assign it here
        self.onSaveSuccess = onSaveSuccess
        self.onLoadingStateChanged = onLoadingStateChanged

        let stateIdString = String(describing: ObjectIdentifier(unifiedState))
        logger.info("🎬 PERSISTENT_STATE_OWNER: 🏗️ INITIALIZING - State owner with persistent state object")

        logger.info("🎬 PERSISTENT_STATE_OWNER: 📊 SINGLE_INSTANCE_GUARANTEE - No dueling state machines can exist")
        logger.info("🎬 PERSISTENT_STATE_OWNER: ✅ DUELING_MACHINES_FIXED - Using single persistent state object")
    }

    // ... The rest of the AddMoveStateOwner body remains the same ...
    var body: some View {
        AddMoveContainer(selectedTab: $selectedTab, unifiedState: unifiedState, onSaveSuccess: onSaveSuccess)
        // ... your .onChange and other modifiers ...
    }
}
```

By making the `MainView` the sole owner of the `AddMoveUnifiedState`, you guarantee that only one instance ever exists. This completely resolves the "dueling state machines" bug and will allow your loading process to successfully transition to the trimmer view every time.
