### The Fundamental Flaw: Incorrect ViewModel Ownership and Lifecycle

The root of all the instability—the infinite loops, the crashes during setup—is an architectural anti-pattern: **The `TrimmerViewModel`'s lifecycle is incorrectly tied to the parent container (`AddMoveContainer`) instead of the view that actually uses it (`TrimmerView`).**

Here is the chain of events this flaw creates:

1.  **Premature Creation:** In `AddMoveContainer`, you create the `trimmerViewModel` as a `@StateObject` when the container itself is created. At this point, it's initialized with a placeholder asset because the real video hasn't been selected yet.
2.  **State Reuse:** When the user selects a video and the state transitions to `.trimming`, you pass this *single, long-lived `trimmerViewModel` instance* down into the new `TrimmerViewWrapper`.
3.  **Fragile Re-configuration:** Inside `TrimmerViewWrapper`'s `.onAppear`, you call `setupAsync()` on this *existing* view model. You are attempting to reconfigure a persistent object for a new context.
4.  **Failure Cascade:** As the logs show, `setupAsync()` fails when it tries to load the asset's duration. This failure triggers your `onError` callback.
5.  **State Conflict:** The `onError` callback correctly sets the `AddMoveViewModel`'s state to `.error`. This causes `AddMoveContainer` to rebuild, intending to show an error view.
6.  **The Crash:** However, the system is now in an unstable state. The original `TrimmerViewWrapper` is still being torn down while the container is trying to rebuild. This conflict, combined with the rapid state changes, is what leads to the debugger killing the app. The log line `WARNING: Same state triggered view rebuild!` is a key symptom of this instability.

The core mistake is treating the `TrimmerViewModel` like a global or parent-level service when it is, in fact, **ephemeral state that belongs exclusively to the trimming screen.**

The solution is to give `TrimmerView` (or its wrapper) exclusive ownership of its own ViewModel. The `TrimmerViewModel` should be created at the exact moment it's needed and destroyed when the trimming view is dismissed.

This ensures a clean, predictable lifecycle every single time the user enters the trimming screen.
