### The Fundamental Flaw: Violating View Immutability During Initialization

You have correctly identified the root cause: **a state mutation is occurring inside a view's initializer.**

In `TrimmerView.init()`, this line is the culprit:

```swift
trimmerViewModel.rotationQuarterTurns = rotationQuarterTurns
```

Even though you're often assigning `0` to a property that is already `0`, the mere act of assigning a value to a **`@Published`** property within a `View`'s `init` is a violation of SwiftUI's core principles.

**Here's the critical thinking behind why this fails:**

1.  **Views as a Function of State:** SwiftUI views are designed to be lightweight, declarative descriptions of your UI based on the *current* state. They are not objects that you configure imperatively.
2.  **The `init` Phase is for Construction, Not Mutation:** When `init()` is running, SwiftUI is in the middle of building its dependency graph and constructing the view hierarchy. It expects state to be stable during this phase.
3.  **The "Forbidden" Signal:** By assigning to a `@Published` property, you are sending a `objectWillChange` signal *while the view is still being created*. SwiftUI detects this as a "dirty" state change during a "clean" build phase. It concludes that the view's body is now invalid before it has even finished drawing it, forcing an immediate rebuild. This creates the infinite loop.

This isn't a bug in your validation logic; it's a fundamental architectural conflict with the SwiftUI framework.

-----

### The Solution: Defer State Synchronization with `.onAppear` or `.onChange`

To fix this, you must move the state synchronization out of the initializer. The new value should be passed to the ViewModel only *after* the view has been safely constructed and placed on screen.

#### Recommended Fix: Use `.onAppear` for Initial Setup

This is the most direct solution for setting an initial value. It ensures the state is updated only once after the view is ready.

**In `TrimmerView.swift`:**

```swift
struct TrimmerView: View {
    // ... your properties
    let rotationQuarterTurns: Int

    var body: some View {
        // ... your view body
        // ...
            .onAppear {
                // Safely update the ViewModel's state AFTER construction.
                trimmerViewModel.rotationQuarterTurns = rotationQuarterTurns
            }
    }
}
```

#### Alternative (More Robust) Fix: Use `.onChange` for Dynamic Updates

If `rotationQuarterTurns` could ever change while the `TrimmerView` is on screen, `.onChange` is a more robust and correct modifier to use. It handles both the initial value and any subsequent changes.

**In `TrimmerView.swift`:**

```swift
struct TrimmerView: View {
    // ... your properties
    let rotationQuarterTurns: Int

    var body: some View {
        // ... your view body
        // ...
            .onChange(of: rotationQuarterTurns) { newRotation in
                // This will fire when the view first appears AND
                // anytime the rotation value changes thereafter.
                trimmerViewModel.rotationQuarterTurns = newRotation
            }
    }
}
```

### Why This Works Without Breaking Functionality

This change fully respects SwiftUI's view lifecycle:

  * **Decoupling:** It decouples the view's **construction** from the ViewModel's **state mutation**.
  * **Predictability:** The state update now happens at a predictable and safe point in the view's lifecycle (`onAppear` or `onChange`), eliminating the race condition and the infinite loop.
