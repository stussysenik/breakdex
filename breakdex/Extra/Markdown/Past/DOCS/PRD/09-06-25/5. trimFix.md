Here is a Spec‑Kit–style, agent‑ready specification for the minimalist, tactile video trimmer—structured around Specify → Plan → Tasks with explicit contracts, acceptance criteria, and review checkpoints. [1][2]

## Specify

- Intent: Deliver a single‑purpose, content‑first video trimming control that lets a person set start and end times with confidence using a super‑minimal “single line + two handles + playhead” UI, keeping the preview as the focus at all times. [1][2]
- Why now: Current UI causes precision and touch‑target issues; this spec reduces cognitive load and increases accuracy by prioritizing tactile feedback and live preview over decorative timelines. [1][2]

### Users and scenarios

- Creator trims the first seconds of a clip and the last few frames to align a move or beat, verifying accuracy via the live preview while dragging. [1][2]
- Editor needs micro‑adjustments for perfect frame alignment using pinch‑to‑zoom on the line for temporary high‑precision control. [1][2]
- Casual user wants a fast cut without learning an editor; two handles and a playhead provide a “grab, drag, confirm” flow with haptic ticks. [1][2]

### Goals

- Minimal surface area: single horizontal line with start/end handles, a passive playhead, and unobtrusive time labels that appear only during interaction. [1][2]
- Tactility and confidence: generous hit targets, subtle haptics, and snapping to frame boundaries while preview updates live. [1][3]
- Clean output: produce precise start and end times to be consumed by the export layer using a time range. [1][4]

### Non‑goals

- No thumbnails, waveforms, filters, split edits, or multi‑clip timelines in v1 to preserve minimalism and speed. [1][2]

### Success metrics

- Task success: >95% users complete a trim on first attempt in <10s under normal device load. [1][2]
- Precision: 100% parity between chosen frame in preview and exported cut at given frame rate and time scale. [1][4]
- Satisfaction: qualitative feedback uses “intuitive,” “precise,” “smooth,” and “satisfying” in moderated tests. [1][2]

## Experience

- Layout: preview on top; below it, a thin timeline line spanning safe width; two draggable handles define start and end; a non‑draggable playhead reflects current playback position. [1][2]
- Gestures: drag handles horizontally; pinch on the line to enter temporary precision zoom; release animates scale back; no direct timeline scrubbing outside handles. [1][5]
- Feedback: light haptic on grab, micro haptics when crossing frame steps, and light impact on release; ephemeral mm:ss (or frames) labels float above the active handle while dragging. [1][5]
- Accessibility: visual handles may be slim, but interactive hit areas are ≥44×44 pt; color and contrast meet platform guidance. [3][2]

## Functional requirements

- FR1 Preview binding: while a handle moves, the preview seeks to that exact time with minimal latency to ensure “what you see is what you cut.” [1][2]
- FR2 Handles: left handle cannot pass right handle; right cannot pass left; both respect absolute media duration bounds. [1][2]
- FR3 Precision zoom: pinch increases seconds‑per‑point scale 2×–6× temporarily; easing returns to base scale on end of pinch. [1][5]
- FR4 Snapping: optional snapping to frame boundaries at native time scale and to playhead position if within 6–12 px, with tactile ticks. [1][5]
- FR5 Labels: transient time labels show hh:mm:ss.ms (or frames if enabled) above active handle during drag, fade out on end. [1][2]
- FR6 Output: exposes startTime and endTime as time values suitable for constructing a CMTimeRange for export. [1][4]
- FR7 State restoration: preserves last trim selection for a given asset URL or identifier within the session. [1][2]

## Non‑functional requirements

- Performance: interaction and preview seeking feel instant with target 60 fps UI and <50 ms median seek latency on current devices. [1][2]
- Reliability: no desync between displayed frame and reported time under repeated drags and pinches. [1][2]
- Accessibility: hit targets ≥44 pt, VoiceOver labels for “Start handle at t=…,” “End handle at t=…,” and “Playhead at t=…”. [3][2]
- Design principle: content‑first, deferential chrome that appears only during manipulation, per Apple guidance. [3][2]

## Contracts

- Inputs: media asset reference, duration, frame/time scale, current playhead time, configuration flags for snapping, precision zoom, and time display mode. [1][2]
- Outputs: startTime, endTime as high‑precision times; events: onBeginDrag(handle), onChange(handle, time), onEndDrag(handle, time), and onConfirm(). [1][2]
- Export integration: downstream exporter constructs a time range from outputs for actual trimming of file bytes rather than playback‑only edits. [4][2]

## Constraints and edge cases

- Very short clips: enforce minimal selectable span of one frame to avoid zero‑length ranges. [1][2]
- Long clips: precision zoom must remain smooth with lazy preview seeking and throttled UI updates to avoid stutter. [1][2]
- Variable frame rates: snapping and labels must respect the asset’s time base; do not assume constant frame rate. [4][2]
- Orientation and size classes: maintain predictable handle spacing and thumb hit areas in compact and regular layouts. [3][2]

## Acceptance criteria

- AC1 Dragging start or end updates the preview frame live, with observable match between handle time and displayed frame. [1][2]
- AC2 Haptic feedback fires on grab, boundary snaps, and release, and can be toggled in configuration. [1][5]
- AC3 Pinch precision provides at least 4× more resolution during drag and returns to baseline smoothly when released. [1][5]
- AC4 Time outputs map 1:1 to exported media when used to create a time range, verified by spot checks at boundaries. [4][2]
- AC5 Hit areas for both handles are ≥44×44 pt regardless of visual size and pass accessibility audits. [3][2]
- AC6 No visual overlap bugs when handles approach each other; handles stop with a minimum one‑frame separation. [1][2]

## Review & acceptance checklist

- Spec reflects the user journey and constraints; non‑goals are explicit and reviewed. [1][2]
- Plan aligns with platform patterns and performance targets. [1][2]
- Tasks are small, independently verifiable, and cover build, test, and demo scenarios. [1][2]
- Accessibility, performance, and export parity validated on target devices and media types. [3][4]

## Plan

- Platform: iOS 18 with SwiftUI for UI and AVFoundation for media timeline and export, matching platform norms and APIs. [1][4]
- Architecture: view (timeline) + view‑model (state, gestures, snapping, formatting) + media service (seek, time base ops), enabling clean bindings and testability. [1][2]
- Performance strategy: coalesce drag updates, prewarm seeking, throttle preview refresh under heavy load, and prioritize user‑perceived latency. [1][2]
- Accessibility and HIG alignment: enforce minimum hit targets, semantic labels, and deferential visuals per Apple guidance. [3][2]
- Export contract: downstream exporter consumes start/end to form a precise time range for final file writing. [4][2]

## Risks and mitigations

- Seek latency on large or high‑bitrate assets may reduce perceived precision; mitigate via adaptive throttling and preview prefetch heuristics. [1][2]
- Variable frame rates can cause boundary mistakes; mitigate by deriving snapping from the asset’s time scale not assumptions. [4][2]
- Over‑minimal UI might confuse; mitigate with transient labels and haptic/snap feedback as guidance without persistent chrome. [1][5]
