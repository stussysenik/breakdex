### **Spec: Resilient Video Loading Experience**

  * **Version**: 1.0
  * **Status**: Proposed
  * **Author**: Gemini (Agentic Principal Engineer)
  * **Date**: 2025-10-04
  * **Feature**: F1-Precision Video Loading Progress & Timer

-----

### **1. Overview: The "What" and "Why"**

#### **1.1. Goal**

To implement a **mechanically precise, resilient, and transparent** video loading experience. This system must provide users with a consistently accurate linear progress bar and a high-precision timer (`mm:ss:ms`) every time a video asset is loaded, processed, or changed. The primary directive is to eliminate state-related race conditions and ensure the UI is a verifiably faithful representation of the backend state.

#### **1.2. User Persona & Journey**

  * **Persona**: "The Athlete". This user values precision, performance, and reliability. They have zero tolerance for ambiguity or errors in their tools, especially during time-sensitive tasks like cataloging training footage. The tool must feel as dependable as a mechanical watch.
  * **User Journey**:
    1.  User taps "Select a Clip" or "Change Video".
    2.  The system immediately displays a loading indicator.
    3.  A linear progress bar appears and progresses smoothly from 0% to 100%.
    4.  Simultaneously, a timer formatted as `mm:ss:ms` starts from `00:00:000` and runs concurrently with the loading process.
    5.  The operation completes, and the user is transitioned to the video trimmer/editor view.

#### **1.3. Business Value**

  * **Enhanced User Trust**: A reliable loading process builds user confidence and reinforces the brand's commitment to quality and precision.
  * **Reduced Friction**: Eliminating loading stalls and UI bugs leads to a smoother, more professional user experience, increasing engagement and retention.
  * **Improved Diagnosability**: A transparent and predictable system is easier to debug and maintain, reducing engineering overhead.

#### **1.4. Non-Goals**

  * Re-architecting the underlying video processing or transcoding pipeline. This spec focuses solely on the state management and UI representation of the loading process.
  * Introducing new UI designs for the loading screen. The goal is to perfect the functionality of the existing components.
  * Changing the core logic of the `UnifiedProgressEngine`'s weighting and prediction algorithms.

### **2. Verifiable Functional Requirements**

#### **2.1. Acceptance Criteria**

| ID | User Story | Acceptance Criteria |
| :--- | :--- | :--- |
| **AC-1** | As a user, when I select a video, I want to see a progress bar that starts at 0% and a timer that starts at `00:00:000`. | - The progress bar must be visible immediately upon entering the `loadingVideo` state.<br>- The timer must be visible and display `00:00:000` at the start of the operation.<br>- Both elements must appear for initial selection and subsequent video changes. |
| **AC-2** | As a user, I want the progress bar to advance linearly and smoothly without stalling, especially at 99%. | - The progress bar's value must only ever increase.<br>- The `UnifiedProgressEngine` must map the terminal loading phase (`validatingTrimmer`) to exactly `1.0` progress to guarantee 100% completion. |
| **AC-3** | As a user, I want the timer to update in real-time with millisecond precision. | - The `TimerManagementService` must be configured for a `0.01s` (10ms) update interval.<br>- The UI must correctly format the elapsed `TimeInterval` into the `mm:ss:ms` string format. |
| **AC-4** | As a user, I want the loading indicator to be resilient to rapid interactions, such as quickly selecting a different video. | - Initiating a new video selection while another is loading must gracefully cancel the previous operation and start the new one from 0% / `00:00:000`.<br>- There must be no state leakage between consecutive loading operations. |

#### \*\*2.2. Edge Cases

| ID | Edge Case | Expected Behavior |
| :--- | :--- | :--- |
| **EC-1** | User selects an invalid or corrupted video file. | The system transitions to an error state, displays a user-friendly error message, and hides the progress bar and timer. |
| **EC-2** | App is backgrounded and then returned to the foreground during a loading operation. | The loading operation's state is preserved. The progress bar and timer must reflect the correct progress upon returning to the app. |
| **EC-3** | Network connection is lost during a cloud-based video download. | The progress bar should pause, and a "Network Connection Lost" status should be displayed. The timer should also pause. |
| **EC-4** | User has insufficient device storage to save the video. | The operation is halted, and a clear error message is shown to the user. |

### **3. Non-Functional Requirements (NFRs)**

  * **Performance**:
      * **State Transition Latency**: The transition from user tap to the `loadingVideo` state appearing on screen must be **\< 16ms** to ensure a 60fps user experience.
      * **Timer Refresh Rate**: The UI timer must update at a minimum frequency of **30Hz** to appear smooth.
  * **Reliability**:
      * **State Integrity**: The `AddMoveUnifiedState` object's lifecycle must be independent of SwiftUI view re-renders. Race conditions related to state re-initialization are considered P0 bugs.
      * **Success Rate**: The video loading flow must have a target success rate of **\>99.9%** for valid video files and stable network conditions.
  * **Security & Compliance**:
      * No sensitive user information should be included in diagnostic logs.
      * All file handling must adhere to iOS sandboxing and privacy best practices.
