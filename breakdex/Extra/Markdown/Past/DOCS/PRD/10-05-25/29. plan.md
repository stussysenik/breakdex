### **1. Overview (The "What" and "Why")**

#### **1.1. Goal**

To eliminate all video loading "hangs" by making the data acquisition pipeline fully resilient to network path changes (e.g., Wi-Fi to 5G switches) and silent failures from the underlying `Photos` framework.

#### **1.2. Problem Statement**

Despite previous fixes that ensured the UI correctly reflects the state of the `UnifiedProgressEngine`, the system still experiences stalls. The latest logs (`28. logs.md`) show the UI render loop is active (timer ticking), but the progress engine receives no updates. This indicates the root cause has moved from a UI state synchronization problem to a **data layer failure**. The video loading service, which is responsible for fetching the video asset, is not robust enough to handle real-world mobile network conditions or silent, non-returning API calls from the `Photos` framework when dealing with iCloud assets.

#### **1.3. User Persona & Journey**

  * **Persona:** "The Athlete" — Demands mechanical precision and has zero tolerance for ambiguity. A progress bar that moves while a timer ticks is an unacceptable discrepancy.
  * **User Journey:**
    1.  User selects a video from their library, often while on the move and switching between Wi-Fi and cellular networks.
    2.  The app begins the download/request process.
    3.  **Failure Scenario:** The underlying `URLSession` task or `PHImageManager` request hangs due to a network path change or a silent iCloud sync issue.
    4.  **Result:** The UI timer continues, but the progress bar freezes, creating a perception of a broken or hung application, violating the user's trust.

#### **1.4. Desired Outcomes**

  * **Deterministic Pausing:** Network interruptions will no longer cause a "hang" but will transition the system into a clear, user-facing "Waiting for Network..." state.
  * **Elimination of Silent Failures:** The system will implement timeouts to detect and gracefully handle non-responsive `Photos` framework requests.
  * **Absolute UI/System Cohesion:** The UI's state will always be a direct, real-time reflection of the data layer's state, including network-related pauses.

#### **1.5. Non-Goals**

  * This spec does not cover changing video codecs or compression settings.
  * It does not introduce a background upload/download capability (which requires a separate architecture using `BGTaskscheduler`).

### **2. Functional Specification**

#### **2.1. Core Requirements (User Stories)**

1.  **`STORY-201`**: As an athlete, when my network connection changes (e.g., Wi-Fi to 5G) during a video download, I want the app to automatically pause and resume the process so that I don't have to restart the selection.
2.  **`STORY-202`**: As an athlete, if a video I select from iCloud is stuck or fails to download for an unknown reason, I want the app to stop trying after a reasonable time and inform me of the failure so that I am not left waiting indefinitely.

#### **2.2. Acceptance Criteria (AC)**

**For `STORY-201` (Network Resilience):**

  * `AC-201.1`: A dedicated, network-aware loading service **MUST** be implemented that utilizes `NWPathMonitor` to observe network connectivity.
  * `AC-201.2`: If `NWPathMonitor` reports an unsatisfied path during the `.downloadingFromCloud` phase, the `UnifiedProgressEngine` **MUST** transition to a `waitingForNetwork` phase within 2 seconds.
  * `AC-201.3`: While in the `waitingForNetwork` phase, the UI **MUST** display the status "Waiting for Network..." and the progress bar's animation **MUST** be halted.
  * `AC-201.4`: When the network path becomes satisfied again, the engine **MUST** automatically transition back to `.downloadingFromCloud` and the underlying download task **MUST** be resumed.

**For `STORY-202` (Silent Failure Handling):**

  * `AC-202.1`: Any call to `PHImageManager.requestAVAsset` **MUST** be wrapped in a manual timeout mechanism (e.g., an `async` task with a `Task.sleep` race).
  * `AC-202.2`: The timeout for the `requestAVAsset` call **MUST** be configurable and set to a default of 45 seconds.
  * `AC-202.3`: If the timeout is exceeded, the loading process **MUST** be terminated, and the system **MUST** transition to a `Failure` state with a user-facing error message: "The request for this video timed out. It may be stuck syncing with iCloud. Please try again later."
  * `AC-202.4`: The underlying `URLSessionConfiguration` used for downloads **MUST** be configured with `waitsForConnectivity = true` and a `timeoutIntervalForResource` of 60 seconds.

#### **2.3. Edge Cases & Constraints**

  * **Low Power Mode:** The system should detect Low Power Mode and inform the user that iCloud downloads may be paused by the OS.
  * **Cost-Constrained Network:** On a cellular network, the `URLSessionConfiguration` must respect the `allowsConstrainedNetworkAccess = false` setting to prevent large downloads over metered connections without user intent.

### **3. Non-Functional Requirements (NFRs)**

  * **3.1. Performance:** The `NWPathMonitor` and associated logic **MUST** run on a background queue to avoid blocking the main thread.
  * **3.2. Reliability:** The video loading success rate, including automatic recovery from temporary network loss, **MUST** exceed 99.5%.
  * **3.3. Diagnostics & Logging:**
      * All network path status changes (`satisfied`, `unsatisfied`, `requiresConnection`) **MUST** be logged with `info` level.
      * The initiation and conclusion (success, failure, or timeout) of every `requestAVAsset` call **MUST** be logged with a unique correlation ID.
      * Timeout events **MUST** be logged as `error` level.
