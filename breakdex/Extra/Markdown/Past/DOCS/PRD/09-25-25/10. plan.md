## 1\. Categorical System Analysis

To understand the failure, we can model the "Add Move" flow as a composition of operations (morphisms) on data structures (objects).

### Objects (Core Modules)

  * **`AddMoveUnifiedState`**: The central state machine object that holds the current `flowState`, asset references (`videoAsset`, `photosIdentifier`), and trim parameters.
  * **`VideoLoader` & `VideoAssetPreparer`**: Components responsible for the initial morphism, transforming a `PhotosPickerItem` into a temporary video file and a playable `AVAsset`.
  * **`TrimmerViewModel`**: An object that manages the state for the trimming view, including start/end times and rotation.
  * **`MemoryHealthMonitor`**: A monitoring object that observes system state (CPU/memory) and triggers defensive actions.
  * **`AddMoveSaveCoordinator`**: The final processing object responsible for transforming the trimmed and named asset into a persisted `Move` entity in Core Data.

### Morphisms (Data Flow & Operations)

The intended data flow is a sequence of transformations:

1.  **Load**: `PhotosPickerItem` → `(URL_temp, AVAsset_original)`
      * This is performed by `VideoLoader`. A temporary file like `F39897EB...mov` is created.
2.  **Prepare**: `AVAsset_original` → `(AVPlayer, TrimmerViewModel_state)`
      * `VideoAssetPreparer` and `AddMoveUnifiedState` create the necessary player and view models.
3.  **Trim**: `TrimmerViewModel_state` → `(TrimRange, Rotation)`
      * User interaction within `FeatureRichTrimmerView` produces the desired trim and rotation values.
4.  **Compose**: `(AVAsset_original, TrimRange, Rotation)` → `AVComposition_trimmed`
      * The `UnifiedPlayerManager` and `VideoTransformBuilder` create a new, non-destructive composition for preview in the naming view.
5.  **Finalize & Save**: `(AVComposition_trimmed, MoveName)` → `(Move_entity, URL_persisted)`
      * This is the final morphism, handled by `AddMoveSaveCoordinator`. It takes the composed asset, exports it to a new permanent file, saves it to the Photos library, and creates a Core Data record.

### Composition (The End-to-End Workflow)

The entire "Add Move" flow is a composition of these morphisms: `Finalize & Save ∘ Compose ∘ Trim ∘ Prepare ∘ Load`. The system's stability depends on the output of each step being a valid input for the next. The failure occurs because an external event (memory cleanup) invalidates the output of the `Load` step before the `Finalize & Save` step can use it.

## 2\. Root Cause Analysis: The Composition Failure

The workflow failed during the **Finalize & Save** morphism. The composition broke because the underlying data required for the operation was removed mid-flight.

### The Failure Point

At **`14:45:38.860`**, the save process begins. However, at **`14:45:39.998`**, the `SAVE_COORDINATOR` reports the asset is not playable, causing the entire chain to fail.

```log

// ... a moment later, the check fails

📋 Metadata: ["duration": "0.0", "is_playable": "false"]
❌ 🎬 SAVE_COORDINATOR: Asset is not playable
```

### The Race Condition: Memory Cleanup vs. Final Save

The root cause is a critical event that occurs just **before** the save coordinator's final check:

1.  **Critical Health Event (`14:45:38.261`)**: The `VideoHealthMonitor` detects critically high CPU usage (118.7%) and receives a system memory warning.

    ```log
    🚨 [14:45:38.261] Health: Critical: CPU usage critically high: 118.7% | Memory: 155MB | CPU: 118.7%
    🧠 Memory warning received from system - taking critical actions
    ```

2.  **Aggressive Cache Cleanup**: In response, the memory manager initiates a cleanup routine. This routine correctly identifies and deletes temporary video files to relieve pressure.

    ```log
    🧠 Clearing video cache
    🧠 Deleted cached video file: F39897EB-0A8B-4F01-8F15-F90FFF3A47F3.mov
    ```

3.  **Invalidated Asset**: The deleted file, `F39897EB-....mov`, is the *exact same temporary file* created at the beginning of the flow (`14:45:15`).

    ```log
    // From earlier in the logs
    🎬 VIDEO_LOADER: Created temp URL: file:///.../tmp/F39897EB-0A8B-4F01-8F15-F90FFF3A47F3.mov
    ```

4.  **Save Fails**: The `AVAsset` object held by `AddMoveUnifiedState` now points to a file that no longer exists on disk. When the `AddMoveSaveCoordinator` attempts to use this asset to create a new export session, the system correctly reports it as unplayable, causing the save operation to fail.

The system is working as designed (freeing up memory when under pressure), but it lacks a mechanism to protect the *currently active asset* from this cleanup process.

## 3\. Architectural Solution & Implementation Plan

The solution is to introduce a simple **asset locking mechanism**. The component responsible for cache cleanup must be aware of any assets that are currently "in-flight" and must not delete them.

### Proposed Solution

1.  **Asset Lock in `AddMoveUnifiedState`**: Add a property to `AddMoveUnifiedState` to store the URL of the active temporary video file. This URL will act as a "lock."
2.  **Modify Cleanup Logic**: Update the `MemoryManager` (or the component responsible for cache clearing) to check against this locked URL before deleting any file.
3.  **Lifecycle Management**:
      * **Acquire Lock**: The lock is set when the temporary video file is first created in `VideoLoader`.
      * **Release Lock**: The lock is released only after the `AddMoveSaveCoordinator` successfully saves the final video to the Photos library or if the user cancels the entire flow.
