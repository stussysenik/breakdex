This specification details the implementation plan to fix the state management conflict in the video loading workflow, ensuring it is resilient to multiple, consecutive video selections.

-----

### **Spec ID:** `FEAT-20251005-CONSECUTIVE-LOAD-RESILIENCE`

  * **Title:** Resilient State Management for Consecutive Video Loading
  * **Author:** Gemini
  * **Status:** `Draft`
  * **Version:** `1.0`

## 1.0 Overview & Goals ("What" & "Why")

### 1.1 Objective 🎯

The current video selection process is not resilient to rapid, consecutive user actions, such as selecting a new video while another is already loading. This can lead to race conditions, stale UI states, and crashes. This spec outlines the work to re-architect the entry point of the loading flow, `didSelectVideo(item:)`, to make it an **atomic and cancellable operation**. The goal is to ensure that selecting a new video gracefully cancels any in-progress loading operation and initiates a clean, new loading sequence, providing a predictable and stable user experience.

### 1.2 User Persona & Journey 🏃

  * **Persona:** "The Athlete". This user is decisive and may change their mind quickly. If they select the wrong video, they expect to be able to correct their mistake immediately by selecting another one without the app becoming unstable.
  * **User Journey (Corrected):**
    1.  The user selects "Video A." The loading overlay appears for "Video A."
    2.  Before the loading completes, the user realizes they selected the wrong clip and immediately returns to the photo picker to select "Video B."
    3.  The moment "Video B" is selected, the system **atomically cancels** all in-progress work for "Video A."
    4.  The loading overlay immediately resets to `0%` and a `00:00.00` timer, now tracking the progress for "Video B."
    5.  The flow completes successfully for "Video B," with no interference or state corruption from the cancelled operation.

### 1.3 Key Features (User Stories) 📝

  * **As The Athlete, I want** to be able to change my selected video at any time during the loading process, **so that** I can quickly correct mistakes without having to wait or restart the app.
  * **As The Athlete, I want** the app to feel responsive and robust, even if I perform actions quickly, **so that** I can maintain my workflow's momentum.

### 1.4 Non-Goals 🚫

  * This fix will **not** introduce functionality to pause and resume a loading operation. The only outcome of a new selection is the cancellation of the previous one.
  * This will **not** alter the UI of the `LoadingOverlayView`; it only ensures the UI accurately reflects the state of the *most recent* loading task.

## 2.0 Verifiable Requirements & Acceptance Criteria

### 2.1 Functional Requirements

  * **Atomicity:** The `didSelectVideo(item:)` function must act as a single, atomic transaction. No partial state from a previous loading operation should persist when a new one begins.
  * **Cancellation:** Selecting a new video must explicitly cancel any ongoing `Task` associated with the previous loading operation to prevent redundant work and race conditions.
  * **State Integrity:** The `AddMoveUnifiedState` must be reset to a pristine "initial loading" state every time `didSelectVideo(item:)` is called. This includes resetting progress, timers, and any loaded data like `videoAsset`.
  * **UI Consistency:** The user interface must never show a stale state. If a video is selected, the loading overlay must immediately reflect the state for that new video.

### 2.2 Non-Functional Requirements (NFRs)

  * **Responsiveness:** The UI must remain responsive and never lock up, even when multiple videos are selected in quick succession. The time between selecting a new video and the UI resetting should be `< 100ms`.
  * **Resource Management:** Cancelled loading operations must release any held resources (e.g., memory for asset data) to prevent memory leaks.
  * **Reliability:** The success rate for loading the *last selected video* in a rapid sequence must be `> 99.9%`.

### 2.3 Edge Cases & Error Handling

| Scenario | Expected Behavior |
| :--- | :--- |
| User selects Video B fractions of a second after Video A. | The task for Video A is cancelled before it can make significant progress. The UI may flicker briefly but must stabilize on the loading state for Video B. |
| A loading operation is in its final stage (e.g., preparing the trimmer) when a new video is selected. | The entire finalization process must be cancelled, and the state must be cleanly reset for the new video. |
| The user dismisses the photo picker without making a new selection while a video is loading. | The current loading operation continues uninterrupted. |

### 2.4 Metrics & Success Criteria 📊

  * **Primary Metric:** `consecutive_load_failure_rate` (Target: `< 0.1%`). This measures failures of the second load attempt.
  * **Secondary Metric:** `ui_reset_latency_ms` (Target: P95 `< 100ms`). This measures the time from the second `didSelectVideo` call to the UI reflecting the reset state.

## 3.0 Implementation & Refinement Checklist

### 3.1 Phase 1: Analysis & Design

  * [ ] **1.1: Identify the State Management Entrypoint:** Confirm that `didSelectVideo(item: PhotosPickerItem?)` in `AddMoveUnifiedState.swift` is the sole entry point for initiating a video load from the UI.
    ```bash
    # Command to locate the video selection function.
    GrepTool(pattern="func didSelectVideo", path="AddMoveUnifiedState.swift")
    ```
  * [ ] **1.2: Design the Cancellation Mechanism:** The primary loading logic initiated by `didSelectVideo` should be encapsulated in a Swift `Task`. A class property, `private var videoLoadingTask: Task<Void, Error>?`, will hold a reference to this task.
  * [ ] **1.3: Plan the Atomic Reset:** Define a private function, `resetForNewVideoSelection()`, that is responsible for resetting all relevant state properties to their initial values. This function will be the first step in a new loading operation.

### 3.2 Phase 2: Implementation

  * [ ] **2.1: Implement Task Management:**
      * In `AddMoveUnifiedState.swift`, add the `private var videoLoadingTask: Task<Void, Error>?` property.
      * At the beginning of the `didSelectVideo` function, call `videoLoadingTask?.cancel()`. This will signal any in-progress task to terminate.
      * Wrap the entire asynchronous loading sequence within `didSelectVideo` in a `videoLoadingTask = Task { ... }` block.
  * [ ] **2.2: Create the Atomic Reset Function:** Implement the `private func resetForNewVideoSelection()` function in `AddMoveUnifiedState.swift`. This function must:
      * Reset progress in `UnifiedProgressEngine`.
      * Stop and reset the timer in `TimerManagementService`.
      * Set `videoAsset`, `photosIdentifier`, etc., to `nil`.
      * Reset `loadingStatusMessage` to its default value.
      * Ensure the `flowState` is ready for a new loading transition.
  * [ ] **2.3: Integrate the Reset into the Loading Flow:**
      * The first line of the new `Task` in `didSelectVideo` should be a call to `await resetForNewVideoSelection()`. This ensures the state is clean before any new work begins.
      * Use `try Task.checkCancellation()` at key points within the loading task (e.g., after file download, before trimmer setup) to ensure the task terminates promptly when cancelled.

### 3.3 Phase 3: Verification & Validation

  * [ ] **3.1: Unit & Integration Testing:**
      * Write a unit test that calls `didSelectVideo` twice in quick succession and verifies that the first `Task` is cancelled.
      * Write an integration test to confirm that all state properties are correctly reset after a second video is selected.
  * [ ] **3.2: Manual "Stress" Testing:**
      * Rapidly select 5-10 different videos consecutively from the photo picker.
      * **Expected Outcome:** The app remains stable, and only the *last* video selected proceeds to the trimming screen. The loading overlay should reset with each selection.
  * [ ] **3.3: Metric Verification:** Add logging to measure the `ui_reset_latency_ms` and confirm it meets the performance target.

### 3.4 Phase 4: Release & Monitoring

  * [ ] **4.1: Code Review:** The review should focus on the correct implementation of `Task` cancellation and the thoroughness of the `resetForNewVideoSelection` function.
  * [ ] **4.2: Phased Rollout:** Release the change behind a feature flag to monitor for any unexpected race conditions or state management issues in a production environment.
  * [ ] **4.3: Monitor Dashboards:** Pay close attention to the `consecutive_load_failure_rate` metric to ensure the fix is robust.
