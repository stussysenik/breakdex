You're right, the **state validation error is still occurring**. Although the new task cancellation and reset logic is working correctly, the logs reveal a subtle but critical race condition during the final transition to the trimming screen.

### Detailed Analysis

1.  **Cancellation and Reset Works**: The logs show that when a second video is selected, the initial loading task is successfully cancelled, and the state is reset.
    * `: 🎬 AddMoveUnifiedState: 🛑 Cancelling previous video loading task.`
    * `: 🎬 AddMoveUnifiedState: 🔄 Resetting state for new video selection.`

2.  **Successful Second Load**: The loading process for the *second* video proceeds correctly all the way to 100%, and the system begins preparing the trimmer.
    * `: 🎬 AddMoveUnifiedState: ✅ UNIFIED VIDEO LOADING COMPLETE - transitioning to trimming stage`

3.  **The Race Condition**: The failure happens in the `transitionToTrimmingWithDelay` function. This function has a `Task.sleep` to ensure the loading overlay is shown for a minimum duration. Here's the critical sequence:
    * The `Task` to transition to trimming is **launched asynchronously**.
    * The `didSelectVideo` function from the *first*, now-cancelled task, continues its execution and hits its `catch` block because it was cancelled.
    * **Crucially**, this `catch` block calls `resetAtomicTransitionLock()`.
    * The *second*, valid `Task` now wakes up from its `sleep`, but its transition lock has been prematurely unlocked by the first task's cancellation handler.
    * It then proceeds to call `setupTrimmerDirectlyWithValidation`, but because the lock was released and the state wasn't yet `.trimming`, the validation fails.
    * `: ❌ Trimmer setup failed [...]: Invalid state for trimmer setup: loadingVideo`

In short, the **cancellation handler of the old task is interfering with the state of the new, valid task**, creating a race condition that unlocks a critical resource too early and causes the same validation failure.

SPECKIT:
This specification details the plan to resolve the race condition in the video loading workflow by implementing a thread-safe, actor-based lock manager.

## 1.0 Overview & Goals ("What" & "Why")

### 1.1 Objective 🎯

The previous fix, while correctly handling task cancellation, introduced a race condition where the cancellation handler of an old task interferes with the execution of a new task by prematurely resetting a shared `atomicTransitionLock`. This spec defines the work to create a **thread-safe `TransitionLockManager` actor** to manage the lifecycle of the transition lock. This will guarantee that only the currently active loading task can acquire and release the lock, completely eliminating the race condition and ensuring that the final transition to the trimmer is atomic and safe.

### 1.2 User Persona & Journey 🏃

  * **Persona:** "The Athlete." This user's experience remains the primary focus. They expect flawless, predictable behavior, especially when correcting an error like selecting the wrong video.
  * **User Journey (Unchanged, but now reliable):** The user journey is identical to the previous spec. The user selects Video A, then quickly selects Video B. The app gracefully cancels the first operation and cleanly processes the second. The key difference is that this journey will now succeed `100%` of the time, without being subject to the previously identified race condition.

### 1.3 Key Features (User Stories) 📝

  * **As The Athlete, I want** my actions to have predictable outcomes, **so that** when I select a new video, I am confident that it will be the one that loads, without any weird errors.
  * **As a Developer, I want** to manage shared mutable state in a thread-safe manner, **so that** I can prevent race conditions in concurrent code.

### 1.4 Non-Goals 🚫

  * This fix will **not** change any user-facing UI. Its impact is purely on the backend state management logic to improve reliability.
  * This will **not** alter the existing `UnifiedProgressEngine` or `TimerManagementService`.

## 2.0 Verifiable Requirements & Acceptance Criteria

### 2.1 Functional Requirements

  * **Mutual Exclusion:** Only one loading task may hold the transition lock at any given time.
  * **Ownership Verification:** The lock may only be released by the same task identifier that acquired it. A cancelled, older task must not be able to release a lock held by a new, active task.
  * **State Integrity:** The `isTransitioningToTrimming` boolean in `AddMoveUnifiedState` must be perfectly synchronized with the lock state managed by the new actor.
  * **Clean Release:** The lock must be guaranteed to be released, even if the holding task fails or is cancelled, to prevent deadlocks.

### 2.2 Non-Functional Requirements (NFRs)

  * **Performance:** The overhead of using an actor for lock management should be negligible and not impact the user-perceived responsiveness (`< 1ms` for lock/release operations).
  * **Concurrency Safety:** The solution must be provably free of data races. This should be verifiable with the Swift compiler's actor-isolation checks and potentially the Thread Sanitizer tool.
  * **Maintainability:** The lock management logic should be centralized in the new actor, simplifying the `AddMoveUnifiedState` class and making the state transition logic easier to reason about.

### 2.3 Edge Cases & Error Handling

| Scenario | Expected Behavior |
| :--- | :--- |
| An old, cancelled task attempts to release the lock after a new task has acquired it. | The `TransitionLockManager` actor should ignore the request, as the identifier from the old task does not match the current lock owner. |
| A task crashes or fails while holding the lock. | The `catch` or `defer` block within the task must ensure the `releaseLock` function is called to prevent the system from getting stuck in a locked state. |

### 2.4 Metrics & Success Criteria 📊

  * **Primary Metric:** `transition_race_condition_failure_rate` (Target: `0%`). The specific `Invalid state for trimmer setup: loadingVideo` error should be completely eliminated from analytics.
  * **Guardrail Metric:** `deadlock_incidents` (Target: `0`). The new mechanism must not introduce deadlocks.
