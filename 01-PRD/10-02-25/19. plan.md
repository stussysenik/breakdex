### 🎯 Root Cause Analysis: The Broken Rotation Isomorphism

The problem is a subtle but critical flaw in the `TrimmerViewModel`'s initialization logic that breaks the perfect `Trimming <--> Naming` isomorphism for rotation.

1.  **Correct State Preservation**: As seen in the logs, when you leave the `TrimmerView`, the system correctly captures the **total rotation** (e.g., 90°) and preserves it in the `TrimmingStateSnapshot`.

      * `📸 [ASYNC] Final state - Intrinsic: 0, User: 1, Total: 1`

2.  **Incorrect State Restoration**: When you tap "Back," the `FlowStateManager` correctly reads the preserved state and creates a *new* `TrimmerViewModel`. It passes the preserved `totalRotationQuarterTurns` (value: 1) to the `initialTotalRotation` parameter of the `init` method.

3.  **The Flaw**: The `TrimmerViewModel`'s `init` method does not correctly use this `initialTotalRotation`. Instead, it initializes its internal rotation properties (`assetIntrinsicRotationTurns` and `userAppliedRotationTurns`) to `0`. It only uses `initialTotalRotation` later in `setupAsync()` to calculate what the user's rotation *should have been*.

      * `ℹ️ [TrimmerViewModel]: 🎬 TrimmerViewModel initialized with ... initial_user_rotation="0"`

4.  **The Double Application**: Later, in `setupAsync()`, the view model loads the *actual* intrinsic rotation from the asset (which is `0`). It then correctly calculates that the `userAppliedRotationTurns` must have been `1` to result in a total of `1`. **However, this calculation happens too late**. By the time the view appears, some parts of the UI have already read the initial incorrect `userAppliedRotationTurns` value of `0`, while others read the final correct value of `1`, causing a visual inconsistency or "double rotation."

The core issue is that `initialTotalRotation` is not immediately deconstructed into its constituent parts (`intrinsic` and `user-applied`) upon initialization, leading to a temporary but fatal state mismatch.
