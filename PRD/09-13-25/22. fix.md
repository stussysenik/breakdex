The issue should be fixed by making PhotosPicker’s selection a single source of truth owned by the ViewModel and bound directly to it, then driving an explicit import/reset state machine so selection, cancellation, and cleanup remain consistent over time. [1][2][3][4][5]

### Goals
- Eliminate desynchronization between local @State and the ViewModel by binding PhotosPicker directly to the ViewModel’s selection. [1][2][4]
- Implement a robust, cancellable import pipeline using PhotosPickerItem.loadTransferable for videos, writing to a file URL and avoiding large in-memory buffers. [6][5][7]
- Define clear lifecycle states (idle → importing → ready → resetting) with deterministic transitions on selection, cancel, and back/reset actions. [2][8]
- Add tests and lightweight instrumentation to ensure reliability, performance, and regressions are caught early. [8][9]

### Non‑goals
- Replacing PhotosPicker with a custom PhotoKit picker or broad PhotoKit refactor beyond selection and import. [5][10]
- Multi-asset selection and preselection logic changes beyond current single-video selection behavior. [4][10]

### Architecture
- Single source of truth: The AddMoveViewModel owns selectedItem: PhotosPickerItem? and related import state; all views read and mutate it through bindings, never duplicating local @State copies. [1][2][3]
- Ownership and propagation: Use @StateObject for the ViewModel at the container level, and @ObservedObject in subviews that consume it, following SwiftUI’s data flow and lifecycle guidance. [8][11][12]
- Picker binding: Bind PhotosPicker(selection:) directly to $viewModel.selectedItem so user actions and programmatic resets are always coherent. [1][4][5]

### Data model changes
- ViewModel properties:
  - @Published var selectedItem: PhotosPickerItem? = nil. [4][5]
  - @Published var state: SelectionState = .idle where SelectionState = .idle | .importing | .ready(URL) | .error(Error). [2][8] 
  - private var importTask: Task<Void, Never>? with cancellation in reset() and on deinit. [8][2]
- Invariants:
  - When state is .ready(url), selectedItem may be nil or non-nil; do not rely on it for downstream work, rely on the persisted URL. [2][3]
  - reset() cancels importTask, clears transient files, sets selectedItem = nil, and returns state to .idle. [1][8]

### View contracts
- Contract: VideoPickerWrapper takes the ViewModel and binds PhotosPicker directly to $viewModel.selectedItem; it does not store its own selectedItem. [1][4][2]
- Contract: Pre‑Trim and downstream views observe viewModel.state and act on .ready(url) to render, never peeking into PhotosPickerItem internals. [5][2]

Here is the corrected wrapper showing the binding to the ViewModel as the only selection state. [1][4]
```swift
struct VideoPickerWrapper: View {
    @ObservedObject var viewModel: AddMoveViewModel

    var body: some View {
        PhotosPicker(
            selection: $viewModel.selectedItem,
            matching: .videos,

        ) {
            Text("Select Video")

                .foregroundColor(.blue)
        }

    }

```

### State transitions
- idle → user selects item → importing: set state = .importing and launch importTask to loadTransferable for a file-backed representation. [6][2]
- importing → ready(url): on success, write to a durable temp/app-scoped URL and set state = .ready(url), optionally clear selectedItem to prevent re-imports. [6][7]
- importing → error(e): on failure, set state = .error(e) and allow retry or reset. [6][2]
- any → resetting: cancel importTask, clear temp files, set selectedItem = nil, then state = .idle. [1][8]

### Import pipeline (videos)
- Use PhotosPickerItem.loadTransferable to obtain a file-backed video representation instead of large in-memory Data, preferring types that map to URLs or a Transferable wrapper for movies. [6][7][13]
- For mixed content type introspection, use supportedContentTypes and UTType checks when needed; for video-only, matching: .videos suffices. [4][14]
- Example ViewModel glue: start import when selectedItem changes, handle cancellation, and transition state deterministically. [6][2]
```swift
final class AddMoveViewModel: ObservableObject {
    @Published var selectedItem: PhotosPickerItem? {
        didSet { handleSelectionChanged() }
    }
    @Published var state: SelectionState = .idle

    private var importTask: Task<Void, Never>?

    func reset() {
        importTask?.cancel()
        importTask = nil
        cleanupTempArtifacts()
        selectedItem = nil
        state = .idle
    }

    private func handleSelectionChanged() {
        guard let item = selectedItem else { return }
        state = .importing

        importTask?.cancel()
        importTask = Task { [weak self] in
            guard let self else { return }
            do {
                // Prefer file-backed representations; Movie is commonly used in examples.
                if let movie = try? await item.loadTransferable(type: Movie.self) {
                    let url = try persist(movie: movie) // write into app-scoped temp/cache
                    if Task.isCancelled { return }
                    await MainActor.run { self.state = .ready(url) }
                } else if let data = try? await item.loadTransferable(type: Data.self) {
                    let url = try persist( data, utType: .movie)
                    if Task.isCancelled { return }
                    await MainActor.run { self.state = .ready(url) }
                } else {
                    await MainActor.run { self.state = .error(ImportError.unsupportedType) }
                }
            } catch {
                if Task.isCancelled { return }
                await MainActor.run { self.state = .error(error) }
            }
        }
    }

    private func persist(movie: Movie) throws -> URL { /* write to file, return URL */ }
    private func persist( Data, utType: UTType) throws -> URL { /* write to file */ }
    private func cleanupTempArtifacts() { /* remove temp files if needed */ }
}

enum SelectionState {
    case idle
    case importing
    case ready(URL)
    case error(Error)
}
```
- The loadTransferable approach and Movie pattern are widely used in SwiftUI PhotosPicker samples and community examples for differentiating videos and images. [13][14]

### Ownership and lifecycle
- Instantiate the ViewModel with @StateObject in the top-level container to tie its lifecycle to the screen rather than to subview re-renders. [8][11]
- Pass the same instance down via @ObservedObject to avoid duplicated storage and maintain a consistent source of truth. [8][12]
```swift
struct AddMoveContainer: View {
```

### Error handling and resets
- Surface .error with actionable retry/reset affordances; ensure reset() cancels work and clears both selection and temp artifacts to prevent stale state. [1][8]
- Consider clearing selectedItem after a successful import to avoid accidental re-import loops on view refreshes. [2][3]

### Performance and memory
- Prefer file-backed transfers to avoid holding entire video Data in memory; persist to a temp/cache URL and stream/process downstream as needed. [6][7]
- Restrict content with matching: .videos to reduce picker noise and simplify import logic. [4][5]
- Offload heavy work to Tasks and respect cancellation to keep UI responsive, per SwiftUI data and side-effect guidance. [8][2]

### Edge cases
- User cancels the picker: selection remains nil and state stays .idle; no-op by design. [4][2]
- Limited Photos access: PhotosPicker is designed to work under limited access and can prompt to extend authorization as needed. [10][15]
- Import interruption: if the task is canceled due to navigation/back, reset returns to .idle and cleans up partial files. [1][8]

### Tests
- Unit tests: 
  - Selection change triggers .importing, then .ready(URL) on success, or .error on failure. [6][2]
  - reset() cancels importTask, clears files, and returns to .idle. [1][8]
- UI tests:
  - Open picker, select a short video, verify transition to .ready and downstream rendering. [4][5]
  - Cancel picker and verify state remains .idle without side effects. [4][2]
  - Trigger back/reset and verify cleanup and responsiveness on subsequent selections. [1][8]

### Migration steps
- Remove any local @State selectedItem from VideoPickerWrapper and subviews. [1][2]
- Add @Published selectedItem and state to the ViewModel; implement import/reset logic around loadTransferable with cancellation. [6][3]
- Bind PhotosPicker(selection:) to $viewModel.selectedItem and rely on ViewModel reactions rather than view-local onChange handlers. [1][4]
- Verify end-to-end flows under selection, cancel, and reset to confirm no regressions. [8][4]

### Risks and mitigations
- Risk: Re-entrancy if selection toggles rapidly; Mitigation: serialize imports and cancel the previous importTask before starting a new one. [8][2]
- Risk: Memory spikes if importing into Data; Mitigation: use file-backed Transferable or write incrementally to disk. [6][7]
- Risk: Misuse of ownership leading to ViewModel loss; Mitigation: ensure @StateObject at container scope per lifecycle guidance. [8][11]

### Acceptance criteria
- Selecting a video transitions to .importing then .ready(URL) with a playable file without UI freezes. [6][5]
- Tapping back/reset immediately cancels any import, clears selection, and the picker remains responsive for the next selection. [1][8]
- No duplicated local state; PhotosPicker’s selection binding points to the ViewModel only. [1][4]

### Checklist
- Binding: PhotosPicker(selection:) → $viewModel.selectedItem. [1][4]
- ViewModel: @Published selectedItem, @Published state, importTask, reset(), cleanup. [2][6]
- Pipeline: loadTransferable for a file-backed result, write to URL, state transitions on success/error. [6][7]
- Lifecycle: @StateObject at container, @ObservedObject downstream. [8][11]
- Tests: unit and UI tests for selection, cancel, reset. [8][4]

This design removes the dual-state bug, aligns with SwiftUI’s single source-of-truth model, and uses the supported PhotosPicker and Transferable flows for resilient, memory-safe video imports. [1][2][5][6]
