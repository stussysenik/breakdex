## iOS 18 Alignment and Best Practices

To ensure the application is robust and compliant with the latest standards, especially for iOS 18, several key practices should be adopted:
* **Unidirectional Data Flow**: State mutations should be kept out of SwiftUI `View.body` computations. Adopting a unidirectional flow where views react to state changes from view models or state objects avoids "publishing changes during view updates" warnings, a pattern emphasized in recent WWDC sessions.
* **Efficient Exporting**: For performance and reliability, the video processing pipeline should export the final composition once to a temporary file. This file can then be added to the Photos library using a `PHAssetChangeRequest`. This approach minimizes latency and memory usage. When only trimming is needed, use `passthrough` presets to avoid unnecessary re-encoding.
* **Reliable Persistence**: To ensure the `MoveDetailView` always displays the correct video, the application must persist and then navigate using the `localIdentifier` returned after successfully saving the asset to the Photos library. Be aware of potential indexing latency in the Photos app and implement a brief retry mechanism if an asset isn't found immediately after saving.

## Core Implementation Steps

### Stabilize the Trimmer View
The most critical first step is to resolve the SwiftUI re-entrancy bug.
1.  **Refactor `TimecodeCalculationService`**: Convert the class from an `ObservableObject` into a stateless, final class or struct. This immediately breaks the reactive loop causing the runtime warning.
2.  **Update State Management**: The `TrimmerViewModel` should be the single source of truth for all trimming-related state. It will call the stateless timecode calculator and store the results in its own `@Published` properties, which the view can then safely consume.

### Ensure Timecode Precision
To deliver a true WYSIWYG experience, timing data must be handled precisely.
1.  **Use `CMTime` in State**: In `AddMoveUnifiedState`, change the `trimStartTime` and `trimEndTime` properties from `Double` to `CMTime`.
2.  **Delay Type Conversion**: All trim and timing logic throughout the application—from the `TrimmerViewModel` to the `AddMoveSaveCoordinator`—should operate on `CMTime` objects. The conversion to `Double` should only occur at the very last step when writing the values to the Core Data `Move` entity. AVFoundation's export APIs are designed to work with `CMTime` and `CMTimeRange`, which preserves frame accuracy.

### Overhaul the Save & Display Pipeline
The data lifecycle must be complete and correct to ensure what is saved is what is displayed.
1.  **Single Export**: Refactor the save logic to perform only one export. The `AddMoveSaveCoordinator` should process the video (applying trims and rotation) and export it to a single temporary file URL.
2.  **Use Final Identifier**: This temporary file URL is then used with `PHAssetChangeRequest.creationRequestForAssetFromVideo(atFileURL:)` to save the video to the "BreakDex" album. This operation returns a new, permanent `localIdentifier` for the asset in the Photos library.
3.  **Persist Correct Data**: This final `localIdentifier` must be what is saved into the `photosIdentifier` attribute of the `Move` entity in Core Data.
4.  **Close the Loop**: The parent view responsible for navigation must receive the final, persisted `Move` object back from the save flow. Use this object, containing the correct `photosIdentifier`, to programmatically navigate to the `MoveDetailView`. This ensures the detail view is loaded with correct, permanent data, not stale in-memory state.
