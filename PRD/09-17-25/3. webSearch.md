Short answer: In iOS 18, combine SwiftUI’s PhotosPicker with the Observation framework by keeping selection state local (State/Bindable) and lifting durable media state into an @Observable model, then load assets asynchronously with loadTransferable, filtering via matching and tuning selectionBehavior/maxSelectionCount while avoiding explicit photo permissions because the picker runs out-of-process and only exposes chosen items [1][2][3]. Prefer Transferable-based loading with proper error handling, progress/cancellation, and memory-aware representations (e.g., URL/Data over in-memory images for large assets), and add custom capture/edit flows when needed since PhotosPicker itself doesn’t provide camera or editing UIs [4][5][6].

### Core setup
- Use PhotosPicker (or the photosPicker view modifier) to present the system picker with selection binding, optional maxSelectionCount, selectionBehavior, matching filters, and preferredItemEncoding to control results at the source [1][3].  
- The system Photos picker runs privately out-of-process and only returns items explicitly chosen by the person, so authorization prompts for broad library access are not required for picking [3][7].  

### Data flow with @Observable
- The Observation framework’s @Observable lets SwiftUI track per-property dependencies and re-render only views that read changed properties, improving performance versus global object updates [2][8].  
- Provide the model via .environment and use @Environment(Model.self) with @Bindable in children to create bindings, and mark caches/derived heavy properties with @ObservationIgnored to avoid unnecessary invalidations [2][8].  

### Loading media correctly
- Convert PhotosPickerItem to concrete data using loadTransferable, which supports async/await and a completion-handler overload (useful for progress) [4][9].  
- Filter and branch on supportedContentTypes or matching to decide whether to load Image, Data, or a file representation (e.g., movie), and handle errors and cancellations explicitly in Tasks [5][9].  

### Privacy and permissions
- The Photos picker does not require photo library authorization because access is limited to the items selected within the picker UI, which is the preferred privacy-preserving integration path [3][7].  
- Request broader PHPhotoLibrary access only when needed for use cases beyond selection (e.g., enumerating assets or background processing), as the picker alone is sufficient for straightforward import flows [7][10].  

### Multi-selection and filtering
- Use maxSelectionCount and selectionBehavior to tune batch selection UX, and matching to constrain to images, videos, or specific categories like panoramas or screenshots [3][5].  
- Debounce or sequence loads in a Task when the bound selection array changes, and aggregate results into model state rather than binding heavy data directly into view State [5][2].  

### Performance and memory
- Prefer loading to file-backed or Data representations for large images and especially videos instead of immediately materializing SwiftUI Image/UI images into memory [5][4].  
- Use the completion-handler overload of loadTransferable for progress tracking and cancellation, and perform decoding/transcoding work off the main actor to keep the UI responsive [4][2].  

### Editing and capture gaps
- PhotosPicker doesn’t ship with cropping or editing tools, so integrate a custom editor or bridge to UIKit (e.g., UIImagePickerController with editing) or a dedicated pipeline for editing needs [6][1].  
- PhotosPicker is selection-only and not a camera; implement capture separately (AVCapture-based or UIKit) if in-app camera is required [1][6].  

### Common pitfalls
- If loadTransferable fails, verify the requested Transferable type matches the picked item’s supportedContentTypes and handle importNotSupported with a fallback (e.g., Data or a different type) [9][11].  
- Avoid over-broadcasting changes by keeping ephemeral selection state in view-local State while persisting only final results or metadata in the @Observable model [2][8].  

### Minimal patterns (snippets)
- Single-photo image load with @State for selection and model sink for results: [1][5]
```swift
import SwiftUI
import PhotosUI
import Observation

@Observable
final class MediaModel {
    var image: Image?
    var lastError: Error?
}

struct PickerView: View {
    @State private var selection: PhotosPickerItem?
    @Environment(MediaModel.self) private var model

    var body: some View {
        VStack(spacing: 12) {
            model.image?
                .resizable()
                .scaledToFit()

            PhotosPicker(selection: $selection, matching: .images) {
                Label("Select image", systemImage: "photo")
            }
        }
        .task(id: selection) {
            guard let item = selection else { return }
            await load(item)
        }
    }

    @MainActor
    private func load(_ item: PhotosPickerItem) async {
        do {
            model.image = try await item.loadTransferable(type: Image.self)
        } catch {
            model.lastError = error
        }
    }
}
```

struct MultiPickerView: View {
    @State private var selections: [PhotosPickerItem] = []
    @Environment(MediaModel.self) private var model

    var body: some View {
        PhotosPicker(
            selection: $selections,
            maxSelectionCount: 10,
            selectionBehavior: .ordered,
            matching: .any(of: [.images, .videos])
        ) {
            Label("Add media", systemImage: "plus")
        }
        .task(id: selections) {
            for item in selections {
                await load(item)
            }
        }
    }

    @MainActor
    private func load(_ item: PhotosPickerItem) async {
        do {
            if item.supportedContentTypes.contains(.image) {
                model.image = try await item.loadTransferable(type: Image.self)
