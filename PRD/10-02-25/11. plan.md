## **Spec (v2): E2E Add Move Flow - Rollback Integrity Fix**

### **1. High-Level Goals & Personas**

#### **1.1. Goal (The "What")**

This specification details the final refinement needed to fix a regression bug introduced during the resolution of the double-rotation issue. The current implementation correctly reconstructs the `TrimmerViewModel` during the "back" navigation from the Naming screen but fails state validation immediately after, causing a new error flow. The goal is to eliminate this validation failure by ensuring the `TrimmerViewModel` is initialized **atomically and synchronously** with its correct time and rotation state before any validation occurs.

#### **1.2. Rationale (The "Why")**

The previous fix correctly addressed the *what* (reconstruct the VM) but not the *how*. The reconstruction is an `async` process, and the system attempts to validate its state mid-flight, while key properties like `startTime` and `endTime` are still `.zero`. This results in a failed user journey. For "The Athlete" persona, a tool that fails on a standard navigation action is unreliable. This fix will ensure the rollback operation is robust, instantaneous, and correct, completing the WYSIWYG experience.

#### **1.3. User Journey (Failure Scenario from Logs)**

1.  User applies a 90° rotation and proceeds to `NameMoveView`. State is correctly preserved (`totalRotation=1`).
2.  User taps "Back".
3.  The `rollbackToTrimming` flow begins. It correctly restores the `trimStartTime`, `trimEndTime`, and `rotationQuarterTurns` into `AddMoveUnifiedState`.
4.  A **new `TrimmerViewModel` is created**, but its `startTime` and `endTime` are initialized to `0.0` pending its internal `async setup`.
5.  **The system immediately validates the state**, sees the new VM's `startTime` and `endTime` of `0.0`, and incorrectly flags it as an error: `State transition validation failed: Start time (0.0) is after end time (0.0)`.
6.  The user is presented with an error screen, breaking the flow.

### **3. Clarity, Refinement, & Implementation Checklist**

The root cause is a race condition. The `TrimmerViewModel`'s initialization is not atomic; its state is inconsistent until an `async` operation completes. We will fix this by making its initial state fully synchronous.

#### **Phase 1: Diagnosis Confirmation from Logs**

  * [x] **1.1. Trace the Failure:** The logs clearly show the sequence of events.
      * `[15:11:57] 🔄 FLOW_STATE: ✅ Trimming state restored from preserved data`
          * At this point, `AddMoveUnifiedState` holds the correct trim times.
      * `[15:11:57] 🔄 FLOW_STATE: 🔧 ROLLBACK MORPHISM - Reconstructing TrimmerViewModel...`
          * A new VM is created. Its `startTime` and `endTime` are `.zero` by default.
      * `[15:11:57] 🔄 FLOW_STATE: ❌ State validation failed: Start time (0.0) is after end time (0.0)...`
