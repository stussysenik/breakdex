### 1\. Overview

This document outlines the requirements to refactor and stabilize the "Add Move" feature in the BreakingFlashcards application. The current implementation suffers from intermittent crashes, unreliable UI behavior, and a suboptimal user experience during video processing. This specification follows Spec-Driven Development principles to ensure the final implementation is correct, reliable, and verifiable.

#### 1.1. Problem Statement

The end-to-end "Add Move" workflow is not fully reliable. Users experience failures at two critical stages: previewing the trimmed/rotated video and saving the final move. [cite\_start]These failures manifest as missing UI elements, abrupt crashes (`SIGABRT`), and incorrect video processing (aspect ratio distortion)[cite: 1, 2, 12, 86]. [cite\_start]Additionally, user feedback indicates that loading indicators are visually distracting and provide poor feedback for long operations[cite: 276, 285].

#### 1.2. Goals

  * **Reliability:** Eliminate all crashes and race conditions within the "Add Move" flow. The system must be fault-tolerant and gracefully handle errors.
  * **Correctness:** Ensure a **WYSIWYG** experience. The final video saved in Core Data and the "BreakDex" Photos album must precisely match the trim, rotation, and aspect ratio configured by the user in the `NameMoveView`.
  * **User Experience:** Improve the perceived performance and feedback mechanisms. Loading indicators should be unobtrusive and informative, managing user expectations during long operations.
  * [cite\_start]**Data Integrity:** Guarantee that move data is persisted correctly and that the "BreakDex" photo album is managed idempotently, without creating duplicates[cite: 216].

#### 1.3. Non-Goals

  * Adding new features to the video trimmer (e.g., filters, speed controls).
  * [cite\_start]Refactoring the Core Data schema beyond what is necessary for stability (i.e., changing the storage of video data from a file path)[cite: 316].
  * Overhauling the entire UI design of the "Add Move" flow.

### 2\. User Profile & Journey

      * [cite\_start]**Pain Point:** The application crashes intermittently during this stage[cite: 12].

### 3\. Functional Requirements & Acceptance Criteria

#### 3.1. FR1: Crash-Free Save Operation

  * **What:** The application must never crash due to a `SIGABRT` signal or any other exception during the save operation.
  * **Why:** This is the most critical stability issue, making the core feature unusable.
  * **Acceptance Criteria:**
      * [ ] All Core Data write operations originating from background tasks (like video export) must be executed on a dedicated background `NSManagedObjectContext`.
      * [ ] The app must successfully save 100 consecutive moves of varying lengths (10s, 30s, 2min) without crashing.
      * [cite\_start][ ] Enabling the Core Data Concurrency Debugger (`-com.apple.CoreData.ConcurrencyDebug 1`) must not trigger a crash during the save process[cite: 37, 305].

#### 3.2. FR2: Reliable Video Preview

  * **What:** The video preview in `NameMoveViewUnified` must always display the correctly trimmed and rotated video.
  * **Why:** Provides essential WYSIWYG feedback to the user before saving.
  * **Acceptance Criteria:**
      * [ ] The `AVPlayerItem` for the preview must have a status of `.readyToPlay` *before* the UI transitions from the trimming view to the naming view.
      * [ ] The `NameMoveViewUnified` must display a deterministic loading state if the player is not yet ready, preventing a blank or failed state.
      * [ ] The preview must load successfully within 1 second after the trimming view disappears.

#### 3.3. FR3: Correct Video Transformation (Rotation)

  * **What:** Applying a 90° or 270° rotation must preserve the video's original aspect ratio.
  * **Why:** To prevent cropping and ensure the saved video is not distorted.
  * **Acceptance Criteria:**
      * [ ] When a 90°/270° rotation is applied, the `AVMutableVideoComposition`'s `renderSize` property must be set to the inverse of the original video track's `naturalSize` (width becomes height and vice-versa).
      * [ ] A 1920x1080 video, when rotated, must be saved as a 1080x1920 video, with no content loss.
      * [ ] A 3840x2160 (4K) video, when rotated, must be saved as a 2160x3840 video.

#### 3.4. FR4: Informative and Unobtrusive Loading Indicators

  * **What:** Loading indicators must be minimal and provide meaningful feedback.
  * **Why:** To improve user experience and manage expectations during processing.
  * **Acceptance Criteria:**
      * [ ] The loading indicator shown after the trimming view (`.finalizing` state) must be a minimal, system-standard `ProgressView` (circular style).
      * [cite\_start][ ] This "finalizing" indicator must only appear if the operation takes longer than 500ms to prevent UI flicker[cite: 283].
      * [ ] The initial video loading progress bar must be driven by actual progress from `PHImageManager` or `AVAssetExportSession` and update continuously, not in discrete jumps.
      * [cite\_start][ ] The loading view for long operations must display a secondary "Elapsed Time" counter (e.g., "0:15") that updates every second[cite: 294].

#### 3.5. FR5: Data Integrity and Persistence

  * **What:** The saved `Move` entity and corresponding video file in the Photos app must be a perfect representation of the user's final configuration.
  * **Why:** This is the core promise of the feature.
  * **Acceptance Criteria:**
      * [ ] The `trimStartTime`, `trimEndTime`, and `rotationQuarterTurns` properties on the saved `Move` Core Data object must exactly match the values from `AddMoveUnifiedState` at the moment of saving.
      * [cite\_start][ ] The app must check for a pre-existing "BreakDex" album by name before attempting to create a new one, ensuring idempotent behavior[cite: 217].
      * [ ] After a successful save, the user must be navigated to a `MoveDetailView` where the video plays with the correct trim and rotation.

### 4\. Non-Functional Requirements (NFRs)

  * **4.1. Performance:**
      * The entire save operation (from tapping "Save" to seeing the success screen) should complete in under 5 seconds for a 30-second 1080p video on a target device.
  * **4.2. Reliability & Fault Tolerance:**
      * The app must gracefully handle errors (e.g., failed video export, no disk space) by transitioning to the `.error` state with a user-friendly message. Temporary files must be cleaned up on failure.
  * **4.3. Memory Management:**
      * The "Add Move" workflow must not cause a memory usage increase of more than 50MB for a 1-minute 1080p video.
      * The app must correctly release all video-related assets from memory when the flow is cancelled or completed by calling the `reset()` function.

### 5\. Edge Cases & Constraints

  * **Input Constraints:**
      * Video with no audio track.
      * Video with a duration less than the minimum trim requirement (3.0s).
      * Vertically-shot videos (e.g., 1080x1920).
  * **Environmental Constraints:**
      * Low device storage.
      * Slow network connection (for iCloud Photos videos).
      * Photos library permissions denied or revoked mid-session.
      * Rapidly tapping the "Save" or "Back" buttons.
