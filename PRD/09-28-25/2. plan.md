            .receive(on: DispatchQueue.main) // Ensure UI updates are on the main thread
            .sink { [weak self] progressUpdate in
                guard let self = self else { return }

                if case .loading = self.flowState {
                    self.logger.info("🎬 UNIFIED_STATE: 📊 Received progress update: \(progressUpdate.phase)")

### **1. Overview & Goals (The "What" and "Why")**

#### **1.1. Executive Summary**

This specification outlines the redesign of the video loading experience within the "Add Move" flow. The current opaque spinner will be replaced with a transparent, state-driven loading indicator that provides real-time feedback on the loading process (e.g., file size, current step). This effort is part of a larger milestone to harden the entire end-to-end "Add Move" pipeline, ensuring videos are saved with frame-accurate precision and robust, fault-tolerant data persistence.

#### **1.2. Business Goal**

The primary goal is to **increase user trust and reduce perceived latency**. By making the loading process transparent, we eliminate user uncertainty about "why it's taking so long," which improves engagement and reduces the likelihood of users abandoning the flow. A robust save pipeline ensures data integrity, which is critical for user retention.

#### **1.3. User Persona**

* **"The Athlete"**: This user values precision, reliability, and a frictionless experience. They treat the app as a professional tool, akin to a mechanical watch. They have zero tolerance for data loss, incorrect transformations (e.g., wrong trim), or unexplained delays. The system must "just work" flawlessly, allowing them to focus on cataloging their training footage.

#### **1.4. User Journey**

1.  **Initiation:** The Athlete taps the "Add" tab to start a new move.
2.  **Selection:** They select a video from their Photos library using the `PhotosPicker`.
3.  **Loading (Feature Focus):** Instead of a generic spinner, they are immediately presented with a loading bar overlay. The overlay cycles through clear, descriptive messages like "Preparing...", "Loading Video (57 MB)", "Validating Format...", and "Preparing Player...".
4.  **Completion:** The loading overlay transitions away, and the video is ready for trimming, having provided the user with full transparency into the loading process.
5.  **Saving:** After trimming, rotating, and naming the move, the user taps "Save." The system flawlessly saves the video to the "BreakDex" Photos album and creates a corresponding `Move` entity in Core Data, preserving the exact transformations (WYSIWYG).
6.  **Verification:** The Athlete can immediately navigate to the new move's detail view and see the correctly trimmed and rotated video playing.

#### **1.5. Goals**

* Implement a new, state-driven loading UI that displays the video's file size and the current loading phase.
* Ensure the `ModernVideoLoadingService` emits detailed progress events to power the new UI.
* Guarantee the end-to-end save process is atomic and reliable, correctly preserving user-defined trims and rotations.
* Ensure the `PhotosPersistenceService` intelligently uses the existing "BreakDex" album, preventing duplicate or empty albums.

#### **1.6. Non-Goals**

* This spec does not cover building a byte-by-byte, real-time progress indicator for the file transfer itself. The phase-based progress is sufficient for V1.
* This spec does not include a redesign of the trimming or naming views, only the loading and saving logic.
* This spec does not change the underlying video processing engine (`VideoTransformBuilder`), only its orchestration.

#### **3.1. Acceptance Criteria**

    * **WHEN** they select a video from the `PhotosPicker`

    * **WHEN** the user saves the move
    * **THEN** a `Move` entity must be created in Core Data with the exact `trimStartTime`, `trimEndTime`, and `rotationQuarterTurns`.

* **Unsupported File:** If the user somehow selects a non-video file or a corrupt video, the loading UI should display a clear error state and allow the user to dismiss it.
* **Cancellation:** The user must be able to cancel the loading process.

#### **3.3. Performance & Quality Metrics**

* **P95 Loading Time:** For local videos under 100MB, the time from selection to preview-ready must be < 4 seconds.
* **Crash-Free Rate:** The "Add Move" flow must maintain a > 99.95% crash-free session rate.
* **Data Integrity:** 100% of saved moves must have matching trim/rotation values between the Core Data entity and the video asset in the Photos library.
