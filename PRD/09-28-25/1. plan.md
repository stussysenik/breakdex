## 🎯 Refined Implementation Plan

The core issue is a lack of transparency in the loading process. The user sees a spinner but has no context on *what* is happening or *why* it's taking time. The solution is to transform the opaque loading morphism into a transparent one that emits detailed state and progress information.

Our plan involves three primary phases:

1.  **Enhance the Data Model & Service Layer:** We'll enrich the `VideoLoadingProgress` object to carry detailed contextual information (phase, file size, status messages) and modify the `ModernVideoLoadingService` to emit these rich events.
2.  **Develop a New UI Component:** We'll build a new, data-driven `LoadingOverlayView` in SwiftUI that visualizes this rich progress information, complying with Apple's design principles.
3.  **Integrate into the State Machine:** We'll update the `AddMoveUnifiedState` and `AddMoveContainer` to manage and display the new loading view, replacing the old spinner.

## 🔬 Step 1: Categorical Analysis of the System

Using category theory helps us model the system formally, revealing the root causes of the current limitations and guiding us to a robust solution.

### **Objects and Morphisms (System Components & Data Flow)**

  * **Objects:** `PhotosPickerItem`, `URL`, `PHAsset`, `AVAsset`, `VideoLoadingProgress`, `Move` (CoreData Entity).
  * **Morphisms (Functions/Processes):**
      * `loadTransferable`: `PhotosPickerItem` → `URL` (The efficient, streaming approach).
      * `requestAVAsset`: `PHAsset` → `AVAsset` (The Photos library approach).
      * `reportProgress`: `InternalState` → `VideoLoadingProgress` (The information-emitting process).
      * `saveMove`: `(AVAsset, Name, ...)` → `Move` (The final persistence step).

### **Step 1.1: Chain-of-Thought Reasoning (Root Cause Analysis)**

1.  **Observation:** The current loading UI is a simple spinner. The `DOCUMENTATION.md` shows a `LoadingOverlayView` with progress, but the implementation details are missing from the service layer.
2.  **Code Analysis (`LiveVideoLoadingService.swift`):** This service has a `progressHandler` specifically for iCloud downloads, scaling progress from 0% to 70%. This is an excellent starting point. However, it only covers one specific scenario.
3.  **Code Analysis (`VideoLoadingService.swift`):** The new `ModernVideoLoadingService` introduces a more generic `VideoLoadingProgress` enum with phases like `.transferring` and `.validating`. This is the correct direction but lacks the data payload (like file size) needed for a rich UI.
4.  **Inference (The Functor Problem):** The current loading "functor" (the end-to-end process mapping a user's tap to a ready `AVAsset`) is not fully observable. It correctly transforms the input object (`PhotosPickerItem`) to the output object (`AVAsset`), but it loses critical information about the transformation process itself. We need to make the functor *instrumented*.

### **Step 1.2: First Principles Breakdown (The Fix)**

  * **Ideal Functor (`F_ideal`):** This functor maps a `PhotosPickerItem` to a stream of `VideoLoadingProgress` events, each rich with context (`phase`, `bytesLoaded`, `totalBytes`, `message`), culminating in a `VideoLoadingResult`.
  * **Observed Functor (`F_observed`):** This functor maps a `PhotosPickerItem` to a stream of simple progress events (`Double`), losing context.
  * **The Solution (A Natural Transformation `η`):** We will implement a "natural transformation" `η: F_observed ⇒ F_ideal`. This is not just a code change; it's a fundamental enhancement of our information pipeline. We will redefine the `VideoLoadingProgress` object to be the carrier of this richer information.

### **Step 1.3: Categorizing Remaining Issues**

  * **Object Gap:** The `VideoLoadingProgress` struct is our "object gap." It's incomplete. It needs to contain the file size to display "Loading X of Y MB."
  * **Missing Morphism:** There is no direct morphism to get the file size *before* starting the transfer. We must add this step. `PhotosPickerItem` can be queried for its `supportedContentTypes`, and we can use `item.loadTransferable(type: PhotoFileRepresentation.self)` to get metadata, including file size, before the main transfer begins.
  * **Non-Commutative Diagram (Potential Bug):** The `PhotosPersistenceService` correctly uses an `NSLock` to prevent a race condition when creating the "BreakDex" album. This ensures the diagram `(Check Album -> Create Album)` commutes correctly. We must ensure our new loading logic doesn't introduce any new race conditions.

### **Step 1.4: Hypothesizing Solutions**

  * **Solution:** We'll introduce a preliminary loading step to fetch the file size. Then, as we transfer the file, we'll update the `VideoLoadingProgress` object. Even if the file copy itself is atomic (like `FileManager.copyItem`), we can emit distinct states: `.initializing`, `.transferring(totalBytes: Y)`, `.validating`, `.completed`. This provides the user with a transparent, step-by-step view of the process.

// MARK: - Loading Progress
public struct VideoLoadingProgress {
    let phase: LoadingPhase
    let correlationId: String

    public enum LoadingPhase {
        case initializing
        // Add totalBytes to show "X of Y MB"
        case transferring(bytesLoaded: Int64?, totalBytes: Int64)
        case validating
        case creatingAsset
        case completed
        case failed(Error)
    }

    // Computed properties for the UI
    public var progress: Double {
        switch phase {
        case .initializing:
            return 0.0
        case .transferring(let bytesLoaded, let totalBytes):
            guard let loaded = bytesLoaded, totalBytes > 0 else { return 0.2 } // Show some progress
            return 0.2 + (Double(loaded) / Double(totalBytes) * 0.6) // Scale transfer to 20%-80%
        case .validating:
            return 0.8
        case .creatingAsset:
            return 0.95
        case .completed:
            return 1.0
        case .failed:
            return 0.0
        }
    }

    public var message: String {
        switch phase {
        case .initializing:
            return "Preparing to load..."
        case .transferring(_, let totalBytes):
            let formattedSize = ByteCountFormatter.string(fromByteCount: totalBytes, countStyle: .file)
            return "Transferring \(formattedSize)..."
        case .validating:
            return "Validating video format..."
        case .creatingAsset:
            return "Preparing video player..."
        case .completed:
            return "Load complete!"
        case .failed(let error):
            return "Error: \(error.localizedDescription)"
        }
    }
}

// In class ModernVideoLoadingService

/// Load video from PhotosPicker item using streaming approach
public func loadVideo(from item: PhotosPickerItem) async throws -> VideoLoadingResult {
    let correlationId = generateCorrelationId()
    currentCorrelationId = correlationId

    logger.info("🎬 VIDEO_LOADING: 🚀 Loading from PhotosPicker [\(correlationId)]")
    await reportProgress(.initializing, correlationId: correlationId)

    let startTime = Date()

    do {
        // 🎯 STEP 1: Get file representation to know the size beforehand.
        // This is our new morphism to close the "object gap".
        guard let fileRep = try await item.loadTransferable(type: PhotoFileRepresentation.self) else {
            logger.warning("🎬 VIDEO_LOADING: ⚠️ Could not load file representation. Falling back.")
            // If this fails, we can fall back to the PHAsset method which doesn't need a pre-fetched size.
            return try await loadViaPhotosLibrary(from: item, correlationId: correlationId) ?? { throw VideoLoadingError.transferableNotSupported }()
        }
        let totalBytes = fileRep.size

        // 🎯 STEP 2: Report the transferring phase with total size.
        await reportProgress(.transferring(bytesLoaded: nil, totalBytes: totalBytes), correlationId: correlationId)

        // Try streaming URL approach first
        if let urlResult = try await loadViaStreaming(from: item, totalBytes: totalBytes, correlationId: correlationId) {
            await reportProgress(.completed, correlationId: correlationId)
            logCompletion(result: urlResult, startTime: startTime, method: "streaming")
            return urlResult
        }

        // Fallback to PHAsset loading if streaming fails
        if let assetResult = try await loadViaPhotosLibrary(from: item, correlationId: correlationId) {
            await reportProgress(.completed, correlationId: correlationId)
            logCompletion(result: assetResult, startTime: startTime, method: "photos_library_fallback")
            return assetResult
        }

        throw VideoLoadingError.transferableNotSupported

    } catch {
        await reportProgress(.failed(error), correlationId: correlationId)
        logger.error("🎬 VIDEO_LOADING: ❌ Loading failed [\(correlationId)]: \(error)")
        throw error
    }
}

## 💣 Step 3: Identifying and Addressing Blind Spots

1.  **Atomic Copy Progress:** `FileManager.copyItem` is atomic; it does not report progress. Our UI will show "Transferring X MB" and then jump from \~15% to \~80% instantly.
      * **Mitigation:** This is an acceptable UX trade-off for V1. The user still gets more information than before (they know the file size and that a transfer is happening). A true byte-by-byte progress bar would require a much more complex `InputStream`/`OutputStream` implementation, which adds significant risk for marginal gain.
2.  **iCloud Download Progress Integration:** The old `LiveVideoLoadingService` had a `progressHandler` for iCloud downloads. When `ModernVideoLoadingService` falls back to `loadViaPhotosLibrary`, it uses `requestAVAsset`. We must ensure the `progressHandler` on the `PHVideoRequestOptions` is configured to pipe its `Double` progress into our new `VideoLoadingProgress` enum.
      * **Action:** In `loadFromPHAsset`, when setting up `PHVideoRequestOptions`, add a `progressHandler` that calls `reportProgress(.transferring(bytesLoaded: Int64(progress * Double(totalBytes)), totalBytes: totalBytes), ...)`
3.  **Cancellation:** The new loading overlay is more engaging, and users might want to cancel it.
      * **Action:** Add a "Cancel" button to the `LoadingOverlayView`. This button's action should trigger `videoLoadingService.cancelCurrentOperation()` and reset the state in `AddMoveStateManager`. This makes the flow fully interactive.
4.  **Error Display:** The `.failed` state in `LoadingOverlayView` should persist for a few seconds or until the user taps to dismiss it, allowing them to read the error message.
      * **Action:** Add a tap gesture to the `LoadingOverlayView` in the `.failed` state that resets the flow back to `.ready`.

This specification outlines the redesign of the video loading experience within the "Add Move" flow. This effort is part of a larger milestone to harden the entire end-to-end "Add Move" pipeline, ensuring videos are saved with frame-accurate precision and robust, fault-tolerant data persistence.

#### **1.2. Business Goal**
The primary goal is to **increase user trust and reduce perceived latency**. By making the loading process transparent, we eliminate user uncertainty about "why it's taking so long," which improves engagement and reduces the likelihood of users abandoning the flow. A robust save pipeline ensures data integrity, which is critical for user retention.

#### **1.3. User Persona**
* **"The Athlete"**: This user values precision, reliability, and a frictionless experience. They treat the app as a professional tool, akin to a mechanical watch. They have zero tolerance for data loss, incorrect transformations (e.g., wrong trim), or unexplained delays. The system must "just work" flawlessly, allowing them to focus on cataloging their training footage.

2.  **Selection:** They select a video from their Photos library using the `PhotosPicker`.

4.  **Completion:** The loading overlay transitions away, and the video is ready for trimming, having provided the user with full transparency into the loading process.
5.  **Saving:** After trimming, rotating, and naming the move, the user taps "Save." The system flawlessly saves the video to the "BreakDex" Photos album and creates a corresponding `Move` entity in Core Data, preserving the exact transformations (WYSIWYG).

* Implement a new, state-driven loading UI that displays the video's file size and the current loading phase.
* Ensure the `ModernVideoLoadingService` emits detailed progress events to power the new UI.
* Guarantee the end-to-end save process is atomic and reliable, correctly preserving user-defined trims and rotations.
* Ensure the `PhotosPersistenceService` intelligently uses the existing "BreakDex" album, preventing duplicate or empty albums.

#### **1.6. Non-Goals**
* This spec does not cover building a byte-by-byte, real-time progress indicator for the file transfer itself. The phase-based progress is sufficient for V1.
* This spec does not include a redesign of the trimming or naming views, only the loading and saving logic.
