### 1. Overview (The “What” and “Why”)

#### 1.1. Goal

The primary goal of this specification is to achieve a **fully functional, correct, and precise end-to-end "Add Move" workflow.** The implementation must be robust enough to handle complex user interactions, various video asset types, and maintain data integrity across the application's state, Core Data, and the Photos library.

#### 1.2. Persona & User Journey

* **Persona:** "The Athlete". This user values a frictionless, reliable tool that feels like a "mechanical watch" in its precision. They need to catalog training footage quickly and accurately, without encountering errors, hangs, or inconsistencies, regardless of interaction speed or file size.
* **Core User Journey:**
    1.  User taps "Add" and selects a video from the Photos library.
    2.  The app displays a real-time, transparent loading indicator.
    3.  The user enters the trimming view, adjusts the trim handles, and applies rotation.
    4.  The user may choose to "Change Video," select a new one, but then cancel and return to the original video with its trim/rotation state preserved.
    5.  The user proceeds to the naming view, where a WYSIWYG preview of the final, trimmed, and rotated video is displayed.
    6.  The user enters a name and saves the move.
    7.  The final video is saved to the "BreakDex" Photos album, and the metadata is saved to the Core Data database.
    8.  The saved move is immediately viewable in the `MoveDetailView` with the correct video playback.

#### 1.3. Non-Goals

* **UI Redesign:** This spec does not cover any visual redesign of the `FeatureRichTrimmerView`, `NameMoveView`, or other UI components.
* **New Combo Features (UI):** While backend logic for combo cleanup and validation is included, the implementation of new UI for combo creation or management is out of scope.
* **Algorithm Changes:** Changes to the spaced repetition algorithm or other unrelated business logic are not part of this task.

### 2. System Requirements & Acceptance Criteria

#### 2.1. Functional Requirements

1.  **FR1: Deterministic State Inheritance:** Rotation and trim settings must be preserved deterministically throughout the user journey, especially when navigating back from the `NameMoveView` or canceling the "Change Video" flow.
2.  **FR2: Real-Time Progress Reporting:** Video loading progress (for both initial and trimmed assets) must be transparently and accurately reported to the UI in real-time, including states like downloading from iCloud.
3.  **FR3: Data Integrity - Orphaned Combos:** The system must automatically detect and delete `Combo` entities from Core Data if all of their associated `Move` entities are orphaned (i.e., the source videos are no longer in the Photos library).
4.  **FR4: Data Integrity - Duplicate Combo Names:** The system must prevent the creation of a `Combo` with a name that already exists in the database (case-insensitive).
5.  **FR5: WYSIWYG Experience:** The video asset saved to the "BreakDex" album and referenced in Core Data must be an exact representation (trim range and rotation) of the preview shown in the `NameMoveView`.
6.  **FR6: Atomic Album Management:** The application must *always* save new videos to a pre-existing "BreakDex" Photos album if it exists. A new album should only be created if one does not exist. Duplicate or empty albums must not be created.

#### 2.2. Non-Functional Requirements

1.  **NFR1: Performance:**
    * iCloud download progress updates must be reflected in the UI with a latency of `<500ms`.
    * The transition from the `Trimming` state to the `Naming` state, including trimmed asset generation, must complete within `3 seconds` for a 60-second 1080p video.
2.  **NFR2: Reliability:**
    * The application must not crash due to state mismatches or race conditions during the "Add Move" flow.
    * The "99% stuck" loading issue must be completely eliminated; all progress bars must deterministically reach 100% upon completion.
3.  **NFR3: Memory Management:** The "Add Move" flow must not introduce retain cycles or memory leaks, verifiable via Instruments profiling.
