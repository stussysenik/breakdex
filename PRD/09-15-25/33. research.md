In practice, report progress from Photos as a 0–1 fraction, avoid synchronous AVAsset property queries by using try await asset.load(…), compute an ETA using NSProgress’s estimatedTimeRemaining or a rolling estimate, throttle UI updates on the main actor, and drive a short 0.1s animation into the ready state once AVPlayerItem is prepared, while handling cancellations and failures via the Photos info dictionary keys. ### Progress reporting
- Use PHVideoRequestOptions with isNetworkAccessAllowed = true and a progressHandler to receive continuous 0–1 progress while Photos downloads iCloud-backed video bytes, and request the AVAsset via PHImageManager.requestAVAsset(forVideo:options:resultHandler:) so the same request yields both progress and the final asset without blocking the UI. [2][1][3]
- For local files or once an AVAsset is obtained, load required properties asynchronously with AVFoundation’s async load API (for example, await asset.load(.playable, .duration, .tracks)) to avoid synchronous property access that can hang the main thread, which Apple explicitly recommends migrating to in WWDC sessions and docs. [4][5][6][13]
- Bridge Photos’ callback-style progress into Swift Concurrency using AsyncStream so a SwiftUI view can observe a continuous sequence of progress values without blocking; produce values off the main actor and consume them on the main actor for UI updates. [7][16][17]


### State management
- Model the progress state in a @Observable view model isolated to the **MainActor** so SwiftUI automatically re-renders as progress updates arrive while guaranteeing main-thread safety for UI mutations. [9][18][19][8]
- Expose a progress AsyncStream<Double> (and a derived ETA) from a VideoLoadingService protocol to keep SRP and DI intact; SwiftUI tasks can for‑await progress values to update @Observable properties, preserving unidirectional data flow. [7][20][9][10]
- Track progress at two levels: (1) asset acquisition from Photos (iCloud download) and (2) AVAsset readiness via async property loads, emitting composed progress to reach **100%** only when the player item is ready for the Pre-Trim view. [1][2][3][4]


### Performance optimization
- Avoid UI freezes by never querying synchronous AVAsset properties on not‑yet‑loaded assets; instead, use AVFoundation’s async load methods and perform heavy work off the main actor, per Apple’s guidance for responsive media apps. [4][13]
- Throttle progress updates to a reasonable cadence (e.g., 15–30 Hz) before mutating @Observable properties to reduce main-thread churn; Apple’s guidance on avoiding main-thread hangs underlines keeping the main actor lightly loaded. [14]
- Memory overhead of progress tracking is minimal (a few Doubles/timestamps); ensure cancellation of Photos requests and Tasks to avoid retaining large assets unnecessarily when views disappear. [1][3]


### User experience
- For ETA, prefer NSProgress.estimatedTimeRemaining when using an NSProgress to aggregate unit counts, or compute a rolling ETA from timestamps and fractionCompleted when Photos only supplies a Double progress. [15]
- Implement the seamless 0.1s transition by setting the “ready” state inside withAnimation(.linear(duration: 0.1)) and optionally use the iOS 17+ completion closure to trigger any post-transition work deterministically. [11][12]
- Handle failures gracefully by inspecting Photos’ result info dictionary (e.g., PHImageErrorKey, PHImageCancelledKey) and presenting a retry/cancel path, while allowing the progress handler’s stop pointer to cancel network downloads if needed. [3][21][1]


### Integration strategy
- Wrap Pre-TrimView with a ZStack that overlays LoadingOverlayView while progress < 1.0 and the player isn’t ready; bind overlay elements to progress and ETA in the @Observable view model injected via the app’s DI container. [9][10][19]
- In AddMoveContainer, introduce a Loading state that carries a progress model and an optional message, then transition to Ready with the prepared AVPlayerItem after await playerItem readiness, animating the handoff in 0.1 seconds. [4][11]
- Maintain backward compatibility by keeping existing binary states for legacy paths while progressively enhancing to a tri-state (idle/loading/ready) with progress fields, leaving the old path untouched until all call sites adopt the new service. [10][19]


### Reference implementation (key pieces)
- Request the Photos asset with progress and bridge to AsyncStream; publish to SwiftUI on the main actor and use AVFoundation async load for readiness. [1][2][3][7][4]

```swift
import Photos
import AVFoundation

struct VideoLoadEvents {
    var fraction: Double
    var etaSeconds: TimeInterval?
}

protocol VideoLoadingService {
    func loadPHAssetWithProgress(_ asset: PHAsset) -> AsyncThrowingStream<VideoLoadEvents, Error>
}

final class LiveVideoLoadingService: VideoLoadingService {
    func loadPHAssetWithProgress(_ asset: PHAsset) -> AsyncThrowingStream<VideoLoadEvents, Error> {
        AsyncThrowingStream { continuation in
            let options = PHVideoRequestOptions()
            options.isNetworkAccessAllowed = true
            let start = CACurrentMediaTime()
            options.progressHandler = { progress, error, stop, info in
                // Compute simple ETA if possible
                let f = max(0.0001, progress)
                let elapsed = CACurrentMediaTime() - start
                let eta = elapsed * (1 - f) / f
                continuation.yield(.init(fraction: progress, etaSeconds: eta))
            }

            let reqID = PHImageManager.default().requestAVAsset(forVideo: asset, options: options) { avAsset, _, info in
                if let error = info?[PHImageErrorKey] as? NSError {
                    continuation.finish(throwing: error)
                    return
                }
                guard let avAsset = avAsset else {
                    continuation.finish(throwing: NSError(domain: "VideoLoad", code: -1, userInfo: [NSLocalizedDescriptionKey: "Asset unavailable"]))
                    return
                }
                Task {
                    // Ensure the asset is playable and prepared
                    do {
                        let _ = try await avAsset.load(.playable, .duration, .tracks)
                        continuation.yield(.init(fraction: 1.0, etaSeconds: 0))
                        continuation.finish()
                    } catch {
                        continuation.finish(throwing: error)
                    }
                }
            }

            continuation.onTermination = { _ in
                PHImageManager.default().cancelImageRequest(reqID)
            }
        }
    }
}
```

final class UnifiedVideoPlayerViewModel {
    enum Phase { case idle, loading, ready, failed(Error) }

    var phase: Phase = .idle
    var progress: Double = 0
    var etaSeconds: TimeInterval?
    var playerItem: AVPlayerItem?

    private var loadTask: Task<Void, Never>?

    func startLoading(asset: PHAsset, service: VideoLoadingService) {
        loadTask?.cancel()
        phase = .loading
        progress = 0
        etaSeconds = nil

        loadTask = Task {
            do {
                var finalAsset: AVAsset?
                for try await ev in service.loadPHAssetWithProgress(asset) {
                    // Throttle if needed; here we just assign directly

                    self.etaSeconds = ev.etaSeconds

    @State var viewModel = UnifiedVideoPlayerViewModel()

### Answers to the research questions

- How to extract real-time progress from Photos/AVAsset, and best practices to avoid blocking the UI? Use PHVideoRequestOptions.progressHandler during PHImageManager.requestAVAsset(forVideo:…) for iCloud downloads, then switch to AVFoundation’s async load(…) for asset properties to keep all I/O non-blocking on iOS 18. [2][1][3][4][13]
- How to structure progress updates for SwiftUI using Swift Concurrency? Bridge callback progress to AsyncStream, consume with for‑await in a Task, and mutate a @Observable model on the main actor for reactive UI updates. [7][17][9][8]
- Where to track progress (asset vs. processing vs. player)? Track at asset acquisition (Photos → progressHandler), then at AVAsset readiness via async loads, and optionally at player-item readiness; combine into a single stream so the bar reaches 100% exactly when the player is ready. [1][2][3][4]
- How to run background processing and balance update frequency? Offload media property loading to async load and reduce main-thread load per Apple’s responsive-media guidance; throttle progress UI updates to a modest cadence to avoid excessive re-rendering. [4][13][14]
- How to compute ETA? When an NSProgress is involved, prefer its estimatedTimeRemaining; otherwise derive ETA from elapsed time and fractionCompleted and smooth with a moving average to prevent jitter. [15]
- How to implement the 0.1s transition? Use withAnimation(.linear(duration: 0.1)) and, on iOS 17+, its completion closure for any follow-up actions after the Pre-Trim view becomes visible. [11][12]
- How to handle failures gracefully? Inspect the Photos result info dictionary for PHImageErrorKey/PHImageCancelledKey to present a retry/cancel UI and safely terminate the AsyncStream. [3][21]
- How to integrate LoadingOverlayView and maintain DI/back-compat? Inject a VideoLoadingService into the view model via the existing container, keep the original binary state path, and add a “loading with progress” path that overlays LoadingOverlayView until the ready state is reached. [10][19]
