# BreakingFlashcards App Architecture Documentation

## 📋 Document Overview
This comprehensive architectural document provides a complete technical overview of the BreakingFlashcards iOS application. It serves as a handover document for principal engineers, detailing the codebase structure, design patterns, data flow, and implementation details.

---

## 🏗️ **ARCHITECTURAL OVERVIEW**

### **Core Design Philosophy**
BreakingFlashcards follows a **Model-View-ViewModel (MVVM)** architecture with **SwiftUI** as the primary UI framework. The app implements a **modular, component-based design** with clear separation of concerns between data management, business logic, and user interface.

### **Technology Stack**
- **Frontend**: SwiftUI with programmatic navigation
- **Data Persistence**: Core Data with SQLite backend
- **Media Management**: AVFoundation for video processing
- **State Management**: SwiftUI's built-in @State, @ObservedObject, @EnvironmentObject
- **Design System**: Custom IBM Plex Mono typography with semantic color system
- **Architecture Pattern**: MVVM with Repository pattern for data access

## 🗄️ **DATA MODEL & PERSISTENCE**

### **Core Data Schema**

#### **Move Entity**
```swift
Move {
    id: UUID                          // Primary key
    name: String                      // Move display name
    createdAt: Date                   // Creation timestamp
    learningState: String             // "NEW", "LEARNING", "MASTERY"
    videoReference: Data              // Encoded file path
    combos: [ComboMove]              // Many-to-many relationship
    reviews: [Review]                 // One-to-many relationship
}
```

#### **Combo Entity**
```swift
Combo {
    id: UUID                         // Primary key
    name: String                     // Combo display name
    comboMoves: [ComboMove]          // Ordered move sequence
}
```

#### **ComboMove Entity** (Junction Table)
```swift
ComboMove {
    id: UUID                         // Primary key
    sequenceIndex: Int64             // Position in combo
    combo: Combo                     // Parent combo
    move: Move                       // Referenced move
}
```

#### **Review Entity**
```swift
Review {
    id: UUID                         // Primary key
    rating: String                   // "AGAIN", "HARD", "GOOD"
    reviewedAt: Date                 // Review timestamp
    move: Move                       // Associated move
}
```

### **Media Index System**
The app implements a dual persistence strategy:

1. **Core Data**: Stores move metadata, combo relationships, and review history
2. **Media Index JSON**: Tracks video file locations, hashes, and metadata for performance

#### **MediaIndexManager Architecture**
```swift
class MediaIndexManager {
    // Singleton instance
    static let shared = MediaIndexManager()

    // Core functionality
    func buildIndexIfMissing(context: NSManagedObjectContext)
    func auditAndRehydrateIfNeeded(context: NSManagedObjectContext)
    func upsert(moveId: UUID, ...)                    // Update or insert
    func findByMoveId(_ moveId: String) -> MediaIndexEntry?
    func exportIndexJSON() -> URL?                    // Export to JSON
    func importFromJSON(_ index: MediaIndex)         // Import from JSON
}
```

## 📊 **ARCHITECTURAL DECISIONS & TRADE-OFFS**

### **Design Decisions**

#### **1. MVVM with SwiftUI**
- **Pros**: Reactive UI updates, type safety, composability
- **Cons**: Learning curve, state management complexity
- **Rationale**: Modern iOS development best practices, Apple's recommended approach

#### **2. Dual Persistence Strategy**
- **Core Data**: Structured data relationships and queries
- **Media Index**: Fast file system operations and integrity checking
- **Rationale**: Optimal performance for different data access patterns

#### **3. State Machine for Complex Workflows**
- **AddMoveView**: Enum-based state management for multi-step processes
- **Benefits**: Clear state transitions, predictable UI updates
- **Alternative Considered**: Coordinator pattern (deemed overkill for this scope)

#### **4. Component-based Video Processing**
- **Modular Design**: Separate components for trimming, playback, thumbnails
- **Benefits**: Reusability, testability, maintainability
- **Integration**: Loose coupling through protocols and closures

### **Technical Trade-offs**

#### **1. SwiftUI Limitations**
- **Challenge**: Complex video processing in SwiftUI context
- **Solution**: UIViewControllerRepresentable for AVFoundation integration
- **Impact**: Some imperative code mixed with declarative UI

#### **2. Core Data + File System**
- **Challenge**: Managing media files alongside database records
- **Solution**: MediaIndexManager for file system tracking
- **Impact**: Additional complexity but better performance

#### **3. Real-time Video Processing**
- **Challenge**: Heavy computation on main thread
- **Solution**: Background Task processing with progress updates
- **Impact**: Complex concurrency management
