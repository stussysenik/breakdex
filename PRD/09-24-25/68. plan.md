## 1\. Overview: What & Why

### 1.1. Goal

The **goal** is to implement a fully functional, end-to-end "Add Move" workflow. A user must be able to select a video, apply trim and rotation edits, name the resulting clip, and successfully save it. The final artifact must be persisted according to the documented architecture: the video file is stored in the user's Photos library, while its metadata, including the Photos library identifier, is stored in the app's Core Data database.

### 1.2. Business Value (Why)

The "Add Move" flow is a **core feature** and the primary content creation mechanism of the application. Its failure blocks the main user journey, posing a critical risk to user retention and app viability. A stable and performant save process is essential for user trust and the app's success.

### 1.3. User Persona & Journey

  * **Persona**: A "Creator" who uses the app to capture, refine, and catalog physical movements for learning and review.
  * **User Journey**:
    1.  The Creator selects a video from their library.
    2.  They trim and rotate the video to isolate the key movement.
    3.  They proceed to the naming screen, viewing a preview of the edited clip.
    4.  They enter a name and tap "Save Move."
    5.  **Desired Outcome**: The user receives a success confirmation, and the new `Move` appears in their "Arsenal".
    6.  **Current Outcome**: The user receives a "Failed to save move" error, caused by a "Trimmer is not available" validation failure, which breaks the flow and prevents content creation.

### 1.4. Non-Goals

  * **UI/UX Overhaul**: This spec does not cover changes to the visual design of the trimming or naming views.
  * **New Features**: Implementation of adjacent features like "Combos" or the "Review" system is out of scope.
  * **General Performance Tuning**: Optimizations outside of correcting the critical Core Data misuse and ensuring the save process meets its latency budget are not included.

## 2\. Verifiable Elements

### 2.1. Acceptance Criteria

  * **AC1 (Success Path)**: When a user with a validly named move taps "Save," the app must:
      * Process the video with the final trim and rotation settings.
      * Save the processed video to the user's Photos library within the "BreakDex" album.
      * Create a `Move` entity in Core Data with the correct `name`, `trimStartTime`, `trimEndTime`, `rotationQuarterTurns`, and the **`localIdentifier`** of the newly created asset in the Photos library.
      * The `videoReference` field in the `Move` entity **must not** be populated.
      * Transition the UI to the `success` state.
  * **AC2 (State Integrity)**: The `TrimmerViewModel` must be deallocated upon leaving the `Trimming` state, and the save validation logic in the `Naming` and `Saving` states must not depend on it.
  * **AC3 (Data Correctness)**: The `photosIdentifier` persisted in Core Data must correctly resolve to the final, edited video in the Photos library.

### 2.2. Edge Cases

  * **Storage Full**: The system must gracefully handle disk space errors during video export or Photos library save, presenting a user-friendly error.
  * **Permission Denied**: If Photos library permissions are insufficient, the save must fail with an informative message.
  * **Minimum Duration**: Validation must prevent saving moves with a final duration of less than 3.0 seconds.
  * **Invalid Name**: The save button must be disabled and validation must fail if the move name is empty or contains only whitespace.

### 2.3. Metrics & Constraints

  * **Latency**: The end-to-end save operation (user tap to success UI) must complete in **\< 5 seconds** for a 30-second source video.
  * **Memory**: The memory usage increase during the save operation must not exceed **150MB**. The `videoReference` data blob must never be loaded into memory during the save-to-database step.
  * **CPU**: Video processing must occur on a background thread, ensuring UI responsiveness.
