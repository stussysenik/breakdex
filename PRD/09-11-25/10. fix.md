# Video Player Architecture Refactoring Plan

Based on my analysis of the current video player implementation, here's a detailed plan to refactor the architecture following Single Responsibility Principle (SRP):

## Current Issues
1. VideoPlayerViewModel handles too many responsibilities (asset loading, player initialization, readiness monitoring, coordination)
2. Extensive logging mixed throughout the codebase
3. Inconsistent error handling across components
4. Lack of proper separation of concerns

## Proposed Architecture

### 1. VideoAssetLoader Component
**Purpose**: Handle loading video assets from various sources (Photos, URLs, etc.)
**Location**: BreakingFlashcards/Video/Processing/Components/VideoAssetLoader.swift

**Responsibilities**:
- Load assets from Photos library using identifiers
- Load assets from file URLs
- Load assets from CoreData Move objects
- Handle asset loading errors
- Provide asset metadata

**API**:
```swift
@MainActor
class VideoAssetLoader {
    enum Source {
        case photos(identifier: String)
        case url(URL)
        case move(Move)
    }
    
    func loadAsset(from source: Source) async throws -> AVAsset
}
```

### 2. PlayerInitializer Component
**Purpose**: Create and configure AVPlayer instances
**Location**: BreakingFlashcards/Video/Processing/Components/PlayerInitializer.swift

**Responsibilities**:
- Create AVPlayer instances from assets
- Apply video transformations (rotation, trimming)
- Configure player properties
- Handle player creation errors

**API**:
```swift
@MainActor
class PlayerInitializer {
    func createPlayer(from asset: AVAsset, quarterTurns: Int = 0) async throws -> AVPlayer
    func createPlayerItem(from asset: AVAsset, quarterTurns: Int = 0) async throws -> AVPlayerItem
}
```

### 3. ReadinessMonitor Component
**Purpose**: Monitor player readiness state with proper timeout handling
**Location**: BreakingFlashcards/Video/Processing/Components/ReadinessMonitor.swift

**Responsibilities**:
- Monitor AVPlayer and AVPlayerItem status changes
- Implement timeout handling for readiness checks
- Provide async readiness waiting
- Handle readiness monitoring errors

**API**:
```swift
@MainActor
class ReadinessMonitor {
    func waitForPlayerReady(_ player: AVPlayer) async throws
    func waitForItemReady(_ item: AVPlayerItem) async throws
    func cancelMonitoring()
}
```

### 4. VideoCoordinator Component
**Purpose**: Coordinate between components and manage overall video workflow
**Location**: BreakingFlashcards/Video/Processing/Components/VideoCoordinator.swift

**Responsibilities**:
- Orchestrate asset loading, player creation, and readiness monitoring
- Manage state transitions
- Handle errors from all components
- Provide unified API for video playback

**API**:
```swift
@MainActor
class VideoCoordinator: ObservableObject {
    enum State {
        case loading
        case ready(AVPlayer)
        case error(String)
    }
    
    @Published private(set) var state: State = .loading
    
    func loadVideo(from source: VideoAssetLoader.Source, quarterTurns: Int = 0) async
    func teardown()
    func startPlayback()
}
```

### 5. Structured Logging Component
**Purpose**: Provide structured logging with correlation IDs
**Location**: BreakingFlashcards/Video/Processing/Components/VideoLogger.swift

**Responsibilities**:
- Generate correlation IDs for video sessions
- Provide structured logging methods
- Track video lifecycle events
- Log errors with context

**API**:
```swift
struct VideoLogger {
    static func log(_ message: String, category: String, correlationID: String? = nil)
    static func error(_ message: String, error: Error, category: String, correlationID: String? = nil)
}
```

### 6. Error Handling Component
**Purpose**: Centralized error handling for video processing
**Location**: BreakingFlashcards/Video/Processing/Components/VideoErrorHandler.swift

**Responsibilities**:
- Define video-specific error types
- Provide error handling strategies
- Convert error types for user display
- Track error occurrences

**API**:
```swift
enum VideoError: LocalizedError {
    case assetLoadingFailed(underlyingError: Error?)
    case playerInitializationFailed(underlyingError: Error?)
    case readinessTimeout
    case playbackFailed(underlyingError: Error?)
    
    var errorDescription: String? { /* implementation */ }
}

class VideoErrorHandler {
    static func handle(_ error: Error, correlationID: String) -> VideoError
    static func getUserMessage(for error: VideoError) -> String
}
```

## Refactoring Plan

### Phase 1: Create Components
1. Create VideoAssetLoader component
2. Create PlayerInitializer component
3. Create ReadinessMonitor component
4. Create VideoCoordinator component
5. Create VideoLogger component
6. Create VideoErrorHandler component

### Phase 2: Refactor VideoPlayerViewModel
1. Update VideoPlayerViewModel to use VideoCoordinator
2. Remove direct asset loading code
3. Remove direct player initialization code
4. Remove readiness monitoring code
5. Replace scattered logging with VideoLogger
6. Replace error handling with VideoErrorHandler

### Phase 3: Update Views
1. Update CustomVideoPlayerView to use refactored VideoPlayerViewModel
2. Update AVPlayerViewRepresentable to use refactored VideoPlayerViewModel
3. Ensure all video-related views work with new architecture

### Phase 4: Testing
1. Unit test each component independently
2. Integration test component interactions
3. End-to-end test video playback scenarios
4. Test error handling paths

### Phase 5: Verification
1. Build project to ensure no compilation errors
2. Run app to verify video playback functionality
3. Check memory usage and performance
4. Verify logging and error handling work correctly

## Expected Benefits
1. **Improved Maintainability**: Each component has a single responsibility
2. **Better Testability**: Components can be tested independently
3. **Reduced Code Duplication**: Common functionality centralized
4. **Enhanced Error Handling**: Consistent error handling across components
5. **Better Logging**: Structured logging with correlation IDs
6. **Easier Debugging**: Clear separation of concerns makes issues easier to isolate

This plan provides a clear path to refactor the video player architecture following SRP principles while maintaining all existing functionality.
