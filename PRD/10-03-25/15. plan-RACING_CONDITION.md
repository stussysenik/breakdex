When the view appears, its `onAppear` logic detects a discrepancy between its local `0.0` state and the model's now-correct 90° state. Instead of simply adopting the correct value, it triggers an unnecessary animation and state change to "catch up," which results in the bug.

This is achieved by moving the state initialization into the view's `init` method, guaranteeing the view is created with the correct state from the start.

### 1\. The "What" and "Why": Vision & Goals

#### **Problem Statement**

The "Add Move" workflow exhibits a race condition during the initialization of the `FeatureRichTrimmerView`. When a video with intrinsic rotation is loaded, the view's local animation state (`@State private var previewRotationDegrees`) is created with a default value of `0.0` before the `TrimmerViewModel` has finished asynchronously loading the asset's true intrinsic rotation. This state mismatch triggers a flawed "correction" logic in the view's `.onAppear` modifier, which unnecessarily increments the `userAppliedRotation`, resulting in an incorrect final rotation (e.g., 180° instead of the expected 90°). This breaks the **isomorphism** (the 1-to-1 structural mapping) that must exist between the model's state and the view's state from the moment of creation.

#### **User Persona & Journey**

  * **Persona:** "The Athlete" — Demands precision, reliability, and a frictionless experience. They value tools that are as dependable as a mechanical watch.
  * **User Journey:**
    1.  The Athlete selects a video that was filmed in portrait mode but is saved with metadata indicating a 90° rotation.
    2.  They tap "Continue" to enter the trimming view.
    3.  **Expected:** The video preview immediately appears correctly oriented (portrait), and the rotation button correctly shows "90°", reflecting the video's intrinsic state with zero user modifications.
    4.  **Actual (Bug):** The video preview flashes from an incorrect orientation to the correct one, and the rotation button incorrectly shows an extra 90° rotation.

#### **Goals (What We Will Do) ✅**

  * **Enforce Isomorphic Initialization:** Ensure that `FeatureRichTrimmerView`'s state is a perfect, 1-to-1 reflection of `TrimmerViewModel`'s state from the very first render, eliminating any "correction" logic.
  * **Eliminate Animation Flash:** The UI must render the correct rotation state on its initial appearance without any visual flickering or animated transitions from an incorrect default state.
  * **Strengthen Single Source of Truth:** Solidify `TrimmerViewModel` as the sole authority for rotation state, ensuring the view is purely a reactive reflection of the model.

#### **Non-Goals (What We Will Not Do) ❌**

  * **Do not alter the `TrimmerViewModel`'s logic:** The view model's categorical rotation mathematics (`Total = Intrinsic + User`) is correct. The problem is in how the view initializes and synchronizes with this model.
  * **Do not introduce asynchronous complexity:** The solution will be a synchronous, deterministic fix within the view's `init` method, not a complex chain of `.onReceive` or `Task` blocks.

#### **Business Value (Why We Are Doing This) 📈**

  * **Increase User Trust and Retention:** A precise, bug-free tool empowers "The Athlete" persona, reducing frustration and making the app a reliable part of their training toolkit.
  * **Improve Perceived Performance:** Eliminating the jarring visual flash on load makes the app feel faster, more professional, and more stable.
  * **Reduce Engineering Debt:** Fixing this race condition at the source prevents future, more complex bugs related to state synchronization.
