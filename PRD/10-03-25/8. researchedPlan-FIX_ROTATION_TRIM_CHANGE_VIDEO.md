### \#\# **1. Root Cause Analysis: The Double Rotation Race Condition**

The bug occurs specifically when navigating back from `NameMoveView` to `FeatureRichTrimmerView`. It's a race condition between SwiftUI's view rendering and `AVPlayer`'s asynchronous item replacement.

Here is the precise sequence of events that causes the bug:

1.  **State in `NameMoveView`**: The video player is displaying an `AVPlayerItem` that has a 90° rotation baked into its `videoComposition`. This is correct for this screen.
2.  **User Taps "Back"**: The `FlowStateManager` begins its rollback logic.
      * It correctly restores the `userAppliedRotation = 1` (90°) in `AddMoveUnifiedState`.
      * It correctly initiates an **asynchronous** command to revert the player to the *original, un-rotated video asset*.
3.  **The Race Condition**: SwiftUI, reacting to the state change, destroys the `NameMoveView` and immediately begins creating and rendering the `FeatureRichTrimmerView` **before the asynchronous player item replacement is complete**.
4.  **Incorrect Render**:
      * The new `FeatureRichTrimmerView` initializes and correctly reads the restored state, applying a `.rotationEffect(.degrees(90))` modifier to its video player subview.
      * Simultaneously, the `AVPlayerViewRepresentable` (the UIKit bridge) is created and renders the `AVPlayer`'s `currentItem`. At this moment, the `currentItem` is **still the old, pre-rotated asset** from `NameMoveView`.
5.  **The Visual Artifact**: The user sees a video frame that is rotated twice: once by the asset's `videoComposition` (90°) and a second time by the SwiftUI view modifier (90°), resulting in an incorrect 180° rotation. The reversion of the player item finishes shortly after, but the damage is done.

The core of the problem lies in **`AVPlayerViewRepresentable.swift`**. Its `updateUIView` function is not robust enough to handle these rapid, asynchronous changes to the `AVPlayerItem`. It only checks if the top-level `AVPlayer` instance has changed, which it never does, as the player instance is shared.

```swift
    diagnosticLogger.startTiming("update_uiview")
    logger.info("🎬 AV_PLAYER_VIEW: updateUIView called (Simplified)")

    // 🎯 THE FIX: This logic makes the view a pure function of the ViewModel's state.
    // It prevents rendering with a stale player item during asynchronous transitions.

    // 1. If the ViewModel says the player is NOT ready (e.g., during an item swap),
    //    clear the player from the layer. This prevents showing a stale, rotated frame.
    if !viewModel.isPlayerReady {
        if uiView.playerLayer.player != nil {
             logger.warning("🎬 AV_PLAYER_VIEW: Player not ready, clearing layer to prevent stale frame.")
             uiView.playerLayer.player = nil
        }
    } else {
        // 2. If the ViewModel IS ready, ensure the layer has the correct player instance.
        //    This handles both initial setup and re-syncing after the new item is ready.
        if uiView.playerLayer.player !== viewModel.avPlayer {
            logger.info("🎬 AV_PLAYER_VIEW: Player is ready, syncing player instance to layer.")
            uiView.playerLayer.player = viewModel.avPlayer
        }
    }
    
    diagnosticLogger.stopTiming("update_uiview")
}
```
