### **1. The Root Cause: A Flawed, Two-Layer Rotation Architecture**

The core problem is that rotation is being applied twice:

1.  **At the Player Layer (Correctly):** When the video is loaded, the `AddMoveUnifiedState` orchestrator creates an `AVPlayerItem`. This process uses `VideoTransformBuilder`, which correctly "bakes" the video's intrinsic 90° rotation into the player item's composition. At this point, the player item itself is already visually correct.
2.  **At the SwiftUI View Layer (Incorrectly):** The `FeatureRichTrimmerView` then receives this already-correct player. However, its state variable `previewRotationDegrees` is also synchronized to the video's total rotation (90°). It then applies a `.rotationEffect(.degrees(90))` modifier to the player view.

The result is a visual composition of `90° (from the player) + 90° (from the SwiftUI view) = 180°`, which is the immediate upside-down preview you are seeing.

### **2. The Implementation Plan: Establishing a Single Source of Truth**

The solution is to eliminate this double rotation by making the **`AVPlayerItem` the single, authoritative source of visual rotation**. The SwiftUI view layer will no longer apply any rotation of its own; its only job is to display the player.

```swift
// In AddMoveUnifiedState.swift

@MainActor
public func handleRotation() async {
    logger.info("🔄 Handling rotation request.")

    // 1. Ensure we have the necessary components
    guard let trimmerVM = self.trimmerViewModel as? TrimmerViewModel,
          let asset = self.videoAsset,
          let identifier = self.photosIdentifier else {
        logger.error("❌ Cannot handle rotation: viewmodel or asset is missing.")
        return
    }

    // 2. Update the ViewModel state (the source of truth for user input)
    trimmerVM.userAppliedRotationTurns = (trimmerVM.userAppliedRotationTurns + 1) % 4
    
    let newTotalRotation = trimmerVM.totalRotationQuarterTurns
    logger.info("🔄 New total rotation will be \(newTotalRotation * 90) degrees.")

    // 3. Regenerate the player with the new total rotation
    do {
        // This call will create a new player item with the correct rotation baked in.
        _ = try await self.unifiedPlayerManager.createOrUpdatePlayer(
            asset: asset,
            photosIdentifier: identifier,
            rotationQuarterTurns: newTotalRotation,
            appContainer: self.appContainer
        )
        logger.info("✅ Player successfully regenerated with new rotation.")
    } catch {
        logger.error("❌ Failed to regenerate player on rotation: \(error.localizedDescription)")
        await setError(message: "Could not apply rotation.")
    }
}
```

### **3. Categorical Verification: Restoring Isomorphism**

This plan restores correctness and commutativity to the system.

  * **Flawed Model**: The previous system was a non-commutative composition of morphisms: `Morphism_Player(Intrinsic) + Morphism_SwiftUI(Total)`. The result was an incorrect visual state that was not a faithful representation (isomorphism) of the desired total rotation.
  * **Corrected Model**: The system is now a simple, commutative diagram.
    1.  The user interaction (`rotateButton()`) triggers a change in the `TrimmerViewModel` state.
    2.  This triggers a single, authoritative morphism (`handleRotation()`) that composes the final state.
    3.  This morphism generates a new `AVPlayerItem` object that has the **correct total rotation** baked in.
    4.  The SwiftUI view now acts as an **identity morphism**—it simply displays the player object without further transformation.

The visual preview is now a true **isomorphism** of the player item's state, and the player item's state is a true representation of the `ViewModel`'s total rotation. The double-rotation flaw is architecturally eliminated.
