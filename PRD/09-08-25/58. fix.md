Short answer: Establish a single source of truth for rotation/trim in one owner view model, route all changes as intents, run side effects via queued tasks outside view updates, and remove cross‑view mirroring and chained .onChange so nothing publishes during body evaluation. [1][2]

## Objectives
- Eliminate “Publishing changes from within view updates” by removing circular updates and ensuring no @Published mutations occur during body updates or view callbacks that run in the update phase. [1][3]
- Make rotation/trim state stable and predictable with one owner, and propagate via bindings down and intents up, avoiding duplicate state holders. [1][4]
- Keep preview/export parity using the composition builder, with side effects scheduled on a serial task pipeline owned by the model, not inline in views. [1][5]

## Non‑goals
- No architectural switch to a third‑party framework; stay with SwiftUI + Combine/Concurrency and existing AVFoundation pipeline. [1][5]
- No new editing features beyond rotation/trim and existing flow. [1]

## Root‑cause diagnosis
- Three competing state owners (AddMoveViewModel, TrimmerViewModel, local @State) create circular update chains via .onChange and property observers. [1][2]
- Async work is started from view updates and mutates @Published outputs synchronously, triggering the forbidden publish during body recomposition. [1][6]
- View identity is thrashed via .id or conditional rendering, causing StateObject re‑instantiation and “not installed” warnings. [1][7]

## Design principles
- Single source of truth: rotationQuarterTurns and trimRange live in TrimmerViewModel during trimming; other layers read them but never mirror or write their own copies. [1][4]
- Unidirectional flow: UI emits intents; model mutates state; view renders; no view-to-model-to-view echo chains via .onChange that set other observable state. [1][8]
- Side effects only from model: schedule preview/export work on a serial task in the model or in .task(id:) hooks that don’t update @Published synchronously. [1][9]

## Ownership and lifetimes
- Container creates and owns @StateObject addMoveVM and @StateObject trimmerVM once per flow; children receive them as @ObservedObject to prevent re‑instantiation. [1][7]
- Remove any @State rotationQuarterTurns in views; expose Binding<Int> computed off trimmerVM.rotationQuarterTurns for controls, with writes funneled to an intent method. [1][10]

## Event flow
- UI tap “Rotate” → trimmerVM.intentRotateNext() → model updates internal rotation, emits @Published after scheduling preview rebuild → view re‑renders. [1][8]
- UI trim drag → trimmerVM.intentSetTrim(range) → same pipeline; no intermediate view state mirrors. [1][8]
- Navigate “Save” → addMoveVM.consume(trimmerVM.snapshot()) to persist canonical rotation/trim; AddMoveViewModel never writes back into TrimmerViewModel during view recomposition. [1][4]

## Concurrency and side effects
- In TrimmerViewModel, queue side effects in a single serial TaskProperty (e.g., a Task handle or an AsyncSequence consumer) that cancels the previous job before starting a new one. [1][9]
- Do not publish @Published outputs while computing the next AVPlayerItem; only assign @Published when the item is ready, preferably via MainActor after awaiting. [1][6]
- Prefer .task(id: compositeKey) in the view to trigger read‑only side effects, but ensure any state mutation happens later via model methods, not inline in the task closure that runs during update. [1][9]

## Prohibited patterns
- No .onChange that writes to another ObservableObject or sets @State mirroring a model value; remove all cross‑wiring change handlers that bounce values. [1][2]
- No setting of @Published in willSet/didSet that can fire during view updates; move to explicit intents and dedicated methods. [1][11]
- No use of .id(viewModel.state) or inline conditional view swaps to force refresh; route navigation via container state and standard presentations. [1][12]

## File‑by‑file spec
- Views/Arsenal/AddMove/AddMoveViewModel.swift
  - Stop mirroring rotationQuarterTurns/trimRange for live UI; retain them only when transitioning or persisting, sourced from TrimmerViewModel.snapshot(). [1][4]
  - Expose intents: beginChangeVideo(), didPickVideo(...), cancelChangeVideo(), and persistMove(rotation, trim) without mutating TrimmerViewModel from view updates. [1][12]
- Views/Video/Trim/TrimmerViewModel.swift
  - Declare @Published rotationQuarterTurns and trimRange as the only canonical UI state for trimming, with public intents intentRotateNext() and intentSetTrim(_:) that enqueue side effects. [1][4]
  - Implement preparePreviewIfNeeded() that cancels prior build, awaits VideoTransformBuilder, then assigns @Published playerItem on MainActor, never during a synchronous view callback. [1][9]
- Views/Video/Trim/TrimmerView.swift
  - Bind controls to trimmerVM via Binding getters/setters that call intents, not via local @State or .onChange. [1][10]
  - Remove any .onChange bridges between AddMoveViewModel and TrimmerViewModel; rely on container to pass initial values once. [1][2]
- Views/Arsenal/AddMove/AddMoveContainer.swift
  - Instantiate @StateObject addMoveVM and trimmerVM exactly once; pass @ObservedObject into children; route states to screens without conditional inline swaps that recreate the trimming subtree. [1][7]
- Views/Video/Player/CustomVideoPlayerView.swift
  - Do not mutate any model state from inside body or overlay actions that run during updates; only send intents; keep video rotation via videoComposition not view transforms. [1][5]
- Video/Processing/VideoTransformBuilder.swift
  - No change in math, but ensure build is pure and side‑effect free, returning results for the model to publish after awaiting. [1][5]

## Synchronization strategy
- Initialization: container seeds trimmerVM with rotation/trim once when entering trimming; after that, only trimmerVM owns mutations. [1][7]
- Persistence: on leaving trimming, container reads trimmerVM.snapshot() to store in Core Data; no back‑writes into trimmerVM from AddMoveViewModel. [1][4]

## Testing plan
- Interaction: hammer rotate and scrub quickly; verify no purple runtime warnings and preview updates smoothly without re‑instantiation of models. [1][2]
- Navigation: enter/exit trimming repeatedly; confirm one TrimmerViewModel lifetime per session and stable rotation/trim values across recompositions. [1][7]
- Async: simulate long preview builds; verify cancellation replaces tasks cleanly and only one playerItem publish occurs per final state. [1][9]

## Acceptance criteria
- Zero “Publishing changes from within view updates” or “StateObject not installed” warnings during trimming, rotate, and save flows. [1][2]
- Rotation/trim state never resets unexpectedly, and no chained .onChange bridges exist between AddMoveViewModel and TrimmerViewModel. [1][8]
- Preview/export parity remains correct since builder usage is unchanged and side effects publish only after await outside view updates. [1][5]

## Rollout
- Feature flag “TrimStateRefactor”; ship to internal/beta with runtime warning capture and cancellation telemetry, then ramp after a clean run. [1][2]

This spec consolidates ownership, removes circular updates, and moves all side effects out of view updates so SwiftUI’s invariants are respected while preserving the AVFoundation pipeline and UX expectations. [1][2][7][5]
