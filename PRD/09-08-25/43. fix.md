Ideal fix: move “Change Video” presentation out of the view’s conditional rendering and into the app’s state machine so selection is driven by a dedicated state, presented modally or via container routing, with proper model ownership to prevent immediate onDisappear and view churn. [1][2][3]

Below is a spec‑kit to implement predictable, state‑driven navigation for video selection that aligns with SwiftUI lifecycle rules and the existing container/router architecture. [1][4]

## Objectives
- Make “Change **Video**” enter a stable selection mode that stays visible until a pick or cancel, without disappearing due to view recomposition. [1][2]
- Keep navigation decisions in AddMoveContainer and AddMoveViewModel, not inside leaf views, using a single source of truth for selection state. [1][4]
- Use PhotosPicker in a supported presentation style (inline or modal) and lift asset handling to the view model to avoid lifecycle glitches. [1][3]

## Core decisions
- Introduce a dedicated AddMoveState.selectingVideo and route it at the container layer, replacing conditional rendering inside PreTrim/Trimmer views. [1][4]
- Present AddMoveSelectClipView as a sheet/full‑screen cover or as a routed screen from AddMoveContainer, not inline toggled in the same body tree. [1][2]
- Ensure model ownership: top container initializes @StateObject models; children accept them as @ObservedObject to prevent re‑instantiation and disappearing views. [1][5]

## State machine changes
- File: Views/Arsenal/AddMove/AddMoveViewModel.swift and the AddMoveState definition file. [1]
- Add enum case: selectingVideo(currentAsset: AVAsset?) to represent the active selection UI mode. [1]
- Add intents:
  - func beginChangeVideo() sets state = .selectingVideo(currentAsset: existingAsset). [1]
  - func cancelChangeVideo() returns to .previewing(asset:..., photosIdentifier:...). [1]
  - func didPickVideo(asset: AVAsset, photosIdentifier: String?) transitions to .previewing or .trimming based on current flow. [1]
- Guarantee that rotationQuarterTurns and trimRange remain on the view model and are not reset during selection transitions. [1]

## Container routing
- File: AppCore/AddMoveContainer.swift (or Views/Arsenal/AddMove/AddMoveContainer.swift). [1]
- Switch on AddMoveState and route:
  - .previewing/.trimming/.naming → existing views. [1]
  - .selectingVideo → present AddMoveSelectClipView either:
    - As a fullScreenCover(isPresented:) bound to a derived boolean from state, or. [1][2]
    - As a dedicated branch of the NavigationStack via navigationDestination if the app prefers push. [1][4]
- Keep AddMoveSelectClipView on‑screen until cancelChangeVideo() or didPickVideo(...) is invoked; do not use inline if/else in the same body tree. [1][2]

## PreTrim/Trimmer view changes
- File: Views/Video/Trim/TrimmerView.swift (PreTrimView responsibilities belong here if currently combined). [1]
- Remove conditional rendering that swaps in AddMoveSelectClipView within the same body, and remove onDisappear toggles that auto‑reset selection state. [1][2]
- Replace the “Change Video” button action with addMoveViewModel.beginChangeVideo() to route through the container. [1][4]
- Ensure TrimmerViewModel is injected as @ObservedObject only; its lifecycle is owned by the container via @StateObject. [1][5]

## AddMoveSelectClipView integration
- File: Views/Arsenal/AddMove/AddMoveSelectClipView.swift. [1]
- Implement PhotosPicker with a @State PhotosPickerItem? bound to the view, and delegate result handling to AddMoveViewModel.didPickVideo(...) after resolving to AVAsset/identifier. [1][3]
- Provide a Cancel button that calls addMoveViewModel.cancelChangeVideo() instead of view‑local state resets. [1][4]
- Do not rely on onDisappear to mutate navigation state; all transitions flow through the view model intents. [1][2]

## Model ownership and lifecycle
- File: AppCore/AddMoveContainer.swift. [1]
- Initialize @StateObject var addMoveViewModel and @StateObject var trimmerViewModel at the container level once per flow. [1][5]
- Pass models down via @ObservedObject to all children to avoid multiple instantiations and “StateObject not installed” warnings. [1][5]
- Confirm rotationQuarterTurns and trimRange are stored on TrimmerViewModel/AddMoveViewModel as appropriate, never in local @State that is lost on recomposition. [1][5]

## Photos intake handoff
- File: Managers/Photos/PhotosClient.swift (or existing managers). [1]
- Keep PhotosPicker UI simple and pass the selected PhotosPickerItem to the view model to resolve into a PHAsset/AVAsset off the main thread, following the previously defined PhotosClient/async wrapper pattern. [1][3]
- Ensure selection completion triggers didPickVideo(asset:photosIdentifier:) which advances state and dismisses the sheet/cover at the container level. [1][4]

## Presentation style guidelines
- Prefer sheet/fullScreenCover for selection UX to keep a modal boundary and prevent inline re-render removal; bind isPresented to (state == .selectingVideo). [1][2]
- Alternatively route via NavigationStack(path:) using a state‑driven destination and values that encode the selection screen, then pop on completion. [1][4]
- Do not mix conditional view swaps and onDisappear‑driven state resets in the same render hierarchy for navigation. [1][2]

## Invariants and guardrails
- Views never mutate navigation by toggling local flags; only call AddMoveViewModel intents to change AddMoveState. [1][4]
- The selection UI remains visible until one of: pick succeeds, cancel tapped, or system dismissal; in all cases, container handles the transition. [1][2]
- Container owns model lifetimes; children never create @StateObject for shared models. [1][5]

## Acceptance criteria
- Tapping “Change Video” holds AddMoveSelectClipView on screen until a pick or cancel, with no flicker or immediate disappearance. [1][2]
- State transitions are visible only as AddMoveState changes, not via local flags; telemetry shows no unexpected onDisappear‑driven resets. [1][4]
- No “Accessing StateObject without being installed on a View” warnings across the flow; rotation/trim state persists across recompositions and transitions. [1][5]
- PhotosPicker selection returns to preview/trimmer reliably with the new asset, with navigation handled exclusively by AddMoveContainer. [1][3]
