Short answer: Stop rotating SwiftUI’s VideoPlayer and instead render rotation in AVFoundation by assigning a videoComposition to the AVPlayerItem for previews and to the export session for files, using the same transform math used at export time. This eliminates the black-screen rendering path and guarantees identical orientation between preview and the saved video. [1][2][3][4]

## Root cause hypothesis
- SwiftUI’s VideoPlayer is sensitive to view-tree transforms; applying rotation to VideoPlayer or its container commonly results in black frames during or after orientation/transform changes. [1][5][6]
- Rotating at the SwiftUI layer leaves the AV pipeline unaware of geometry changes; some compositing paths and driver stacks can yield a “playing audio, black video” symptom when the player layer is transformed or its superlayer is rotated. [1][5][7]
- Using AVFoundation’s composition transforms avoids these issues by producing correctly oriented frames before they hit the rendering layer, which also aligns preview and export behavior. [1][2][3]

## Design shift: rotate in composition, not UI
- For previews: create an AVPlayerItem from the trimmed asset and assign an AVMutableVideoComposition that applies preferredTransform plus the user’s quarter-turn rotation and necessary translation, with renderSize swapped for 90°/270°. [1][2][3]
- For exports: reuse the exact same transform builder to set AVAssetExportSession.videoComposition, ensuring the file is baked with the same orientation seen in preview. [1][4][3]
- Remove all SwiftUI .rotationEffect/.transformEffect on any hierarchy that contains VideoPlayer, and keep overlays (controls, chrome) unrotated to prevent accidental GPU path changes that trigger black screens. [1][5][6]

## Spec: common video composition builder
- Inputs: source AVAsset, trimRange (CMTimeRange), rotationQuarterTurns ∈ {0,1,2,3}. [1]
- Algorithm: get the video track and its preferredTransform, compute natural width/height, then compose T · Ruser · Rsrc where Rsrc is preferredTransform, Ruser is quarter-turn rotation, and T is a translation to keep the rotated frame in-bounds, with renderSize swapped for 90°/270°. [1][4][8]
- Output: (composition: AVMutableComposition, videoComposition: AVMutableVideoComposition) for both preview and export, ensuring identical math and renderSize. [1][2][3]

## Transform math (precisely)
- Let the source track be s, with preferredTransform Rsrc and clean-aperture size (ws, hs) before user rotation. [1][4]
- Define quarter-turn rotation $$R(\theta)$$ where $$\theta \in \{0,\frac{\pi}{2},\pi,\frac{3\pi}{2}\}$$ from rotationQuarterTurns. [1][8]
- The applied layer transform is $$T \cdot R(\theta) \cdot R_{src}$$, where T translates the rotated content into the positive quadrant; for 90° clockwise, translate by (hs, 0), and for 270°, translate by (0, ws), given Core Animation’s top-left origin. [1][8][4]
- Set videoComposition.renderSize = (ws, hs) for 0°/180°, or (hs, ws) for 90°/270° to match the rotated output canvas exactly. [1][4][3]

## Trimming and asset intake
- Implement trimming by inserting only trimRange into an AVMutableComposition track, avoiding decode of unneeded segments and minimizing export time and memory. [1][4][9]
- Ensure preview uses the same composition track/timeRange as export, so scrubbing and playback reflect the precise final duration. [1][2][9]
- If the PHAsset yields a non-file-based AVAsset (e.g., composition/streaming), materialize a local file via PhotoKit before building compositions, because AVPlayerItem.videoComposition works only with file-based media. [1][2][10]

## UI integration and state
- State of **rotation**: keep rotationQuarterTurns as the single source of truth across TrimmerView and NameMoveView; derive Angle.degrees only for non-video decorations if desired, but never apply to the video surface. [1]
- State of **trim**: maintain CMTimeRange in the view model and feed to the composition builder for both preview and export. [1]
- Playback view: swap SwiftUI’s VideoPlayer for a PlayerContainer that hosts AVPlayerItem configured with the videoComposition and shows overlays above it without rotating the player view. [1][2]

## Concrete implementation plan
- Create VideoTransformBuilder with an API: build(asset: AVAsset, trim: CMTimeRange, quarterTurns: Int) -> (AVMutableComposition, AVMutableVideoComposition). [1][4][3]
- In TrimmerView and NameMoveView, construct an AVPlayerItem from the returned AVMutableComposition, set playerItem.videoComposition, and assign to a single long-lived AVPlayer to avoid lifecycle glitches that can also trigger black frames. [1][2][11]
- Remove .rotationEffect/.transformEffect from any container hosting VideoPlayer; keep rotations for static thumbnails only if needed, not for live video surfaces. [1][5][6]
- On export, pass the same AVMutableVideoComposition to AVAssetExportSession.videoComposition; choose a preset that supports composition (e.g., HEVC/H.264 High), not Passthrough, because transforms require rendering. [1][4][3]

## Performance and seek tuning
- Expect some seek overhead with a videoComposition; improve UX by setting playerItem.seekingWaitsForVideoCompositionRendering = true during scrubs to align timing with rendered frames, and consider disabling it for coarse seeks to reduce latency. [1][12]
- Keep transforms static and compute once per rotation change; reuse the same videoComposition unless rotation/trim changes. [1][3]
- Continue using SwiftUI for haptics/animations on the rotate button, but do not animate the video layer itself; this preserves 60 fps overlays while the AV pipeline renders frames. [1][2]

## iCloud and file-based guarantee
- When loading via PHImageManager.requestAVAsset, enable networkAccessAllowed and show a progress UI; if the result is not a file-based asset, write the relevant PHAssetResource to a temp file to guarantee videoComposition compatibility. [1][10][2]
- Only attach videoComposition to file-based items; if the asset unexpectedly becomes HLS or non-file, fall back to materializing a file before attaching videoComposition to avoid black/unsupported playback. [1][2][10]

## Validation to prevent regressions
- Preview parity: verify the AVPlayerItem’s presentation size equals the videoComposition.renderSize given the selected rotation, and that the visible orientation matches the export. [1][2][3]
- Output parity: after export, check that the output track’s preferredTransform is identity when baking rotation, and the duration ≈ trimRange.duration within a frame. [1][4][13]
- No-UI-transform rule: assert at runtime that VideoPlayer is not under any non-identity CGAffineTransform/rotationEffect to prevent reintroducing black screens. [1][5][6]

## Fallback: custom player layer (only if needed)
- If a specific device/OS still shows black with SwiftUI’s VideoPlayer, render via a UIViewRepresentable that manages an AVPlayerLayer, sets its frame in layoutSubviews, and avoids applying 3D transforms to the player layer itself. [1][14][7]
- Even with a custom layer, prefer composition-based rotation rather than CATransform3D on AVPlayerLayer to keep the video rendering path stable and consistent with export. [1][2][3]

## Migration checklist for the agent
- Remove rotationEffect/transformEffect from CustomVideoPlayerView and any parent containing VideoPlayer. [1][5][6]
- Implement VideoTransformBuilder and replace current preview rotation with playerItem.videoComposition from the builder. [1][3][2]
- Ensure export reuses the same builder and math, not a separate code path. [1][4][3]
- Gate videoComposition usage on file-based assets; materialize PHAsset to a temp file if necessary. [1][2][10]
- Add assertions/telemetry: record rotationQuarterTurns, renderSize, and whether the preview/export transforms matched; flag any black-frame incidents. [1][2][13]

## Debug checklist
- Reproduce black screen with UI transforms applied, then confirm it disappears when using playerItem.videoComposition with no SwiftUI rotation. [1][5][2]
- Verify 90°/270° swaps: renderSize flips and translation keeps the image in bounds, using T · R(θ) · Rsrc; check edges for cropping. [1][8][3]
- Validate that seeking remains responsive with seekingWaitsForVideoCompositionRendering tuned, and measure worst‑case seek time on long 4K assets. [1][12][2]

This plan replaces fragile UI transforms with AVFoundation-native rotation at playback and export time, unifying math and eliminating the black preview path while preserving a simple UX focused on choosing a video, setting **rotation**, and selecting the **trim** range. [1][2][3][4]
