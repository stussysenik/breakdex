## Analysis from First Principles: State-Driven vs. View-Driven Logic

The root cause of these issues is a conflict between two design patterns:

1.  **State-Driven Architecture (The Goal):** Your `AddMoveUnifiedState` is designed to be the single source of truth. The flow state (`.naming`, `.trimming`, etc.) should dictate all behavior, including whether a video should play. The critical fix comment in `transitionTo(.naming)` shows this is the intended approach: `// 🎯 CRITICAL FIX: State-driven playback control`.

2.  **View-Lifecycle-Driven Behavior (The Problem):** The `CustomVideoPlayerView`'s `.onAppear` modifier is a view lifecycle event. By having it automatically trigger playback, you create behavior that is independent of the application's overall state. The view decides to play simply because it appeared on screen, regardless of whether the current flow state (`.naming`) dictates it should be paused.

**The primary architectural fix is to ensure all actions are exclusively state-driven.** A view should only render the current state and report user interactions back to the state manager; it should not contain its own behavioral logic that can conflict with the state.
