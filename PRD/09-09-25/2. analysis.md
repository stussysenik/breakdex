## The Fundamental Problem

Your architecture has a **reactive feedback loop** where:

```
State Change → View Construction → Async Operations → State Changes → View Updates → More State Changes → Infinite Loop
```

The core issue is **timing**: async operations that modify state are running **during** the view construction phase, which SwiftUI explicitly forbids.

## What Needs Fundamental Change

### **1. Decouple State Changes from View Construction**

**Current Problem**: `.task` modifiers run during view construction and modify `@Published` properties, triggering view updates during construction.

**Required Change**: Move all async initialization logic **after** view construction is complete. Use `.onAppear` instead of `.task` for operations that modify state.

### **2. Break the Reactive Chain**

**Current Problem**: The architecture creates a cycle where state changes trigger view construction which triggers more state changes.

**Required Change**: Implement a **coordinator pattern** or **navigation controller** that manages navigation separately from the reactive state system.

### **3. Separate UI State from Navigation State**

**Current Problem**: `AddMoveViewModel.state` serves double duty - it both manages the UI state AND controls navigation.

**Required Change**: 
- Keep UI state in view models
- Move navigation logic to a separate coordinator/router that doesn't trigger reactive updates during construction

### **4. Async Initialization Strategy**

**Current Problem**: Views assume they can run async operations during construction.

**Required Change**: Use a **two-phase initialization**:
1. **Phase 1**: View construction (no state changes)
2. **Phase 2**: Post-construction initialization (state changes allowed)

### **5. Error Handling Architecture**

**Current Problem**: Errors during async operations trigger state changes during view construction.

**Required Change**: Implement **deferred error handling** - collect errors during initialization and handle them after the view is stable.
