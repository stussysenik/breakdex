The root cause is that the rotation logic in `TrimmerViewModel` is triggered **before** the view model has had a chance to asynchronously load the video's duration. This sends an invalid, zero-duration time range (`0.0-0.0s`) to `AVFoundation`, which correctly rejects it.

### \#\# Deep Analysis: The Initialization Race Condition

#### ✅ What's Working Perfectly

The logs from your successful 90° rotation are the most important piece of evidence. They prove that the new single-source-of-truth architecture is sound:

  * **Rotation Triggers Transformation:** When the user acts, the system correctly calls the asset transformation pipeline: `🎬 TRIMMER_VM: Applying asset-level rotation: 90°`.
  * **`VideoTransformBuilder` is Flawless:** The builder receives valid data and creates a correctly composed and rotated asset with the right dimensions (`🎬 VideoTransformBuilder: Manually set render size to (902.0, 1604.0)`).
  * **Player Hot-Swap Succeeds:** The `UnifiedVideoPlayerViewModel` successfully replaces its current item with the newly transformed one, making the preview update: `🎬 TRIMMER_VM: ✅ Asset rotation applied successfully.`.

#### ❌ What's Still Wrong

The failure happens during the initial setup, not during user interaction. Here is the step-by-step breakdown of the race condition:

1.  **Initialization:** `FeatureRichTrimmerView` initializes `TrimmerViewModel`. During this `init`, `rotationQuarterTurns` is set to its initial value (0).
2.  **`didSet` Fires Prematurely:** This assignment immediately triggers the `didSet` observer on `rotationQuarterTurns` in `TrimmerViewModel`.
3.  **Invalid State:** At this exact moment, `startTime` and `endTime` are still their default `.zero` values because the `setupAsync()` method—which loads the asset's duration—has not yet been called from the view's `.task` modifier.
4.  **`AVFoundation` Error:** The `applyRotationToPlayerAsset()` function is called with a `trimRange` of `0.0-0.0s`. `AVFoundation` cannot insert a video track with zero duration, resulting in the error: `❌ Failed to insert video track 1: Error Domain=AVFoundationErrorDomain Code=-11800`.

-----

### \#\# The Solution: Robust Initialization and State Gating

The fix is simple and targeted: we must prevent the transformation logic from running until the `TrimmerViewModel` is fully initialized and in a valid state.

#### **Step 1: Introduce an Initialization State Flag**

We will add a flag to track whether the asynchronous setup is complete.

  * **File to Modify:** `TrimmerViewModel.swift`
  * **Action:** Add a new private property.

<!-- end list -->

```swift
@Observable
@MainActor
public final class TrimmerViewModel {
    // ... existing properties
    private var isSetupComplete = false // 👈 ADD THIS LINE
    // ...
```

-----

#### **Step 2: Gate the Rotation Logic**

The `didSet` observer for `rotationQuarterTurns` will now check this flag before executing.

  * **File to Modify:** `TrimmerViewModel.swift`
  * **Action:** Add a guard statement to the `didSet` block.

<!-- end list -->

```swift
public var rotationQuarterTurns: Int = 0 {
    didSet {
        // 🛑 PREVENT running during initialization
        guard isSetupComplete else { return } // 👈 ADD THIS GUARD

        Task {
            await applyRotationToPlayerAsset()
        }
    }
}
```

-----

#### **Step 3: "Arm" the Logic After Setup**

Once `setupAsync()` successfully completes, we'll set the flag to `true`, allowing future rotation changes to trigger the transformation.

  * **File to Modify:** `TrimmerViewModel.swift`
  * **Action:** Set the flag at the end of `setupAsync()`.

<!-- end list -->

```swift
public func setupAsync() async throws {
    videoDuration = try await asset.load(.duration)
    // ... existing setup logic
    endTime = videoDuration

    // ✅ ARM the rotation logic now that the model is in a valid state.
    isSetupComplete = true // 👈 ADD THIS LINE
}
```

-----

#### **Step 4 (Recommended): Add a Defensive Guard**

As a final layer of defense, we can add a check inside `applyRotationToPlayerAsset()` to ensure it never runs with an invalid time range. This makes the function itself more robust.

  * **File to Modify:** `TrimmerViewModel.swift`
  * **Action:** Add a guard to check for a non-zero duration.

<!-- end list -->

```swift
private func applyRotationToPlayerAsset() async {
    // ... logger
    
    // 🛡️ DEFENSIVE GUARD: Ensure the time range is valid before processing.
    guard (self.endTime - self.startTime).seconds > 0 else {
        logger.warning("🎬 TRIMMER_VM: Skipping asset rotation due to invalid (zero-duration) time range.")
        return
    }

    do {
        // ... existing transformation logic
    } catch {
        // ... existing error handling
    }
}
```

This solution directly resolves the race condition by enforcing a correct initialization order. It makes the `TrimmerViewModel` more robust and ensures the powerful asset transformation pipeline you've built only operates on valid data, leading to a stable and reliable user experience.
