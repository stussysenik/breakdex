The exact issue is that the TrimmerView kicks off async initialization via a task that mutates @Published properties and, on failure, writes to the parent AddMoveViewModel.state during a view update, which SwiftUI forbids and flags as “Publishing changes from within view updates is not allowed.” [1][2][3] This cross-layer mutation during construction causes the container to rebuild immediately, re-running the same task and repeating the cycle into an infinite loop. [1][2]

## What triggers it
- Tapping “Trim Video” changes AddMoveViewModel.state to .trimming, causing the container to rebuild and construct TrimmerView, whose task then runs setupAsync and updatePreview and updates TrimmerViewModel’s @Published state. [1][2]
- If initialization throws, the error handler sets addMoveViewModel.state = .error from inside the child’s lifecycle, which is precisely the mutation timing SwiftUI warns about. [1][2]

## Why SwiftUI warns
- SwiftUI prohibits publishing observable changes while it is reconciling a view update; mutating @Published during construction or inside an in-flight update yields the purple “Publishing changes from within view updates” runtime message. [2][3]
- Lifecycle hooks like .task or onAppear can run at times that coincide with render/update passes; if those code paths publish model changes, the runtime warning appears. [4][2]

## Why it loops
- The child view’s task mutates its own @Published, prompting a view update, and on error also mutates the parent’s state, which forces the container to rebuild and recreate TrimmerView. [1][2]
- Re-creation re-triggers the task, the same failure path executes, parent state is mutated again, and the process repeats indefinitely. [1][2]

## The concrete hot spots
- The TrimmerView task runs setupAsync and updatePreview that update observable properties in TrimmerViewModel and, in the catch path, assigns AddMoveViewModel.state = .error, all while the view tree is still stabilizing. [1][2]
- The container’s reactive “currentView” switching on AddMoveViewModel.state ensures any parent-state write immediately reconstructs the subtree, making re-entry trivial. [1][2]

## Minimal reproduction shape
- Any handler that publishes to an ObservableObject while SwiftUI is processing UI updates (e.g., onKeyPress or a task body) will reproduce the same warning, as documented in community examples. [3][5]
- Similarly, updates triggered by third-party components or bindings during a render can surface the same runtime message even if the UI “seems to work.” [6][7]

## What it’s not
- This is not a NavigationStack bug; it’s a timing and layering issue: publishing parent navigation/state changes from a child during render is the root cause. [2][1]
- A coordinator helps by decoupling navigation, but the fundamental violation is mutation during view updates, which must be avoided regardless of the navigation mechanism. [8][2]

## One-line fix direction
- Stop mutating parent state from TrimmerView’s initial task; restrict the task to local view-model updates and defer any cross-layer navigation/error escalation until after a stable frame via a coordinator or a scheduled post-render action. [1][2]
