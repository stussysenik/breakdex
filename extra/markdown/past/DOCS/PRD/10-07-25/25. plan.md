The problem is a **race condition** between the video loading service completing its work and the main state machine being ready for the next step. The completion notification arrives *before* the loaded video asset is assigned to your `AddMoveUnifiedState`, causing the transition to fail.

-----

## 🔍 In-Depth Analysis of the Race Condition

Here’s the step-by-step breakdown of what's happening, which is confirmed by your logs:

1.  **Early Notification:** The `modernVideoLoadingService` finishes loading the video. It immediately sends a `.completed` status update through a Combine publisher, which is picked up by `VideoProgressMonitoringService`.

2.  **Premature Trigger:** Your `AddMoveUnifiedState` has a subscriber (`setupPhaseChangeCompletionHandler`) that listens for phase changes in the `unifiedProgressEngine`. It sees the `.completed` phase and immediately calls `handleEngineCompletion()`.

3.  **Awaiting Result:** At the same time, the original function that started the process, `loadVideoAssetWithCancellation`, is still `await`ing the result from `modernVideoLoadingService.loadVideo(from: item)`. The code that actually sets `self.videoAsset` and `self.photosIdentifier` has **not run yet**.

4.  **Dependency Check Fails:** The `handleEngineCompletion()` function tries to transition to the trimming state. Its dependency check (`guard videoAsset != nil, photosIdentifier != nil else ...`) fails because `videoAsset` is still `nil`.

5.  **First Error State:** The transition fails, and the `flowState` is correctly set to `.error(message: "Missing video dependencies for transition...")`. Your log confirms this with the `PERFORMANCE_TRANSITION_FAILED` message.

6.  **State Corruption:** A moment later, other completion notifications from the loading service arrive. The `handleVideoLoadingProgress` function receives a `.completed` update but sees the `flowState` is now `.error`, not the expected `.loadingVideo`. It correctly identifies this as a state mismatch and triggers the second, final error: `"Video loading state corrupted"`.

-----

## 💡 The Solution: Centralizing the Completion Trigger

To fix this, we must ensure the completion logic is only triggered *after* the loaded video asset has been successfully assigned to `AddMoveUnifiedState`. The `async` function that receives the result is the only place that can guarantee this.

The solution involves two small but critical changes in **AddMoveUnifiedState.swift**.

### 1\. Disable the Premature Completion Trigger

We need to stop the `setupPhaseChangeCompletionHandler` from prematurely acting on the `.completed` phase. It can still handle errors, but the successful completion trigger must move.

```swift
// In AddMoveUnifiedState.swift

@MainActor
private func handleEnginePhaseChange(to phase: UnifiedProgressEngine.LoadingPhase) async {
    let phaseChangeId = UUID().uuidString.prefix(8)
    logger.info("🎬 AddMoveUnifiedState: 🔄 PHASE_CHANGE [\(phaseChangeId)]: \(phase.displayName)")

    guard case .loadingVideo = flowState else {
        logger.debug("🎬 AddMoveUnifiedState: 📊 PHASE_CHANGE [\(phaseChangeId)]: Ignored - not in loadingVideo state")
        return
    }

    guard !isCompletingLoad else {
        logger.debug("🎬 AddMoveUnifiedState: 📊 PHASE_CHANGE [\(phaseChangeId)]: Ignored - already completing load")
        return
    }
    
    // 🛑 FIX: DO NOT handle completion here. This is the source of the race condition.
    // The completion will now be triggered manually from `loadVideoAssetWithCancellation`
    // after the video asset has been successfully assigned.
    /*
    if phase == .completed {
        logger.info("🎬 AddMoveUnifiedState: 🏆 COMPLETION_MORPHISM: Terminal phase .completed detected")
        await handleEngineCompletion(phaseChangeId: String(phaseChangeId))
    }
    */
    
    // We can still handle errors detected by the engine.
    if phase == .error {
        logger.warning("🎬 AddMoveUnifiedState: ❌ COMPLETION_MORPHISM: Error phase detected")
        await handleEngineError(phaseChangeId: String(phaseChangeId))
    }
}
```

### 2\. Trigger Completion from the Correct Location

Now, we will manually trigger the completion logic inside `loadVideoAssetWithCancellation` right after the `videoAsset` and `photosIdentifier` are set. This guarantees the dependencies are available when the transition to trimming begins.

```swift
// In AddMoveUnifiedState.swift

@MainActor
private func loadVideoAssetWithCancellation(from item: PhotosPickerItem, correlationId: String) async throws {
    logger.info("🎯 RESILIENT_LOADING: 🎬 Delegating loading and all phase management to modernVideoLoadingService [\(correlationId)]")

    let result = try await modernVideoLoadingService.loadVideo(from: item)

    logger.info("🎯 RESILIENT_LOADING: ✅ modernVideoLoadingService completed its full sequence. Setting final asset properties. [\(correlationId)]")

    // Assign the final result
    self.videoAsset = result.asset
    self.photosIdentifier = result.photosIdentifier

    // Forward the file size information for the UI
    if let fileSize = result.fileSize, fileSize > 0 {
        let formattedSize = ByteCountFormatter.string(fromByteCount: fileSize, countStyle: .file)
        await updateEstimatedFileSize(fileSize, formattedSize: formattedSize)
    }

    // ✅ FIX: Manually trigger the completion handler HERE.
    // This is the only point where we can be 100% certain that the video asset
    // is assigned and we are ready to transition to the trimming state.
    logger.info("🎯 RESILIENT_LOADING: 🚀 Triggering atomic completion transition now that asset is assigned. [\(correlationId)]")
    await handleEngineCompletion(phaseChangeId: "asset_load_complete_\(correlationId)")
}
```

By making these changes, you tie the completion event directly to the availability of the loaded asset, deterministically eliminating the race condition and ensuring the state machine transitions correctly every time.
