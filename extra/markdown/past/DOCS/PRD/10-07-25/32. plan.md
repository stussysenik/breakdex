The root cause is a **race condition** within `FeatureRichTrimmerView.swift`. An `.onChange(of: unifiedState.photosIdentifier)` modifier, intended for the initial video load, is incorrectly firing during the "Change Video" workflow. It tries to set up a new trimmer *while the main state machine is still tearing down the old video*, leading to a crash in a background task that stalls the UI.

Here’s a detailed breakdown of the problem and the precise solution.

-----

## Step-by-Step Analysis of the Bug

1.  **The Trigger:** You are in the `.trimming` state. You tap the "Change Video" button in `FeatureRichTrimmerView`.

2.  **Correct Action:** The view's `.photosPicker` modifier correctly presents the video selection sheet. You pick a new video. The `.onChange(of: tempVideoSelection)` modifier correctly calls `unifiedState.didSelectVideo(customItem)`. This is the single, correct entry point for any new video load.

3.  **The State Machine Begins its Work:** Inside `AddMoveUnifiedState.swift`, the `didSelectVideo` function starts its robust, atomic process:

      * It cancels any previous loading tasks.
      * It calls `prepareForNewVideoSelection()`, which is a comprehensive reset function. This function correctly tears down the *old* `TrimmerViewModel` and `UnifiedVideoPlayerViewModel`, clears the old `videoAsset` and `photosIdentifier`, and forces the `flowState` back to `.ready`.
      * After the reset, it transitions the `flowState` to `.loadingVideo` and begins loading the *new* video's data.

4.  **The Interference (Root Cause):** The `mainContent` view inside `FeatureRichTrimmerView.swift` has this modifier:

    ```swift
    .onChange(of: unifiedState.photosIdentifier) { oldValue, newValue in
        // ...
        self.viewModel = nil
        self.lazyInitializationAttempted = false
        Task {
            await setupTrimmerViewModel()
        }
    }
    ```

    This modifier fires as soon as `photosIdentifier` changes. During the "Change Video" flow, `photosIdentifier` changes twice in quick succession: first to `nil` (during the reset) and then to the new video's ID (during the load).

5.  **The Race Condition:** When this `onChange` fires, it immediately launches a *new, concurrent `Task`* to run `setupTrimmerViewModel()`. However, the main `didSelectVideo` task is still in the middle of its process. At this exact moment, `unifiedState.currentPlayerViewModel` is `nil` because it was just torn down by the reset. The `setupTrimmerViewModel` function then fails because its dependency (`currentPlayerViewModel`) is missing, throwing a `TrimmerSetupError.missingPlayerViewModel` error. This background failure halts the process, and the UI remains stuck at the "Initializing..." state.

-----

## The Solution

The solution is to recognize that `FeatureRichTrimmerView` should not be trying to orchestrate the loading process. Its only job is to react to the `flowState` provided by the `AddMoveUnifiedState` (the single source of truth). The existing `.onAppear` modifier on the `mainContent` is already correctly handling the lazy initialization of the `TrimmerViewModel` at the appropriate time.

**You must remove the interfering `.onChange(of: unifiedState.photosIdentifier)` modifier.**

### File to Edit: `FeatureRichTrimmerView.swift`

Find the `mainContent` computed property in `FeatureRichTrimmerView.swift` and delete the entire `.onChange(of: unifiedState.photosIdentifier)` block.

#### Before (Incorrect Code):

```swift
// FeatureRichTrimmerView.swift
```

#### After (Corrected Code):

```swift
// FeatureRichTrimmerView.swift

private var mainContent: some View {
    // ... (Group with if/else logic)
    .onAppear {
        // This onAppear is now the ONLY trigger for setting up the view model.
        // It runs correctly on the initial appearance and will run again
        // after the "Change Video" flow completes and the view is ready
        // to show the trimmer for the new video.
        diagnosticLogger.logInfo("🎯 UNIFIED_LAZY_LOADING: mainContent appeared - triggering unified lazy ViewModel initialization")
        Task {
            await setupTrimmerViewModel()
        }
    }
    // The .onChange modifier has been completely removed.
}
```

### Why This Fix Works

1.  **Eliminates the Race Condition:** By removing the `onChange` modifier, we eliminate the rogue `setupTrimmerViewModel()` task that was interfering with the main loading workflow.
2.  **Restores Sequential Logic:** The app now follows a clean, predictable sequence:
      * User selects a new video.
      * `didSelectVideo` in `AddMoveUnifiedState` takes full control, resets everything, and starts loading.
      * The UI simply shows a loading state because `viewModel` is `nil`.
      * `AddMoveUnifiedState` finishes loading and transitions its `flowState` to `.trimming`.
      * SwiftUI re-renders `FeatureRichTrimmerView`, the `.onAppear` for `mainContent` fires, and *now*, at the correct time, `setupTrimmerViewModel()` runs with all its dependencies (like `currentPlayerViewModel`) correctly in place.
3.  **Reinforces Single Source of Truth:** This change enforces the correct architectural pattern. `AddMoveUnifiedState` is the state machine that *orchestrates* the workflow. The `View`'s job is to *react* to that state, not to manage its own complex, concurrent logic.
