## 1\. Categorical System Analysis: The Flawed Isomorphism

To understand the failure, we model the system using category theory.

  * **Objects (Data Structures & Components):**

      * `VideoAsset`: Contains the raw video data, including its intrinsic rotation metadata (an object in the space of integers $Z_4 = \{0, 1, 2, 3\}$).
      * `TrimmerViewModel`: The state model, which holds two distinct rotation objects: `assetIntrinsicRotationTurns` and `userAppliedRotationTurns`.
      * `FeatureRichTrimmerView`: The UI component, which should be an **isomorphism** (a faithful, structure-preserving representation) of the `TrimmerViewModel`.

  * **Morphisms (Functions & Data Flows):**

      * `loadVideo()`: A morphism that maps a `VideoAsset` to a `TrimmerViewModel`, correctly extracting the intrinsic rotation.
      * `init()`: The initializer for `FeatureRichTrimmerView`, a morphism mapping the `TrimmerViewModel` state to the `View` state.
      * `rotateButton()`: A user interaction morphism that transforms the `userAppliedRotationTurns` object within the `TrimmerViewModel`.

### The Bug: A Non-Commutative Diagram

The system fails because the `init()` morphism is flawed. It creates a "buggy isomorphism" where the view does not faithfully represent the model's state. This leads to a non-commutative diagram, meaning the final state of the system is inconsistent.

**Ideal Flow (Commutative Diagram):**

1.  **`loadVideo()`**: `VideoAsset(intrinsic=1)` → `TrimmerViewModel(intrinsic=1, user=0)`
2.  **`init()`**: `TrimmerViewModel` → `FeatureRichTrimmerView(displayRotation=90°, userControl=0°)`
3.  **Final State:** The video preview is rotated 90°, and the user's control correctly shows 0°. The system is consistent.

**Actual Flow (Non-Commutative Diagram):**

1.  **`loadVideo()`**: `VideoAsset(intrinsic=1)` → `TrimmerViewModel(intrinsic=1, user=0)`
2.  **`init()` (Flawed)**: `TrimmerViewModel` → `FeatureRichTrimmerView(displayRotation=90°, userControl implicitly thinks it's 90°)`
3.  **Final State:** The video preview is rotated 90°, but the UI state is derived from the *total* rotation, creating an inconsistent user experience. The user did not apply this rotation, but the UI state implies they did.

This log entry shows the view's `initial_rotation_degrees` is being set to `90.0` because it's reading `total_rotation="1"`, directly violating the required separation of concerns.

## 2\. Root Cause Analysis: Tracing the Morphism Failure

The failure chain is clear: the `loadVideo()` morphism correctly populates the `TrimmerViewModel`, but the `FeatureRichTrimmerView.init()` morphism misinterprets that state.

The exact failure point is in the initializer of `FeatureRichTrimmerView.swift`.

**File:** `FeatureRichTrimmerView.swift`

**Problematic Code:**

```swift
init(unifiedState: AddMoveUnifiedState, viewModel: TrimmerViewModel) {
    self.unifiedState = unifiedState
    self.viewModel = viewModel

    // ❌ FLAWED MORPHISM: This conflates intrinsic and user rotation.
    // It uses the SUM of both to set the initial visual state.
    let initialRotationDegrees = Double(viewModel.totalRotationQuarterTurns * 90)
    self._previewRotationDegrees = State(initialValue: initialRotationDegrees)
    // ...
}
```

This code uses `viewModel.totalRotationQuarterTurns`, which is a computed property defined in `TrimmerViewModel.swift` as `(assetIntrinsicRotationTurns + userAppliedRotationTurns) % 4`.

On a fresh load, `assetIntrinsicRotationTurns` is correctly set to `1` (for a 90° video) and `userAppliedRotationTurns` is `0`. The sum is `1`, so `initialRotationDegrees` becomes 90°. This correctly orients the video preview, but it establishes the wrong baseline for all subsequent user interactions and breaks the intended user experience.

## Specification: Isomorphic Video Rotation Initialization

### 1\. "What" & "Why": Goals and Rationale

#### 1.1. Overview

The video trimmer component currently conflates a video's **intrinsic (metadata) rotation** with **user-applied rotation**. This creates a flawed user experience where a video with pre-existing rotation (e.g., 90°) appears in the trimmer as if the user has already applied a 90° rotation. This violates the WYSIWYG principle and confuses the user's mental model.

#### 1.2. 🎯 Goal

To refactor the trimmer's initialization logic to achieve a clear **separation of concerns**. The system must display the video with its intrinsic rotation while ensuring all user-facing rotation controls start from a neutral 0° state. The final saved asset must be a composite of both intrinsic and user-applied rotations.

#### 1.3. 👑 Rationale (The "Why")

The current implementation erodes user trust and undermines the precision required by the app's target persona. A flawed WYSIWYG experience means the user cannot be certain that their final saved move will match their intent. This fix is critical for ensuring data integrity and providing a reliable, professional-grade tool.

#### 1.4. User Persona & Journey

  * **Persona**: "The Athlete" — Demands a frictionless, precise, and reliable tool to catalog training footage. They value accuracy and have zero tolerance for software that misrepresents their input or data.
  * **Current Flawed Journey**:
    1.  The Athlete selects a video shot in portrait mode (90° intrinsic rotation).
    2.  The trimmer loads, and the video preview correctly appears rotated at 90°.
    3.  However, the rotation control UI *also* shows "90°", implying the user has already performed an action.
    4.  The Athlete is now confused. To get back to the original orientation, they must rotate three more times, which is counter-intuitive.
  * **Target Journey**:
    1.  The Athlete selects the same 90° video.
    2.  The trimmer loads, and the video preview correctly appears rotated at 90°.
    3.  The rotation control UI shows "0°", correctly indicating the user has not yet applied any changes.
    4.  The Athlete can now apply intentional rotations, confident that their actions are additive to the video's original state.

#### 1.5. Non-Goals

  * This spec does **not** cover refactoring the final video export pipeline. The current export logic, which combines intrinsic and user rotations, is correct and will be preserved.
  * This spec does **not** introduce any changes to the UI design, only the state initialization logic.
  * This spec does **not** address any other part of the `Add Move` flow, such as trimming or naming.
