#### Flaw \#1: The UI's Broken Isomorphism

The trimmer UI incorrectly displays the video's total rotation (`intrinsic` + `user`) in the user control button, instead of showing only the rotation the user has applied.

  * **Ideal Flow (Correct Isomorphism):**
    1.  **Model State:** `TrimmerViewModel` loads a 90° video: `(intrinsic=1, user=0)`.
    2.  **View Initialization:** `FeatureRichTrimmerView` initializes. The video preview is rotated 90° (correctly reflecting the total), but the user control button displays "0°" (correctly reflecting the user's action).
  * **Actual Flow (Buggy Isomorphism):**
    1.  **Model State:** `TrimmerViewModel` loads a 90° video: `(intrinsic=1, user=0)`.
    2.  **View Initialization:** `FeatureRichTrimmerView` initializes. The video preview is rotated 90°, but the user control button incorrectly displays "90°".

This bug is located in the `controlSection` of **`FeatureRichTrimmerView.swift`**, where the button's text is bound to the wrong property.

#### Flaw \#2: The Export's Non-Commutative Diagram (Double Rotation)

The video export process applies the intrinsic rotation twice, leading to incorrect cropping and black screens. This happens because the `VideoTransformBuilder` receives the *total desired rotation* but then incorrectly combines it with the asset's original `preferredTransform`.

  * **Let:**
      * `R_intrinsic` = The intrinsic rotation (from `preferredTransform`).
      * `R_user` = The user-applied rotation.
      * `R_total` = The final desired rotation (`R_intrinsic + R_user`).
  * **Ideal Flow (Commutative):** The builder receives `R_total` and applies exactly that rotation to a raw, un-rotated video frame.
  * **Actual Flow (Non-Commutative):**
    1.  The `TrimmerViewModel` correctly calculates `R_total`.
    2.  It sends `R_total` to `VideoTransformBuilder`.
    3.  `VideoTransformBuilder` creates a transform for `R_total` but then **also** applies the asset's original `preferredTransform` (`R_intrinsic`).
    4.  **Final applied transform = `R_intrinsic * R_total` = `R_intrinsic * (R_intrinsic + R_user)`**. This is a mathematical error that results in a double application of the intrinsic rotation.

This critical bug is located in the `build()` method of **`VideoTransformBuilder.swift`**.

#### Part 2: Fix the Export Double Rotation (Flaw \#2)

The goal is to ensure the `VideoTransformBuilder` applies the exact total rotation it is given, without incorrectly combining it with the asset's original transform.

**File**: `VideoTransformBuilder.swift`
**Location**: `build()` method.

```swift

// 🎯 CRITICAL FIX: Apply transforms in correct mathematical order
// For AVFoundation: rotation first, then translation

// --- BEFORE (INCORRECT) ---
// This line applies the intrinsic rotation a second time, causing the bug.

layerInstruction.setTransform(transform, at: .zero)
```

**Result**: Removing this single line corrects the mathematical error. ## Specification: Isomorphic Video Rotation Initialization

  * **Status**: `Approved`
  * **Date**: 2025-10-03
  * **Context**: Addresses bug `FEAT-2025-ROTATION-ISOMORPHISM` where a video's intrinsic rotation is incorrectly reflected as a user-applied rotation on initial load, violating the WYSIWYG principle and causing export failures. The attached images show an upside-down video in the trimmer (IMG\_2296 2.jpg) and in the final preview (IMG\_2298.jpg), which is a direct result of this miscalculation.

### 1\. "What" & "Why": Goals and Rationale

#### 1.1. Overview

The video trimmer component currently conflates a video's **intrinsic (metadata) rotation** with **user-applied rotation**. This creates a flawed user experience where a video with pre-existing rotation (e.g., 90°) appears in the trimmer as if the user has already applied a 90° rotation. This violates the WYSIWYG principle, confuses the user's mental model, and leads to incorrect final exports where the video frame is rotated but the pixel data is not, resulting in black screens or severe cropping.

#### 1.2. 🎯 Goal

To refactor the system's initialization and export logic to achieve a clear **separation of concerns** between intrinsic and user-applied rotation. The system must:

1.  Display the video preview with its **intrinsic rotation** correctly applied from the first frame.
2.  Ensure all user-facing rotation controls start from a neutral **0° state**.
3.  Ensure the final exported video is a mathematically correct composite of **both** intrinsic and user-applied rotations, preserving all pixel data.

#### 1.3. 👑 Rationale (The "Why")

The current implementation erodes user trust and undermines the precision required by the app's target persona. A flawed WYSIWYG experience means the user cannot be certain that their final saved move will match their intent. This fix is critical for ensuring data integrity and providing a reliable, professional-grade tool.

#### 1.4. User Persona & Journey

  * **Persona**: "The Athlete" — Demands a frictionless, precise, and reliable tool to catalog training footage. They have zero tolerance for software that misrepresents their input or data.
  * **Current Flawed Journey**:
    1.  The Athlete selects a video shot in portrait mode (90° intrinsic rotation).
    2.  The trimmer loads, and the video preview correctly appears rotated at 90°.
    3.  However, the rotation control UI *also* shows "90°", implying the user has already performed an action they have not.
    4.  The Athlete is now confused. If they apply another rotation, the total becomes 180°, and the export fails due to a double-rotation bug in the transform builder.
  * **Target Journey**:
    1.  The Athlete selects the same 90° video.
    2.  The trimmer loads, and the video preview correctly appears rotated at 90°.
    3.  The rotation control UI shows "0°", correctly indicating the user has not yet applied any changes.
    4.  The Athlete applies an intentional 90° rotation. The UI now shows "90°" and the preview shows 180°.
    5.  The final saved asset is physically rotated 180° with no data loss.

#### 1.5. Non-Goals

  * This spec does **not** cover refactoring the logic within `TrimmerViewModel` that calculates the `totalRotationQuarterTurns`; that logic is correct.
  * This spec does **not** introduce any changes to UI design, only the state initialization logic and transform composition.
