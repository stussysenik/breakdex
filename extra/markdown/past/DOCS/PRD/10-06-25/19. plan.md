* **Version:** 2.0

### **1. Overview (What & Why)**

#### **1.1. Goal**
To refine the "Change Video" user journey into a seamless, in-context modal experience, eliminating the current jarring navigation that takes the user out of their workflow.

#### **1.2. Background & Problem**
The previous critical issue of the video loading process stalling on the second attempt has been **successfully resolved**. The latest logs confirm that an atomic state reset now correctly triggers before a new loading sequence begins.

However, this fix has introduced a suboptimal user experience. The state reset causes the entire view hierarchy to revert to its initial state, effectively "exiting" the user from the trimmer/naming screen back to the starting "Select a Clip" page. This is functionally correct but feels like a bug to the user, breaking their workflow momentum.

#### **1.3. User Persona & Journey**
* **Persona: "The Athlete"**
    * **Needs:** A fluid, precise, and uninterrupted workflow. The tool must feel like an extension of their intent.
    * **Expectations:** Actions should occur within the current context. Being unexpectedly navigated away from a task feels like a system failure and erodes trust.

* **User Story**
    * "As an Athlete, when I decide to change my selected video from the trimming or naming screen, I want to pick a new one from a modal sheet **without leaving my current view**, so that I can maintain my workflow's context and immediately continue my task with the new clip."

#### **1.4. Goals**
* Present the `PhotosPicker` as a modal sheet over the currently active view (`FeatureRichTrimmerView` or `NameMoveViewUnified`).
* Ensure that cancelling the modal `PhotosPicker` returns the user to their previous state with no loss of data or context.
* Upon selecting a new video, the existing `LoadingOverlayView` should appear modally, providing the same transparent, deterministic progress feedback.
* Upon successful loading, the `Trimming` view must be seamlessly updated with the new video's data.

#### **1.5. Non-Goals**
* Re-architecting the state reset logic. The existing implementation is correct and robust.
* Changing the appearance of the `LoadingOverlayView` or the native `PhotosPicker`.

### **2. Verifiable Requirements**

#### **2.1. Functional Requirements**
* **FR1: Contextual Picker Presentation:** The "Change Video" button must trigger a modal `PhotosPicker` presentation without altering the underlying view hierarchy.
* **FR2: Graceful Cancellation:** If the user cancels the `PhotosPicker`, the application state must remain unchanged, and the user must be returned to the exact state they were in before tapping the button.
* **FR3: Atomic Reset on Selection:** The atomic state reset must be tied directly to the successful selection of a *new* item from the picker, not the presentation of the picker itself.
* **FR4: Seamless Data Refresh:** After the new video is loaded, the `Trimming` view must be automatically refreshed to display the new video asset, duration, and other relevant metadata.

#### **2.2. Acceptance Criteria**
* **AC1.1:** Tapping the "Change Video" button solely toggles a local `@State` variable to `true`, which is bound to the `.photosPicker` view modifier's `isPresented` parameter. The UI does not navigate away.
* **AC2.1:** When the `PhotosPicker` is presented and then dismissed without a selection, the `onChange(of: selectedItem)` modifier is not triggered, and no state reset occurs. The UI remains on the trimmer/naming view with the original video.
* **AC3.1:** When a new `PhotosPickerItem` is selected, the `.onChange` modifier **must** first `await unifiedState.prepareForNewVideoSelection()` and then immediately `await unifiedState.handleVideoSelection(newItem)`.
* **AC4.1:** After the loading sequence completes (logged as `PRD_CRITICAL_FIX_SUCCESS`), the `LoadingOverlayView` dismisses, and the `TrimmerViewModel` within `AddMoveUnifiedState` is populated with the new video's data, causing the UI to update.

#### **2.3. Edge Cases to Verify**
* **Rapid Taps:** Rapidly tapping the "Change Video" button should only present the picker once.
* **Memory on Repeated Changes:** Changing the video 3-4 times in a row should not result in a compounding increase in memory usage, proving that old assets and view models are being correctly deallocated. The log `🗑️ DiagnosticLoggingHelper deinitialized` is a good indicator of this cleanup.
* **Selection During Network Fluctuation:** Initiate the "Change Video" flow on Wi-Fi, then switch to Cellular while the picker is open before making a selection. The load must proceed correctly on the new network interface.

#### **2.4. Performance & Metrics**
* **P1 (UI Responsiveness):** The latency between tapping "Change Video" and the `PhotosPicker` starting its presentation animation must be **< 50ms**.
* **P2 (Reliability):** The end-to-end success rate of this new flow (tap -> select -> load -> new trimmer) must remain **> 99.9%**.
* **P3 (Cancellation Integrity):** The success rate for the cancellation flow (tap -> cancel -> return to original state) must be **100%**.

### **3. Implementation Plan & Constraints**

#### **3.1. Technical Approach: UI-Driven Modal Flow**
The implementation will shift from a state-driven navigation reset to a UI-driven modal presentation, which then triggers the correct state transitions.

* **Phase 1: Modify UI for Modal Presentation**
    * In the view containing the "Change Video" button (inferred from logs to be `FeatureRichTrimmerView`), introduce `@State private var showPhotoPicker = false` and `@State private var selectedItem: PhotosPickerItem?`.
    * The "Change Video" button's action will be simplified to a single line: `showPhotoPicker = true`. This decouples the UI action from the state logic.

* **Phase 2: Implement the Selection-Triggered Workflow**
    * Attach a `.photosPicker` modifier to the view, bound to `$showPhotoPicker` and `$selectedItem`.
    * Implement the `.onChange(of: selectedItem)` modifier. This is the new control point for the entire workflow. Inside its closure, perform the following sequence:
        1.  Guard against a `nil` new item.
        2.  `await unifiedState.prepareForNewVideoSelection()`: Execute the proven atomic state reset.
        3.  `await unifiedState.handleVideoSelection(newItem)`: Pass the new item to the existing handler, which triggers the resilient loading pipeline.

#### **3.2. Code Reference Points (GrepTool Commands)**
* **Locate the "Change Video" button's view:** The logs indicate this is where the `User Interaction` originates.
    * `GrepTool(pattern="User Interaction: Video replacement initiated", path="18. logs.md")`

* **Reference the Back Button Action:** The `handleBackButton` in `NameMoveViewUnified.swift` provides a pattern for a UI element invoking a function on the `unifiedState` object. The "Change Video" button will be modified to follow a similar, but modal, pattern.
    * `GrepTool(pattern="handleBackButton", path="NameMoveViewUnified.swift")`

* **Identify the State Reset Logic to Encapsulate:** The new `prepareForNewVideoSelection()` function should be modeled directly on the successful reset sequence captured in the logs.
    * `GrepTool(pattern="ATOMIC_STATE_RESET_MORPHISM", path="18. logs.md")`

#### **3.3. Constraints**
* The implementation must not introduce a "Change Video" button in `NameMoveViewUnified.swift`. The "Back" button on that screen correctly handles the transition back to the trimmer, which is the appropriate place for a "Change Video" action.
* The `prepareForNewVideoSelection()` function in `AddMoveUnifiedState` must be the *single source of truth* for the reset logic. Do not duplicate reset logic in the UI layer.
