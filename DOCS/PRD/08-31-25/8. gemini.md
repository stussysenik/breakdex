## **PRD: BreakDex Photos-Native Architecture**

* **Version:** 1.0
* **Status:** Ready for Implementation
* **Author:** Gemini
* **Last Updated:** August 31, 2025

### 1. Overview & Vision

This document outlines a fundamental architectural shift for the BreakDex application. We are moving away from an internal, file-based video management system to a **Photos-native architecture**. [cite_start]The user's Photos library will become the single source of truth for all video content, managed through a dedicated "BreakDex" album[cite: 1].

This change will simplify the codebase, increase reliability, and provide users with a transparent and familiar way to manage their video assets. [cite_start]The application's focus will shift from complex media management to its core business logic: the learning and review system[cite: 1].

### 2. Problem Statement

The current architecture, which copies videos into the app's sandboxed directory, has several critical drawbacks:
* **Data Silo:** Videos are hidden from the user within the app's internal storage, preventing them from managing these files through the familiar Photos app.
* **Redundant Storage:** The same video may exist in the user's Camera Roll and within the app, consuming unnecessary device space.
* **Brittle References:** File-path-based references are fragile and can break.
* [cite_start]**Code Complexity:** Significant custom code exists to manage file I/O, thumbnail generation, and indexing—functionality that the iOS Photos framework provides natively and more efficiently[cite: 1].

### 3. Goals & Success Metrics

#### **Product Goals**
* [cite_start]**Increase User Trust:** By making the video storage transparent and user-controllable via the Photos app[cite: 1].
* [cite_start]**Improve App Performance:** Leverage the highly optimized Photos framework for streaming, caching, and thumbnail generation[cite: 1].
* [cite_start]**Enhance Data Portability:** Make the import/export of a user's learning library robust and reliable, even across different devices[cite: 1].
* [cite_start]**Reduce Codebase Complexity:** Eliminate redundant media management code, making the app easier to maintain and extend[cite: 1].

#### **Success Metrics**
* [cite_start]**Data Integrity:** 100% of existing user videos are successfully migrated and remain accessible after the update[cite: 1].
* [cite_start]**Performance:** Video playback starts near-instantly, streaming directly from the Photos library[cite: 1].
* [cite_start]**Stability:** A >5% failure rate in video playback or a significant number of data migration errors will trigger a rollback[cite: 1].
* [cite_start]**Adoption:** Successful creation of the "BreakDex" album for all new and existing users post-update[cite: 1].

### 4. Core Architectural Principles (The Axioms)

The new architecture is founded on 10 deterministic axioms that must be followed:

1.  **Photos Album as Primary Storage:** All videos will be stored in a dedicated "BreakDex" album within the user's Photos app. [cite_start]The app will manage this album using `PHAssetCollection` APIs[cite: 1].
2.  **Core Data Stores Only Metadata:** Core Data will no longer store file paths. [cite_start]It will store the `photosIdentifier` from the Photos framework, alongside trim ranges and learning data[cite: 1].
3.  **Streaming Playback with On-the-Fly Trimming:** Videos will be streamed directly from Photos using `PHAssetResourceManager`. [cite_start]Trim ranges will be applied in real-time using `AVPlayerItem.timeRange` without creating local copies[cite: 1].
4.  [cite_start]**Proactive Health Checks:** On every launch, the app will verify Photos permission and the existence of the "BreakDex" album to prevent errors before they occur[cite: 1].
5.  [cite_start]**Video Import via Album Copy:** Adding a new move will copy the selected video into the "BreakDex" album using `PHAssetChangeRequest`, ensuring a reliable reference[cite: 1].
6.  [cite_start]**Graceful Error Handling for Missing Videos:** The system must detect when a video is missing from the Photos library (e.g., user deleted it) and provide a UI for the user to re-link their metadata to a new video[cite:1].
7.  **Metadata-Driven Learning System:** The core review and flashcard systems will remain driven by the metadata stored in Core Data. [cite_start]Videos will be streamed on demand during sessions[cite: 1].
8.  [cite_start]**Album Content Synchronization:** The app will periodically synchronize its Core Data records with the contents of the "BreakDex" album to maintain data integrity and handle cases where a user manually adds or removes a video from the album[cite: 1].
9.  **Consolidate Media Management:** Redundant, file-based media management classes (`MediaManager.swift`, `MediaIndexManager.swift`, `ThumbnailGenerator.swift`) will be deleted. [cite_start]The Photos framework will handle these tasks natively[cite: 1].
10. **Streamlined Video Processing:** Local video trimming that results in file exports will be removed. [cite_start]Trimming will now only save metadata (time ranges) that are applied during streaming playback[cite: 1].

### 5. Functional Requirements

#### **5.1. First Launch & Setup**
* As a new user, the app must request permission to access my Photos library.
* [cite_start]Upon granting permission, the app must create a new album named "BreakDex" in my Photos app[cite: 1].
* [cite_start]As an existing user, the app must check for permission and album existence on first launch after the update[cite: 1].

#### **5.2. Video Management**
* [cite_start]When I add a move, the app must copy the selected video into the "BreakDex" album and store its metadata in Core Data[cite: 1].
* [cite_start]When I trim a video, the app must save the start and end times as metadata without creating a new, trimmed video file[cite: 1].
* [cite_start]When I view a move or combo, the video player must stream the video directly from the "BreakDex" album and apply the saved trim range during playback[cite: 1].

#### **5.3. Data Portability & Recovery**
* [cite_start]When I export my library, the app must generate a metadata file containing all learning data and the `photosIdentifier` for each video[cite: 1].
* [cite_start]When I import a library, the app must intelligently match the `photosIdentifier`s with videos in my "BreakDex" album and automatically create the corresponding moves[cite: 1].
* [cite_start]If an imported move's video is not found, the app must add it to a "Re-link Queue" and provide a UI for me to manually select a replacement video from my Photos library[cite: 1].
* [cite_start]If a video is missing during normal playback, the `VideoRelinkManager` must be triggered, presenting a UI for me to find a replacement video[cite: 1]. [cite_start]This re-link feature becomes the central "Recovery Hub" for all missing video scenarios[cite: 1].

### 6. Phased Implementation Plan

[cite_start]This project will be implemented in four distinct, risk-managed chunks[cite: 1].

* **Chunk 1: Foundation (Low Risk):** Implement the non-breaking infrastructure. Create `PhotosPermissionManager` and `BreakDexAlbumManager`. Update the Core Data schema with a lightweight migration. [cite_start]This phase is purely additive[cite: 1].
* **Chunk 2: Import Flow (Medium Risk):** Rework the `AddMoveViewModel` and `TrimmerViewModel` to be album-based. [cite_start]This can be developed alongside the existing flow and enabled with a feature flag[cite: 1].
* **Chunk 3: Playback System (High Risk):** This is the most critical phase. Modify `CustomVideoPlayerView` to stream from Photos and apply trims. [cite_start]This will temporarily break all video playback until complete[cite: 1]. [cite_start]Implement the `VideoRelinkManager` for error recovery[cite: 1].
* **Chunk 4: Cleanup & Migration (High Risk):** After all new systems are validated, implement the data migration logic for existing users. [cite_start]Finally, delete the legacy files (`MediaManager.swift`, etc.)[cite: 1].

### 7. Scope: File System Impact

#### [cite_start]**Files to CREATE** [cite: 1]
* `BreakDexAlbumManager.swift`: Manages all interactions with the "BreakDex" Photos album.
* `PhotosPermissionManager.swift`: Handles all permission requests and status monitoring.
* `VideoRelinkManager.swift`: Provides the UI and logic for recovering missing videos.
* `AlbumSyncManager.swift`: Reconciles Core Data metadata with the album's contents.

#### [cite_start]**Files to MODIFY** [cite: 1]
* `Move+CoreDataProperties.swift`: Add new fields for `photosIdentifier`, `trimStartTime`, `trimEndTime`.
* `AddMoveViewModel.swift`: Rework to use album-based import logic.
* `CustomVideoPlayerView.swift`: Rework for Photos streaming and real-time trim application.
* `TrimmerViewModel.swift`: Rework to store trim ranges as metadata only.
* `BreakingFlashcardsApp.swift`: Add album health checks on launch.
* `ReviewView.swift`: Update to load move metadata and stream videos on demand.

#### [cite_start]**Files to DELETE** [cite: 1]
* `MediaManager.swift`: Redundant, as the Photos framework handles media management and caching.
* `MediaIndexManager.swift`: Redundant, as Photos provides native indexing.
* `ThumbnailGenerator.swift`: Redundant, as `PHAsset` provides thumbnail APIs.
