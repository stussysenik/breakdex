# How OpenSpec works:
⏺ OpenSpec Workflow Explanation

  Based on the documentation, here's how the OpenSpec workflow integrates with TaskMaster for this project:

  OpenSpec Workflow Overview

  OpenSpec provides a three-stage spec-driven development workflow:

  Stage 1: Creating Changes (Proposal Phase)

  - Trigger: New features, breaking changes, architecture shifts, performance optimizations
  - Process:
    a. Review existing specs and changes
    b. Create unique change-id (kebab-case, verb-led like add-video-trimming)
    c. Scaffold proposal files: proposal.md, tasks.md, optional design.md
    d. Write spec deltas using ## ADDED|MODIFIED|REMOVED Requirements
    e. Validate with openspec validate [change-id] --strict
    f. Wait for approval before implementation

  Stage 2: Implementation Phase

  - Process:
    a. Read proposal.md to understand requirements
    b. Read design.md (if exists) for technical decisions
    c. Read tasks.md for implementation checklist
    d. Implement tasks sequentially
    e. Update checklist when complete
    f. Set every task to - [x] when finished

  Stage 3: Archiving Phase

  - Trigger: After deployment
  - Process: Move changes to archive/ and update specs

  Integration with TaskMaster MCP

  TaskMaster handles the task execution and tracking while OpenSpec handles specification and approval workflow:

  1. OpenSpec creates the plan (proposal.md, tasks.md, spec deltas)
  2. TaskMaster manages the implementation (subtasks, dependencies, progress)
  3. Both systems track completion independently

  How We Should Work Together

  For New Features/Changes:

  1. You: "I want to add [feature]"
  2. Me: Check if proposal needed → Create OpenSpec change proposal
  3. You: Review and approve proposal
  4. Me: Use TaskMaster to break down tasks.md into manageable subtasks
  5. Me: Implement using TaskMaster task tracking
  6. Both: Track completion through respective systems

  For Bug Fixes/Small Changes:

  1. Direct implementation without OpenSpec proposal
  2. Use TaskMaster for tracking if multi-step task
  3. Skip OpenSpec entirely (restores intended behavior)

  Current Project State:

  - OpenSpec: No active changes, no specs yet (clean slate)
  - TaskMaster: Initialized but no tasks yet
  - Integration Ready: Both systems operational

  Decision Tree:

  Your request?
  ├─ Bug fix/typo? → Direct implementation
  ├─ New feature? → OpenSpec proposal → TaskMaster execution
  ├─ Breaking change? → OpenSpec proposal → TaskMaster execution
  └─ Unclear? → OpenSpec proposal (safer)

  This ensures spec-driven development with proper approval gates while maintaining efficient task execution through
  TaskMaster's tracking capabilities.

# How I should be using OpenSpec with task-master?

⏺ ELI19: OpenSpec + TaskMaster Workflow

  Think of it like building with LEGOs:

  OpenSpec = The Instruction Manual

  - Before building anything, we create the instruction booklet
  - Shows what we're building, why, and step-by-step plans
  - Must be approved before we start building
  - Lives in openspec/changes/[feature-name]/

  TaskMaster = The Workbench

  - After manual is approved, this tracks actual building progress
  - Breaks big steps into smaller subtasks
  - Shows what's done, what's in progress, what's next
  - Lives in .taskmaster/

  ---
  Your Workflow as Developer:

  1. Want to Build Something New?

  You: "I want to add video trimming feature"
  Me: Creates OpenSpec proposal (the manual)
  You: Review & approve the plan
  Me: Creates TaskMaster tasks from the approved plan

  2. During Development:

  - TaskMaster shows: "Task 3.2: Add trim handles - IN PROGRESS"
  - OpenSpec shows: "This is the approved plan we're following"

  3. Quick Bug Fixes:

  You: "Fix this button not working"
  Me: Fix it directly (no OpenSpec needed)

  ---
  Simple Rules:

  | Task Type   | Use OpenSpec?               | Use TaskMaster?        |
  |-------------|-----------------------------|------------------------|
  | New feature | ✅ Yes (create manual first) | ✅ Yes (track building) |
  | Big change  | ✅ Yes (create manual first) | ✅ Yes (track building) |
  | Bug fix     | ❌ No (just fix it)          | Maybe (if complex)     |
  | Small tweak | ❌ No (just do it)           | ❌ No (just do it)      |

  ---
  Your Mental Model:

  **- OpenSpec = "What are we building and why?" (PLANNING)**
  **- TaskMaster = "Are we done yet?" (EXECUTION)**

  You give me ideas → I make plans → You approve → I build with tracking

  That's it! 🎯
