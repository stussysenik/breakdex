### \#\# 1. Overview & Problem Statement

The application currently experiences an infinite loading state when a user selects a video. The root cause is a race condition: the `AddMoveViewModel` transitions to the `.previewing` state *before* its associated `VideoPlayerViewModel` has finished its asynchronous setup.

This causes the `PreTrimView` to receive a not-yet-ready player. Its internal logic then incorrectly creates a new, "orphan" `VideoPlayerViewModel` instance for display, while the "real" instance, which eventually becomes ready, is never observed by the UI.

The goal of this task is to re-architect this data flow to be explicit and race-condition-free, strictly following the Single Responsibility Principle (SRP) and enhancing observability through detailed logging.

-----

### \#\# 2. Guiding Principles & Acceptance Criteria

  * **Single Responsibility Principle (SRP):** Views must only be responsible for rendering state, not for fetching or creating their own sub-viewmodels. The `AddMoveViewModel` is the sole orchestrator.
  * **Logging-First:** All state transitions and asynchronous boundaries must be logged in detail to ensure future traceability.
  * **Clean & Readable:** The flow of data must be explicit and easy to follow. State should be the single source of truth.
  * **Performant:** The solution should not introduce any unnecessary view updates or data processing.

#### **Acceptance Criteria**

1.  When a user selects a video, the UI correctly displays a loading indicator and then reliably transitions to the `PreTrimView` with a fully playable video.
2.  The "infinite loading" bug is completely eliminated.
3.  No new instances of `VideoPlayerViewModel` are created outside of the `AddMoveViewModel`.
4.  Logs clearly show the point at which the system begins waiting for the `VideoPlayerViewModel` to be ready, and the point at which it succeeds, before the `.previewing` state is set.

-----

### \#\# 3. Proposed Solution & Implementation Steps

The core of the solution is to make the prepared `VideoPlayerViewModel` a direct part of the `AddMoveState`. This makes the player's readiness a prerequisite for the state transition, thus eliminating the race condition at its source.

#### **Step 3.1: Refactor `AddMoveViewModel` and its State**

1.  **Modify `AddMoveState`:** Update the `.previewing` state case to directly hold the prepared `VideoPlayerViewModel`. This makes the state fully self-sufficient.

      * **File:** `AddMoveViewModel.swift`
      * **Change:**
        ```swift
        // FROM:
        case previewing(asset: AVAsset, photosIdentifier: String?, rotationQuarterTurns: Int)

        // TO:
        case previewing(playerViewModel: VideoPlayerViewModel, asset: AVAsset, photosIdentifier: String?, rotationQuarterTurns: Int)
        ```

2.  **Update `prepareVideoForDisplay` Logic:** Modify this function to wait for the `VideoPlayerViewModel` to become fully ready *before* setting the `.previewing` state.

      * **File:** `AddMoveViewModel.swift`
      * **Logic:**
        ```swift
        // Inside the Task block of prepareVideoForDisplay(from:)

        // ... after videoLoader.loadVideo(from:) succeeds ...
        let result = try await videoLoader.loadVideo(from: item)

        logger.info("🎬 VIEWMODEL: Creating VideoPlayerViewModel synchronously.")
        let playerViewModel = VideoPlayerViewModel(asset: result.asset, rotationQuarterTurns: 0)
        self.currentVideoPlayerViewModel = playerViewModel

        // --- NEW LOGIC ---
        logger.info("🎬 VIEWMODEL: ⏳ Waiting for VideoPlayerViewModel to become ready...")
        try await playerViewModel.waitForReady() // Wait for the player's async setup to complete.
        logger.info("🎬 VIEWMODEL: ✅ VideoPlayerViewModel is ready.")
        // --- END NEW LOGIC ---

        if Task.isCancelled {
            logger.info("🎬 VIEWMODEL: Video preparation task was cancelled after player readiness wait.")
            return
        }

        self.selectedFilename = result.filename
        self.currentPhotosIdentifier = result.photosIdentifier

        logger.info("🎬 VIEWMODEL: Transitioning to previewing state with prepared player.")
        self.state = .previewing(
            playerViewModel: playerViewModel, // Pass the ready ViewModel into the state.
            asset: result.asset, 
            photosIdentifier: result.photosIdentifier, 
            rotationQuarterTurns: 0
        )
        ```

#### **Step 3.2: Update `AddMoveContainer`**

Modify the router to extract the `VideoPlayerViewModel` from the new state and pass it down.

  * **File:** `AddMoveContainer.swift`
  * **Change:**
    ```swift
    // Inside the switch statement for viewModel.state

    // FROM:
    case .previewing(let asset, let photosIdentifier, let rotationQuarterTurns):
        logger.info("🎬 CONTAINER: 🎬 Rendering PreTrimView - FINAL STEP")
        // ... (existing logs)
        PreTrimView(viewModel: viewModel, asset: asset, photosIdentifier: photosIdentifier, rotationQuarterTurns: rotationQuarterTurns, selectedTab: $selectedTab)

    // TO:
    case .previewing(let playerViewModel, let asset, let photosIdentifier, let rotationQuarterTurns):
        logger.info("🎬 CONTAINER: 🎬 Rendering PreTrimView with prepared PlayerViewModel.")
        logger.info("🎬 CONTAINER: PlayerViewModel state: \(String(describing: playerViewModel.state))")
        PreTrimView(
            viewModel: viewModel,
            playerViewModel: playerViewModel, // Pass the playerViewModel directly
            asset: asset,
            photosIdentifier: photosIdentifier,
            rotationQuarterTurns: rotationQuarterTurns,
            selectedTab: $selectedTab
        )
    ```

#### **Step 3.3: Simplify `PreTrimView`**

`PreTrimView` can now be a "dumber," more reliable component. It no longer needs to manage its own player state.

1.  **Update `init` and Properties:** Add a property for the `VideoPlayerViewModel` and update the initializer.

      * **File:** `PreTrimView.swift`
      * **Change:**
        ```swift
        @ObservedObject var viewModel: AddMoveViewModel
        @ObservedObject var playerViewModel: VideoPlayerViewModel // NEW: The source of truth for the player
        let asset: AVAsset
        // ...

        init(viewModel: AddMoveViewModel, playerViewModel: VideoPlayerViewModel, asset: AVAsset, /*...*/) {
            self.viewModel = viewModel
            self.playerViewModel = playerViewModel // Initialize it
            self.asset = asset
            // ...
        }
        ```

2.  **Refactor `body` and Remove Faulty Logic:** Use the new `playerViewModel` property directly and delete the old helper function.

      * **File:** `PreTrimView.swift`
      * **Change:**
        ```swift
        // In the body, where the video player is rendered...
        private func renderVideoPlayerSection() -> some View {
            logger.info("🎬 PRE_TRIM_VIEW: Rendering video player section with directly provided ViewModel.")
            // Pass the guaranteed-to-be-ready playerViewModel.
            return CustomVideoPlayerView(viewModel: playerViewModel) 
                .cornerRadius(12)
                .padding(.horizontal)
        }

        // DELETE the entire createOrGetVideoPlayerViewModel() function. It is the source of the bug.
        // DELETE the isValidState() function and its usage. The state transition now guarantees validity.
        ```

### \#\# 5. Rationale & Long-Term Benefits

This refactor provides a more robust and maintainable architecture for several reasons:

  * **Eliminates Race Conditions:** The state transition to `.previewing` is now atomic. The view will not be rendered until its required data (the `VideoPlayerViewModel`) is fully prepared.
  * **Improves SRP & Readability:** `PreTrimView` is simplified to a pure display component. All logic for preparing its dependencies is now correctly located in the `AddMoveViewModel`, making the flow of data explicit and easy to trace.
  * **Enhances Testability:** The `AddMoveViewModel`'s state transitions can be tested more easily, as the readiness of its dependencies is part of the state itself.
