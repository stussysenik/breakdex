### Executive Summary: The Root Cause

The bottleneck is an **incorrect order of operations** in our state transition logic.

Currently, when the user taps "Continue" in the trimmer, the `flowState` is immediately changed to `.naming`. This tells SwiftUI to start destroying the `FeatureRichTrimmerView` and building the `NameMoveViewUnified`. *Concurrently*, our state machine begins executing cleanup logic for the trimming state, such as setting the `trimmerViewModel` to `nil`.

This creates a race condition: SwiftUI's view teardown process might try to access the `trimmerViewModel` at the exact moment our state machine has destroyed it, leading to an undefined state that halts further UI updates. The `NameMoveViewUnified` is technically on screen, but it's "stuck" because the previous view's teardown process interfered with its presentation.

-----

## In-Depth Analysis: The Chain of Failure

By examining the logs and source code, we can see the exact sequence that leads to this frozen state.

1.  **Successful Trimming:** The user interacts with the trimmer, and everything works correctly. The application state is `.trimming`. The logs show no errors.

2.  **The "Continue" Action:** The user taps the "Continue" button in `FeatureRichTrimmerView`. This triggers the `validateAndContinue()` function, which in turn calls `unifiedState.proceedToNextState()`.

3.  **The Race Condition Begins:** Inside `proceedToNextState()` in `AddMoveUnifiedState.swift`, the code immediately calls `await transitionTo(.naming)`.

4.  **The Flawed Order:** The `transitionTo(_:)` function is structured like this:

      * **Step A (Immediate):** It sets `flowState = .naming`. This is a `@Published` property, so it instantly notifies SwiftUI to start destroying the old view (`FeatureRichTrimmerView`) and building the new one (`NameMoveViewUnified`).
      * **Step B (Concurrent):** It then proceeds to execute the logic inside the `case .naming:` block, which includes `await cleanupTrimmerViewModel()`.

5.  **The Collision:** While SwiftUI is in the middle of its complex, asynchronous view transition, our code pulls the rug out from under it by calling `cleanupTrimmerViewModel()`, which sets `self.trimmerViewModel = nil`. The `FeatureRichTrimmerView`, which is still being torn down, suddenly loses its `viewModel`. This interruption of the view lifecycle causes the UI rendering system to halt, leaving the `NameMoveViewUnified` "stuck on the preview."

-----

## What We Are Still Doing Wrong

  * **Violating State Machine Principles:** We are not fully completing the exit logic for the `.trimming` state before entering the `.naming` state. Cleanup should be an integral part of leaving a state, not an action performed after the transition has already begun.
  * **Conflating State Change with Cleanup:** The `transitionTo` function is trying to do two things at once: change the state *and* perform the cleanup for the state it's transitioning *to*. This is architecturally unsound.

## What We Are Still Missing

We are missing a **strict, sequential ordering of operations.** A robust state machine must guarantee that all actions associated with leaving a state (like cleanup) are fully completed *before* the system formally enters the next state.

This solution restructures the state transition logic to be sequential and deterministic, eliminating the race condition permanently.

### ✅ **Task 1: Correct the Order of Operations in State Transitions (The Core Fix)**

We will modify `AddMoveUnifiedState` to ensure cleanup happens *before* the state change, not during or after.

  * **File:** `AddMoveUnifiedState.swift`

  * **Action:** Restructure the `proceedToNextState()` function to handle the cleanup for the `.trimming` state *before* it calls `transitionTo(.naming)`. Then, remove the cleanup call from within the `transitionTo(.naming)` case.

  * **Modification 1: Update `proceedToNextState`**

      * **From**:
        ```swift
        public func proceedToNextState() async throws {
            switch flowState {
            // ... other cases
            case .trimming:
                await transitionTo(.naming)
            // ... other cases
            }
        }
        ```
      * **To:**
        ```swift
        public func proceedToNextState() async throws {
            switch flowState {
            // ... other cases
            case .trimming:
                // 🧠 FIRST: Perform all cleanup for the state we are LEAVING.
                await cleanupTrimmerViewModel()
                // 🚀 THEN: Transition to the new state.
                await transitionTo(.naming)
            // ... other cases
            }
        }
        ```

  * **Modification 2: Update `transitionTo`**

      * **From**:
        ```swift

            playerState = .paused
        ```

  * **Rationale:** This change enforces a strict, predictable order. The `trimmerViewModel` is now guaranteed to be `nil` *before* SwiftUI receives the `.naming` state change. This gives SwiftUI a clean slate to work with, allowing it to tear down the old view and build the new one without any mid-transition interference.

### ✅ **Task 2: Harden the Player State Transition**

The logs reveal a minor secondary issue: `pauseForTrimming()` is asynchronous, meaning the player state might not be `.paused` at the exact moment the naming view appears. We can make this more robust.

  * **File:** `UnifiedVideoPlayerViewModel.swift`

  * **Action:** Convert the `pauseForTrimming` function from an asynchronous `Task` to a direct, synchronous MainActor function.

  * **Modification:**

      * **From**:
        ```swift
        public func pauseForTrimming() {
            Task { @MainActor in
                // ... switch state logic ...
            }
            shouldPlay = false
        }
        ```
      * **To:**
        ```swift
        public func pauseForTrimming() {
            logger.info("🎬 UNIFIED_VIDEO_PLAYER_VIEWMODEL (\(mode)): pauseForTrimming() called", metadata: nil)
            // Ensure this runs on the main actor synchronously.
            guard Thread.isMainThread else {
                DispatchQueue.main.async { self.pauseForTrimming() }
                return
            }

            switch state {
            case .playing(let player):
                player.pause()
                videoHealthMonitor.pauseMonitoring()
                state = .paused(player: player)
            case .ready(let player):
                player.pause()
                videoHealthMonitor.pauseMonitoring()
                state = .paused(player: player)
            default:
                break
            }
            shouldPlay = false
        }
        ```

  * **Rationale:** This guarantees that when `pauseForTrimming()` is called during the transition, the player's internal state is updated to `.paused` *immediately* and synchronously. This prevents any ambiguity and ensures the `NameMoveViewUnified` always receives the player in the correct, expected state.
