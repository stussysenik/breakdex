The core problem isn't just a stale flag in the UI; it's a fundamental **deadlock pattern** combined with a **retain cycle** that prevents the "Change Video" workflow from ever completing.

#### The Deadlock Chain of Events:

1.  **User Taps "Change Video":** This action eventually calls `processVideoReplacement()` in `FeatureRichTrimmerView.swift`.
2.  **Synchronous-Looking Async Call:** `processVideoReplacement` is a `func`, but inside it, it calls other `async` functions. Crucially, the old implementation (which the logs and your description point to) likely had a blocking call. The comments in the latest `FeatureRichTrimmerView.swift` explicitly state this was the issue:
    > `ROOT CAUSE: processVideoReplacement() had waitForVideoReady() call that blocked main thread waiting for state changes`
3.  **The Deadlock Morphism:**
      * **Morphism 1 (State Update):** The system calls `unifiedState.didSelectVideo()`. This function dispatches a `Task` to load the new video and eventually update the `flowState`. These state updates *must* happen on the `@MainActor` (the main thread).
      * **Morphism 2 (Blocking Wait):** Simultaneously, the `processVideoReplacement` function (running on the main thread) calls a function like the now-removed `waitForVideoReady()`. This function essentially says, "Pause the main thread until `flowState` changes to `.trimming`."
      * **Non-Commutative Diagram (The Deadlock):** These two operations are a deadlock. The main thread is blocked, waiting for a state change. But the state change can only be processed on the main thread, which is blocked. The app freezes indefinitely at the "Initializing..." stage.
