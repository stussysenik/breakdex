⏺ Engineering Debug Approach: UI/UX Issues → Code Solutions

  The Debug Framework

  Phase 1: Symptom Analysis

  User says: "Stuck at 98%"Developer reality: User sees UI problem, we need code solution

  Key Principle: Translate UI symptoms into technical evidence
  - User perception → Concrete behavior
  - "Stuck at 98%" → What is actually showing? Which loading interface?
  - "Doesn't work" → Exactly what happens vs. what should happen?

  Phase 2: Evidence Collection (Non-Invasive)

  Our approach: Start with existing evidence
  - ✅ Read existing logs - Don't ask user to reproduce yet
  - ✅ Examine code paths - Trace the user flow theoretically
  - ✅ Review historical context - Check previous fixes (frame separation specs)

  Key Principle: Evidence before assumptions
  - Every theory must have supporting evidence
  - Don't change code until you understand the problem
  - Historical context often reveals why current code exists

  Phase 3: Hypothesis Formation

  Our hypotheses (in order of investigation):
  1. Frame separation issue ❌ (Wrong - frame separation was a solution, not problem)
  2. State transition timing ✅ (Partially correct - but needed refinement)
  3. Dual loading interface ✅ (Root cause)

  Key Principle: Multiple working hypotheses
  - Don't commit to one theory too early
  - Use evidence to eliminate incorrect hypotheses
  - Be willing to pivot when evidence contradicts theory

  Phase 4: Strategic Diagnostic Logging

  Our breakthrough: Minimal, targeted logging to validate assumptions

  // Pattern: Log the transition points
  Logger.info("About to call [function] - [context]", emoji: "🎯")
  [function call]()
  Logger.info("[function] completed", emoji: "✅")

  // Pattern: Log state synchronization
  Logger.debug("Component: [property1]: [value1], [property2]: [value2]", emoji: "📊")

  Key Principle: Log the boundaries, not the internals
  - Focus on component interfaces and state transitions
  - Log before/after critical function calls
  - Include property values that affect UI rendering
  - Use emojis for visual scanning in logs

  Phase 5: Evidence-Based Validation

  Our validation method:
  - Added logging only (no behavior changes)
  - Single test run to collect diagnostic data
  - Compare actual behavior against expected behavior

  Key Principle: Validate before you fix
  - Prove your hypothesis with data
  - Don't implement fixes based on assumptions
  - Let the evidence guide the solution

  Guiding Principles for iOS Mobile Development

  1. UI Symptom → Technical Evidence Mapping

  User Symptom                Technical Investigation
  "Stuck at X%"           → Which loading interface? What progress?
  "Doesn't transition"   → What state? What callback chain?
  "Shows wrong thing"    → What view is rendering? What data?

  2. Component Boundary Analysis

  Always trace the full chain:
  Service Layer → ViewModel → View → Parent View → UI
  RobustVideoLoader → AddMoveViewModel → SelectClip → AddMoveView → MinimalTrimmerView

  Key questions at each boundary:
  - What data is passed?
  - When is the callback executed?
  - What state conditions are required?
  - What UI should be visible?

  3. State Synchronization Validation

  For UI issues, always check:
  - Loading states: Asset ready vs. Player ready vs. Fully ready
  - Observer timing: When does @Published trigger vs. when is data actually ready?
  - View lifecycle: onAppear vs. onDisappear vs. state changes
  - Callback execution: Is the callback called at the right time with right data?

  4. Historical Context Awareness

  Before changing anything, ask:
  - Why was this code written this way?
  - What problems were previous fixes addressing?
  - What are the ripple effects of changes?

  Our example: Frame separation was implemented to solve SwiftUI coalescing issues - breaking this would reintroduce old problems.

  5. Progressive Evidence Gathering

  Start non-invasive, escalate as needed:
  1. Code analysis (no runtime)
  2. Existing logs (no new runs)
  3. Diagnostic logging (minimal changes)
  4. Targeted fixes (based on evidence)

  Debug Playbook for Common iOS UI Issues

  Issue: "Loading stuck at X%"

  Debug Steps:
  1. Identify which loading interface is visible
  2. Trace state progression through all components
  3. Check callback chain execution
  4. Validate state synchronization at component boundaries
  5. Look for race conditions or premature transitions

  Issue: "View doesn't update"

  Debug Steps:
  1. Verify @Published property changes are triggering
  2. Check @StateObject/@ObservedObject lifecycle
  3. Validate view rendering conditions (if/else, switch)
  4. Look for multiple updates per frame warnings
  5. Check for competing state updates

  Issue: "Shows wrong content"

  Debug Steps:
  1. Trace data flow from source to UI
  2. Verify transformation logic in ViewModels
  3. Check view composition and conditional rendering
  4. Validate state timing and synchronization
  5. Look for stale state or caching issues

  Implementation Strategy

  1. Evidence-First Development

  - Never implement fixes without confirming the root cause
  - Always add diagnostic logging before changing behavior
  - Always validate assumptions with actual runtime data

  2. Minimal Intervention Approach

  - Add logging before changing logic
  - Change one thing at a time
  - Test each change independently
  - Preserve existing solutions to previous problems

  3. Systematic Documentation

  - Log the investigation process
  - Document evidence that supports conclusions
  - Note what was ruled out and why
  - Create reproducible debug procedures

  Why This Approach Works

  For Developers

  - Reduces guesswork: Evidence-based decisions
  - Prevents regressions: Understand why code exists before changing
  - Improves efficiency: Targeted fixes instead of trial-and-error
  - Builds confidence: Each step validated with data

  For Users

  - Accurate solutions: Fix the real problem, not symptoms
  - Faster resolution: Systematic approach finds issues faster
  - Better quality: Comprehensive testing prevents regressions
  - Clear communication: Can explain what was found and fixed

# APPROACH:

⏺ Universal Problem-Solving Framework

  Core Principles

  1. Evidence Before Assumptions

  - Never trust initial theories without data
  - Always gather concrete evidence first
  - Validate each hypothesis with real information

  2. Map the System

  - Understand the complete flow from input to output
  - Identify all components and their relationships
  - Trace data/state through every boundary
  - Document interfaces and dependencies

  3. Work Backwards from Symptoms

  - Start with the observable problem
  - Trace backwards through the causal chain
  - Ask "what must be true for this to happen?"
  - Look for the root cause, not just symptoms

  4. Multiple Working Hypotheses

  - Never commit to one theory too early
  - Keep several possibilities in mind
  - Use evidence to eliminate incorrect theories
  - Be willing to pivot when data contradicts assumptions

  5. Non-Invasive Investigation First

  - Code analysis before runtime testing
  - Existing logs before new logging
  - Read-only investigation before modifications
  - Minimal changes before major fixes

  6. Strategic Information Gathering

  - Log boundaries and transitions, not internals
  - Focus on component interfaces and state changes
  - Capture before/after states for critical operations
  - Use patterns that make evidence easy to scan

  7. Isolate Variables

  - Test one thing at a time
  - Change only one variable between experiments
  - Use control groups when possible
  - Document what was held constant

  8. Understand Context and History

  - Ask "why" before asking "how"
  - Learn what problems previous solutions addressed
  - Understand constraints and trade-offs
  - Respect existing architecture and decisions

  9. Progressive Escalation

  - Start with cheapest, lowest-risk investigations
  - Escalate to more invasive methods only when needed
  - Each step should inform the next
  - Stop when you have sufficient evidence

  10. Validate Before Fixing

  - Prove your hypothesis with data
  - Confirm the fix addresses the root cause
  - Test that the solution doesn't create new problems
  - Verify success with the original stakeholder

  The Problem-Solving Algorithm

  1. DEFINE: What is the observable problem?
  2. TRACE: Map the complete system flow
  3. HYPOTHESIZE: Generate multiple possible causes
  4. INVESTIGATE: Gather evidence non-invasively
  5. ANALYZE: Evaluate evidence against hypotheses
  6. ISOLATE: Identify the specific root cause
  7. DESIGN: Create targeted solution
  8. VALIDATE: Test that the fix works
  9. IMPLEMENT: Apply the solution
  10. VERIFY: Confirm the problem is resolved

  Universal Application

  For Technical Problems

  - Code analysis → logs → targeted fixes
  - System architecture → component boundaries → interface issues
  - Performance bottlenecks → profiling → optimization

  For Business Problems

  - Process mapping → stakeholder interviews → root cause analysis
  - Data analysis → hypothesis testing → solution validation
  - User feedback → behavior patterns → experience improvements

  For Personal Problems

  - Self-reflection → pattern identification → behavior modification
  - Goal analysis → constraint identification → strategic planning
  - Habit tracking → root cause understanding → systematic change

  Mindset Shifts

  From "I think" to "I can prove"

  - Replace assumptions with evidence
  - Use data to support conclusions
  - Acknowledge uncertainty where evidence is lacking

  From "Fix fast" to "Fix right"

  - Understand before acting
  - Solve root causes, not symptoms
  - Validate solutions before implementation

  From "Blame" to "Understand"

  - Focus on systems, not people
  - Learn from failures and mistakes
  - Improve processes, not assign fault

  From "Complex solutions" to "Simple truths"

  - Look for elegant, minimal interventions
  - Prefer solutions that address core issues
  - Value simplicity over complexity

  Success Indicators

  You're on the right track when:

  - Each step reduces uncertainty
  - Evidence supports your current theory
  - Solutions become clearer, not more complex
  - Stakeholders can follow your logic

  You need to step back when:

  - You're making assumptions without data
  - Solutions are creating more problems
  - Multiple hypotheses remain equally likely
  - Progress stalls despite increased effort

  This framework works because it respects complexity while providing a systematic way to reduce it to manageable, solvable pieces. It transforms confusion into clarity through
   evidence-based reasoning.
