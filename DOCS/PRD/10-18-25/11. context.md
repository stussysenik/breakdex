⏺ The Duplicate Observer Issue Explained

  The Core Problem: Competing onChange Handlers

  When AddMoveViewModel.coordinatePlayerInitialization() updates the @Published loadingState property, both of these fire simultaneously:

  1. AddMoveView line 70: .onChange(of: viewModel.loadingState) { _, newState in
    - Manages step transitions (ready → selecting → trimming)
    - Calls handleLoadingStateChange(newState)

  2. SelectClip (internal loading UI):
    - Displays loading progress bar (0% → 100%)
    - Updates loading UI components

  The Collision Timeline:

  ViewModel: loadingState = 95%  →  publishes change
      ├── AddMoveView.onChange: "Should I transition steps?" (evaluates)
      └── SelectClip.onChange: "Update progress bar to 95%" (updates UI)

  ViewModel: loadingState = 99%  →  publishes change
      ├── AddMoveView.onChange: "Should I transition steps?" (evaluates)
      └── SelectClip.onChange: "Update progress bar to 99%" (updates UI)

  ViewModel: loadingState = fullyReady  →  publishes change
      ├── AddMoveView.onChange: "Transition to trimming step!" (updates step)
      └── SelectClip.onChange: "Hide loading UI!" (updates view)

  Why This Breaks SwiftUI:

  SwiftUI's update coalescing mechanism sees these as "multiple updates per frame" to the same view hierarchy and treats it as a performance violation. It then:

  1. Drops the final state (fullyReady) to prevent update storms
  2. Leaves the UI stuck at the previous state (around 94-95%)
  3. Generates the warning: "onChange action tried to update multiple times per frame"

  The Evidence in Logs:

  - Line 57: Warning occurs BEFORE the 90%+ progress starts
  - Lines 109-111: ViewModel successfully reaches 100%
  - But the UI never reflects this final state because SwiftUI dropped it due to the collision

  The Fix: Remove the duplicate observer in AddMoveView and let SelectClip handle loading state exclusively, then communicate step completion through callbacks instead of
  competing onChange handlers.
