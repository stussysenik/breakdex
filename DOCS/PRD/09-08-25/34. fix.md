Ideal direction: fix state ownership and lifetimes, unify rotation+trim into AVFoundation compositions for both preview and export, and isolate PhotoKit into a typed, cancelable wrapper so async work can’t race or leak. [1][2][3]

## Objective
- Deliver a stable add-move flow where rotation changes update preview immediately, trim is accurate, and the exported file exactly matches the preview without black frames or state resets. [1][3]
- Remove fundamental causes of failure: incorrect SwiftUI object ownership, broken state propagation to the builder, racy PhotoKit downloads, and uncoordinated async cancellations. [1][2]

## Root causes to address
- Misplaced **StateObject** leads to multiple TrimmerViewModel instances, resets, and “accessing StateObject without being installed on a View” warnings. [1][2]
- Rotation state never reaches the VideoTransformBuilder, so preview/export always compute for quarterTurns=0 despite UI showing 1–3. [1]
- PhotoKit requests race and cancel each other as rotation changes rebuild playback during ongoing iCloud downloads. [1][4]
- Two concurrent “process selection” paths run, indicating the state machine lacks single ownership and reentrancy guards. [1]

## Design principles
- View creates and owns one model: initialize long‑lived models with @StateObject in the topmost owning view, and pass them down as @ObservedObject, never recreating them on updates. [1][2][5]
- One source of truth: rotationQuarterTurns and trimRange live in a single view model and are the only inputs to the AV composition builder used for both preview and export. [1][6]
- Playback/export parity: use AVPlayerItem.videoComposition for preview and the same AVMutableVideoComposition for export, avoiding any SwiftUI transforms on video. [1][3][7]
- Cancel and isolate: wrap PhotoKit in a **PhotosClient** actor that provides typed async APIs and explicit cancel via PHImageManager.cancelImageRequest(_:) tied to Task cancellation. [1][4][8]

## State model and ownership
- AddMoveContainer.swift: create @StateObject var addMoveVM and @StateObject var trimmerVM at the container boundary to ensure a single lifetime for the entire add-move flow. [1][2]
- TrimmerView.swift: receive TrimmerViewModel as @ObservedObject and never initialize it locally, preventing SwiftUI from recreating it on every body recompute. [1][5]
- rotationQuarterTurns and trimRange reside in TrimmerViewModel and are updated via intent methods, not via ad-hoc local state, ensuring builder sees the correct values. [1][6]

## Data flow and synchronization
- Flow: PHAsset → PhotosClient.resolveAsset → file-backed AVAsset → TrimmerViewModel.state(rotation, trim) → VideoTransformBuilder.build → AVPlayerItem.videoComposition → SwiftUI overlays (no transforms). [1][3][4]
- All rotation button taps call trimmerVM.setRotation(nextQuarterTurns) which updates rotationQuarterTurns and triggers a debounced rebuild of the AVPlayerItem on a serial Task queue to avoid floods. [1][9]
- The same rotationQuarterTurns and trimRange are passed to export, guaranteeing WYSIWYG between preview and saved video. [1][3]

## Concurrency and cancellation
- New actor Managers/Photos/PhotosClient.swift: encapsulates PHImageManager.requestAVAsset(forVideo:) with networkAccessAllowed and progress, returning a concrete AssetHandle and canceling requests with cancelImageRequest on Task cancellation. [1][8][4]
- TrimmerViewModel coordinates a single in-flight “prepare player item” Task; starting a new rotation/trim cancelably cancels the prior Task before starting a new one. [1][9]
- Export runs as a single Task with explicit state, cannot overlap with a live re-prepare unless user cancels; UI disables export button during in-flight export to prevent double processing. [1][9]

## Composition pipeline
- Video/Processing/VideoTransformBuilder.swift: given (asset, trimRange, quarterTurns) returns (AVMutableComposition, AVMutableVideoComposition), applying T · Ruser · Rsrc and swapping renderSize for 90°/270°. [1][7][3]
- Preview: create AVPlayerItem(asset: composition) and set item.videoComposition to the returned AVMutableVideoComposition; assign to the long‑lived AVPlayer. [1][3][9]
- Export: reuse the same AVMutableVideoComposition on AVAssetExportSession.videoComposition; select a composition-capable preset; never use Passthrough when transforms are present. [1][7][3]
- Guard file-backed media: AVPlayerItem.videoComposition only works on file-based media; materialize non-file assets before building to avoid silent failures. [1][3][10]

## File-by-file changes
- Views/Arsenal/AddMove/AddMoveViewModel.swift
  - Replace withCheckedThrowingContinuation usage with calls into PhotosClient.resolveAsset(for:allowNetwork:) to remove generic inference ambiguity and to centralize cancellation. [1][8][11]
  - State enum carries photosIdentifier, file-backed AVAsset URL, rotationQuarterTurns, and trim times; no transient model re-creation during rotation. [1][6]
- Views/Video/Trim/TrimmerViewModel.swift
  - Own rotationQuarterTurns and trimRange; expose setRotation(_:) and setTrimRange(_:) that schedule a single debounced preparePreview() Task using the builder and replace the AVPlayerItem atomically. [1][9]
  - Maintain one AVPlayer for the view lifetime; set playerItem.seekingWaitsForVideoCompositionRendering = true for precise scrubs. [1][12]
- Views/Video/Trim/TrimmerView.swift
  - Hold @ObservedObject var trimmerVM injected from parent; remove any .rotationEffect/.transformEffect on the player hierarchy; overlays remain untransformed. [1][5]
  - onRotate action calls trimmerVM.setRotation((current+1) % 4); no direct SwiftUI rotation applied to VideoPlayer or parent ZStacks. [1]
- Views/Video/Player/CustomVideoPlayerView.swift
  - Stop rotating the SwiftUI view tree; build an AVPlayerItem via the builder with videoComposition and present with VideoPlayer or AVPlayerLayer-backed UIViewRepresentable. [1][3]
- Views/Arsenal/AddMove/NameMoveView.swift
  - Build preview player item via builder using persisted rotationQuarterTurns and trimRange, not via visual transforms, to ensure parity. [1][3]
- Managers/Photos/PhotosClient.swift (new)
  - Provide resolveAsset(for:allowNetwork:) async throws -> AssetHandle and a progress AsyncStream; wire cancelImageRequest(_:) to Task cancellation and serialize overlapping requests per asset. [1][4][8]
- Video/Processing/VideoTransformBuilder.swift
  - Implement T · R(θ) · Rsrc math and renderSize; expose build(asset:trim:quarterTurns:) for reuse by preview/export; ensure only one instruction spanning the full time range. [1][7][3]

## Invariants and assertions
- A video player hierarchy must have no non-identity transforms; add a debug assertion to guard against accidental .rotationEffect reintroduction. [1]
- There is exactly one TrimmerViewModel instance during the add-move flow; assert that rotationQuarterTurns never resets during a single screen lifetime. [1][2]
- AVPlayerItem.videoComposition is only set on file-backed media; assert and fallback to materialization otherwise. [1][3][10]

## Telemetry
- Log rotationQuarterTurns, trimRange, renderSize, export preset, preparePreview and export durations, and whether materialization was required. [1][9]
- Count cancellations from PhotoKit and player-prep to detect excessive churn from UI taps; tune debounce accordingly. [1][4]

## Testing matrix
- State: rapid rotation taps, back/forward navigation, and view reloads; verify no StateObject warnings and rotation value continuity. [1][2]
- Assets: portrait/landscape, slo‑mo/time‑mapped, long 4K HEVC/H.264, and iCloud-only requiring network with progress and cancellation. [1][8]
- Parity: preview orientation equals export orientation; presentation size equals renderSize; duration within ±1 frame; output preferredTransform identity when rotation baked. [1][3]
- Negative: cancel during iCloud download, rotate mid-download, start export while another export is pending; verify single in-flight task and clean cancellation. [1][4]

## Rollout
- Gate with feature flag “AVCompositionRotation”; ship to internal/beta, monitor black-frame incidents, state resets, and cancellation churn; ramp to 100% after stability. [1]
- Keep emergency fallback: disable preview composition (show unrotated preview) while still baking rotation at export to preserve correctness during investigation. [1]

## Acceptance criteria
- No “Accessing StateObject without being installed” warnings; rotation value persists across recomputes and navigation within a single add-move session. [1][2]
- Preview never goes black for any rotation, and matches exported file orientation, size, and duration across local and iCloud assets. [1][3]
- PhotoKit requests cancel cleanly on rotation changes; only one player-prep/export task runs at a time; no double-processing warnings. [1][4]
- No SwiftUI/CALayer transforms on video surfaces anywhere in the add-move flow. [1]
