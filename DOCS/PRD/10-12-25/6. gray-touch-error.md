The standard practice is not to remove the highlight entirely, but to deselect it gracefully so it fades out as the new screen appears. This provides good user feedback while keeping the interface clean. You can do this by deselecting the tapped row right after the tap is registered. It's a small but important detail for a polished user experience.

-----

### In-depth Explanation

In iOS navigation, when you tap a `UITableViewCell` to push a new `UIViewController` onto the navigation stack, the cell remains in its "selected" state. During the push animation (where the new screen slides in from the right), the underlying table view from the previous screen is still visible. If the cell isn't told to deselect, its gray highlight will remain visible until the animation is complete, which is what you're seeing.

The **best practice** is to deselect the row in the `viewWillAppear` method of the view controller that contains the table. This method is called every time the screen is about to be shown. This ensures that if the user navigates to a new screen and then taps the "Back" button, the cell they originally tapped will no longer be highlighted, creating a clean state.

An alternative is to deselect the row immediately within the `tableView(_:didSelectRowAt:)` delegate method, which also resolves the visual glitch during the push animation.
