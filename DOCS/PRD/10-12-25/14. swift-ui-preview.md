⏺ How CreateComboView.swift Affects MainView Preview

  Direct Parent-Child Relationship

  Looking at MainView.swift:34-39, the MainView directly includes CreateComboView() as one of its four tab views:

  // Create Combo Tab
  CreateComboView()
      .tabItem {
          Image(systemName: "wand.and.stars")
          Text("Create Combo")
      }
      .tag(2)

  SwiftUI Preview Rendering Process

  When you run the MainView preview:

  1. MainView Preview Initializes → MainView() is created
  2. TabView Renders All Children → SwiftUI attempts to render ALL tabs immediately
  3. CreateComboView Instantiates → Tries to create the Create Combo tab
  4. @FetchRequest Executes → The malformed fetch request runs without an entity
  5. Core Data Crash → NSInvalidArgumentException: A fetch request must have an entity
  6. MainView Preview Fails → The entire preview crashes

  The Root Cause Chain

  MainView Preview
      ↓
  TabView renders all tabs
      ↓
  CreateComboView instantiates
      ↓
  @FetchRequest executes without entity
      ↓
  Core Data crashes
      ↓
  MainView preview fails

  Why the Fix Works

  By adding entity: Move.entity() to the @FetchRequest in CreateComboView.swift:

  1. Core Data Knows What to Fetch → The fetch request now has a valid entity
  2. No Exception Thrown → Core Data can execute the request successfully
  3. CreateComboView Renders → The view loads properly
  4. MainView Preview Succeeds → All tabs render without crashing

  ** SwiftUI's "All-or-Nothing" Preview**

  SwiftUI previews try to render the entire view hierarchy, not just the visible tab. So even though CreateComboView is on
  tab 2, it still gets initialized during the MainView preview process, causing the crash.

  Bottom Line: The MainView preview was failing because one of its child views (CreateComboView) had a malformed Core Data
  fetch request that crashed the entire preview rendering process.
