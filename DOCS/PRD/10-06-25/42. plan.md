## **Spec: Implement App-Wide Loading UI and Optimize Player Transition**

### 1\. Overview

  * **1.1. Problem Statement**
    The current implementation presents two critical user experience failures. First, the video loading UI is not persistent; it disappears if the user navigates to another tab, leading to a loss of context and perceived failure. Second, the transition from a completed video load to the interactive trimmer view is resource-intensive, causing significant CPU and memory spikes that can lead to hangs or crashes, especially with older or edited iCloud videos.

  * **1.2. Goal**
    To refactor the loading UI to be a persistent, app-wide modal overlay that is independent of tab navigation. Concurrently, to optimize the post-loading transition by decoupling and deferring player/trimmer initialization, ensuring a smooth, low-resource transition that feels instantaneous to the user.

  * **1.3. Non-Goals**

      * Changing the `UnifiedProgressEngine`'s deterministic weighting.
      * Altering the `ResilientVideoLoader`'s networking logic.

-----

### 2\. User Persona & Journey

  * **2.1. Persona: "The Athlete"**
    This fix directly addresses the persona's needs. A loading process that continues seamlessly in the background regardless of navigation feels robust and trustworthy. A transition to the trimmer that is instantaneous and doesn't strain the device feels like a precise, well-oiled machine.

  * **2.2. User Journey (To Be Achieved)**

    1.  User selects a video (initial or "Change Video").
    2.  The loading overlay appears over the **entire application**.
    3.  User is free to switch to the "Arsenal" or "Review" tab; the loading overlay **remains visible** and continues to show accurate progress.
    4.  When the user returns to the "Add" tab and the loading completes, the app transitions instantly (\<250ms) to the trimmer view without any stutter or lag.

-----

### 3\. Functional Requirements

  * **3.1. Persistent, App-Modal Loading UI**
    The `LoadingOverlayView` must be elevated in the view hierarchy to be independent of the `AddMoveContainer`'s lifecycle. It must be presented whenever `AddMoveUnifiedState.flowState` is `.loadingVideo` and remain visible across all tabs.

  * **3.2. Efficient, Decoupled Player Initialization**
    The process of creating the `UnifiedVideoPlayerViewModel` and `TrimmerViewModel` must be deferred from the critical state transition path. The transition from `.loadingVideo` to `.trimming` should be a lightweight state change, with the view itself handling the creation of its necessary view models upon appearance.
