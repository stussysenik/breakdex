## 1\. Overview (What & Why)

### 1.1. Goal

This specification outlines the critical fixes required to eliminate a deadlock in the "Change Video" workflow and resolve a UI stall when saving a move. The core goal is to refactor the state management around video replacement to be **fully synchronous and non-blocking**, ensuring the UI remains "snappy" and responsive, consistent with the "Athlete" persona's expectations of a high-precision tool.

### 1.2. User Persona & Journey

  * **Persona:** "The Athlete" – Values speed, precision, and frictionless workflows.
  * **Pain Points:**
    1.  **Change Video Deadlock:** After trimming a video, tapping the "Change Video" button causes the app to hang indefinitely. The user is stuck and must force-quit the application.
    2.  **Save Move Stall:** After naming a move and tapping "Save," the UI sometimes freezes before the save operation completes, creating ambiguity and frustration.

### 1.3. User Stories

  * **US-1:** As an athlete, when I tap "Change Video," I want the photo picker to appear instantly so I can immediately select a new clip without any delay or hang.
  * **US-2:** As an athlete, when I tap "Save Move," I want the UI to remain responsive and provide clear feedback so I know the save is in progress without the app freezing.

### 1.4. Non-Goals

  * Re-architecting the `UnifiedProgressEngine`.
  * Changing the underlying `AVAsset` composition logic in `VideoTransformBuilder`.

### ✅ **Step 1: Identify the Blocking Operation in `FeatureRichTrimmerView`**

The logs clearly indicate that the `video_replacement` task, initiated from `FeatureRichTrimmerView`, is blocking for 12.4 seconds. Your first step is to locate the exact code responsible.

1.  **Locate the video replacement method:**
    ```bash
    GrepTool(pattern="processVideoReplacement", path="FeatureRichTrimmerView.swift")
    ```
2.  **Analyze:** The logs state `CRITICAL_FIX_DEADLOCK: Starting SYNCHRONOUS video replacement` and `processVideoReplacement is now synchronous`. This confirms the function itself is synchronous, but it is kicking off an `async` operation (`didSelectVideo`) and improperly waiting for it to finish, thus blocking the main thread.

### ✅ **Step 2: Refactor for Non-Blocking Task Initiation**

Modify the implementation to launch the video replacement process as a background task without blocking the main thread. This decouples the UI response from the background processing.

1.  **Locate the call to the state machine:**

    ```bash
    GrepTool(pattern="didSelectVideo", path="FeatureRichTrimmerView.swift")
    ```

2.  **Action:** The `processVideoReplacement` method must remain synchronous. Inside it, wrap the call to `unifiedState.didSelectVideo(tempVideoSelection)` in a detached `Task`. **Do not `await` this task.** The function should return immediately after launching the task.

    **Conceptual Code Change:**

    ```swift
    // In FeatureRichTrimmerView.swift

    // BEFORE (Hypothesized based on logs - blocking behavior)
    private func processVideoReplacement() {
        // ...
        // This is effectively blocking the main thread.
        Task {
            await unifiedState.didSelectVideo(tempVideoSelection)
        }
        // ... function waits here for the Task to finish ...
    }

    // AFTER (Correct non-blocking implementation)
    private func processVideoReplacement() {
        // ...
        guard let tempVideoSelection = tempVideoSelection else { return }

        // Launch the long-running task in the background.
        Task {
            await unifiedState.didSelectVideo(tempVideoSelection)
        }
        
        // Return immediately, allowing the UI to stay responsive.
        logger.info("✅ Non-blocking video replacement initiated. UI is free.")
    }
    ```
