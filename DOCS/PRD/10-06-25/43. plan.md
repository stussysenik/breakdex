## **Spec: Implement App-Wide Persistent Loading UI & Optimize Player Transition**

### 1\. Overview

  * **1.1. Problem Statement**
    The application currently suffers from two critical, user-facing flaws:

    1.  **Ephemeral UI State:** The video loading overlay is architecturally tied to a specific tab's view hierarchy. When the user navigates to another tab, SwiftUI removes the loading view, giving the false impression that the background loading process has failed.
    2.  **Resource Contention:** The transition from a completed video load to the interactive trimmer view is inefficient. It triggers significant CPU and memory spikes (`143.1% CPU`, `Memory warning received`) when initializing player components for older or large iCloud videos. This resource contention leads to a sluggish user experience, hangs, or intermittent crashes, which users perceive as the feature "not working" on those videos.

  * **1.2. Goal**
    To architect a fully persistent, app-wide loading UI that is decoupled from any single view's lifecycle. Concurrently, to optimize the post-loading state transition by deferring and simplifying the creation of resource-intensive player components, ensuring a consistently smooth, fast, and reliable user experience that aligns with the "mechanical watch" design principle.

  * **1.3. Non-Goals**
