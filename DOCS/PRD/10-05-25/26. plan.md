### **1. Overview (The "What" and "Why")**

#### **1.1. Goal**
To re-architect the video loading pipeline to be **100% transparent, reliable, and deterministic**. The end state will provide the user with precise, real-time feedback on the loading process and gracefully handle common environmental failures, such as network interruptions.

#### **1.2. Problem Statement**
The current video loading implementation suffers from a **state synchronization flaw**. A generic, high-level status message (`loadingStatusMessage` in `AddMoveUnifiedState`) overrides the detailed, real-time status from the low-level `UnifiedProgressEngine`. This results in a user-facing UI that is opaque ("Loading from iPhone..."), misleading, and occasionally stalls without a clear reason, failing to meet the precision demanded by our target persona.

#### **1.3. User Persona & Journey**
* **Persona:** "The Athlete" — Values precision, reliability, and frictionless tooling. They have zero tolerance for ambiguity or perceived hangs in a core workflow.
* **User Journey:**
    1.  The user selects a video from their photo library to add as a "move."
    2.  If the video is in iCloud, the app begins downloading it.
    3.  During download and subsequent processing, the user sees a loading overlay.
    4.  **Desired Experience:** The overlay provides a continuously updating, specific status (e.g., "Downloading from iCloud 21%," "Generating Thumbnail," "Validating Video...") until the video is ready for trimming. The process feels mechanical, precise, and trustworthy.

#### **1.4. Desired Outcomes**
* **Increased User Trust:** Eliminate all loading stalls and opaque messages to build confidence in the app's reliability.
* **Reduced User Friction:** A transparent process removes cognitive load, allowing the user to focus on their training, not on debugging the app.
* **Improved Diagnosability:** Granular state logging will dramatically reduce the time required to debug future video-related issues.

#### **1.5. Non-Goals**
* This refactor will **not** change the UI/UX of the video trimming screen itself.
* This work will **not** implement background uploading capabilities (this will be addressed in a separate spec).
* This will **not** alter the existing video compression or transcoding logic.

### **2. Functional Specification**

#### **2.1. Core Requirements (User Stories)**
1.  **`STORY-101`**: As an athlete, I want to see precise, real-time status updates during video loading so that I understand exactly what the app is doing and how long it will take.
2.  **`STORY-102`**: As an athlete, I want the app to gracefully handle a temporary network interruption during an iCloud download so that I don't lose progress or have to restart the process.

#### **2.2. Acceptance Criteria (AC)**

**For `STORY-101` (Transparency):**
* `AC-101.1`: The status message displayed in `LoadingOverlayView` **MUST** be sourced *exclusively* from the `unifiedState.unifiedProgressEngine.unifiedStatus` property.
    * **Verification:** `GrepTool(pattern="unifiedState.loadingStatusMessage", path="LoadingOverlayView.swift")` should yield no results in the `statusMessage` computed property, except for the line being removed.
* `AC-101.2`: The `loadingStatusMessage` property on `AddMoveUnifiedState` **MUST** be removed entirely to eliminate the dual source of truth.
    * **Verification:** `GrepTool(pattern="loadingStatusMessage", path="AddMoveUnifiedState.swift")` should yield no results.
* `AC-101.3`: The `UnifiedProgressEngine.LoadingPhase` enum **MUST** be expanded to include the following new, distinct phases: `requestingDownload`, `waitingForNetwork`, and `generatingThumbnail`.
* `AC-101.4`: Each new phase **MUST** have a corresponding user-facing status string (e.g., "Requesting Download," "Waiting for Network...").
* `AC-101.5`: The progress calculation **MUST** remain deterministic, with the sum of all `phaseWeights` in `UnifiedProgressEngine` equaling exactly `1.0`.

**For `STORY-102` (Resilience):**
* `AC-102.1`: When network connectivity is lost during the `.downloadingFromCloud` phase, the engine **MUST** transition to the `.waitingForNetwork` phase within 2 seconds.
* `AC-102.2`: While in the `.waitingForNetwork` phase, the UI **MUST** display "Waiting for Network..." and the progress bar **MUST** halt.
* `AC-102.3`: When network connectivity is restored, the engine **MUST** automatically transition back to `.downloadingFromCloud` and resume the download.

#### **2.3. Edge Cases & Constraints**
* **Zero-Byte File:** If a selected video asset is empty or corrupted, the process must immediately transition to a `Failure` state with a descriptive error.
* **Unsupported Codec:** If the local video file cannot be processed by `AVFoundation`, the process must fail gracefully with a "Video format not supported" message.
* **Low Disk Space:** The system must check for sufficient disk space before initiating an iCloud download. If space is insufficient, it must fail with an appropriate user-facing error.
* **Permissions:** If Photo Library permissions are revoked mid-operation, the process must terminate cleanly.

### **3. Non-Functional Requirements (NFRs)**

* **3.1. Performance:**
    * The UI rendering of the progress animation **MUST** maintain a consistent 60 FPS on a target device (iPhone 14 Pro or equivalent).
    * The state transition logic within `UnifiedProgressEngine` **MUST NOT** block the main thread. All operations must be asynchronous.
* **3.2. Reliability:**
    * The video loading success rate for valid, accessible video files **MUST** exceed 99.9%.
* **3.3. Diagnostics & Logging:**
    * Every state transition within `UnifiedProgressEngine` **MUST** be logged via `OSLog` with `info` level, including the "from" and "to" phases.
    * All network connectivity changes detected **MUST** be logged with `debug` level.
    * All failures **MUST** be logged with `error` level, including a correlation ID and a descriptive error message.
* **3.4. Tech Agnosticism (Separation of Concerns):**
    * The logic within `UnifiedProgressEngine` **MUST** remain pure state management logic, with no dependencies on SwiftUI or any other UI framework. Its public API should only expose Combine publishers and simple properties.
